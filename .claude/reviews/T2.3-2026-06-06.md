## Lifecycle trace (Q7 — attempt arithmetic end to end)
`enqueue` defaults `attempt=1`; `retryOrFail` computes `next = job->attempt() + 1` and calls `delayFor($next)`:

| Pop `attempt()` | handler call | outcome | `next` | branch | DB `attempts` | scheduled delay |
|---|---|---|---|---|---|---|
| 1 (initial) | **processing #1** | transient fail | 2 | `2 ≤ 3` → retry | 2 | `delayFor(2)` = 2–4s |
| 2 (retry #1) | **processing #2** | transient fail | 3 | `3 ≤ 3` → retry | 3 | `delayFor(3)` = 4–8s |
| 3 (retry #2) | **processing #3** | transient fail | 4 | `4 > 3` → exhausted | — | interim `markFailed` |

**Result: 3 real processing attempts, 2 scheduled retries** — exactly FR-7 "max 3 attempts". No off-by-one: the increment site is single (`retryOrFail`, `RetryScheduler.php:70`), the boundary is `next > MAX_ATTEMPTS` (`:72`), and the envelope value carried into the zset equals the value written to the DB (`:78-79`). `delayFor(1)` (1–2s) is defined but never used on the retry path — the first *retry* waits `delayFor(2)` = 2–4s.

## At-least-once safety (Q1, Q2 — no job-loss path found)
- **`promoteDueRetries` (`Queue.php:162-184`)** — RPUSH-then-ZREM with skip-ZREM-on-RPUSH-failure is correct. If the process dies between RPUSH and ZREM, the member stays in the zset and is promoted again next sweep (a duplicate, not a loss); the guarded `markProcessing` (`EventRepository.php:116-126`) neutralises the duplicate (second claim matches 0 rows). If RPUSH returns `false`, the member is left in the zset and retried next sweep (`continue`, no ZREM). Both failure modes lean toward **at-least-once, never at-most-once** — the correct bias. Non-atomicity is safe for the single worker and is explicitly documented at the method with the Lua `ZPOPMIN` hardening path named (D2).
- **`retryOrFail` DB-first ordering (`RetryScheduler.php:78-79`)** — `markForRetry` (status→`received`) runs before `scheduleRetry`. If `scheduleRetry` throws, the row is left at the *recoverable* `received` but is on **no** queue. The job is not auto-recovered, but: (a) the throw propagates to the worker's outer backstop (`worker.php:158-164`) which logs it, (b) the row is visible to the dashboard at `received` with a `last_error`, and (c) this is strictly better than the Redis-first alternative, which on a DB failure would leave a job scheduled to re-run against a row still in `processing` (the guard would then *block* the legitimate retry forever). DB-first is the right trade; it is documented at `RetryScheduler.php:60-62`. Acceptable. See NIT-3 for the one residual gap (stranded-`received` row has no reaper) — already shared with T2.2's stuck-`processing` debt.

## Spot-checks (Q3, Q4)
- **Q3 — guarded `markProcessing` re-arm:** `markForRetry` (`EventRepository.php:157-165`) sets `status='received'` with no guard. Correct: the worker holds the row in `processing` (it just won the claim), so it owns this transition; setting back to `received` re-arms the `AND status='received'` claim so the promoted retry wins again. Verified consistent with ADR 0012 Decision 2.
- **Q4 — `scheduleRetry` treats only `false` as failure (`Queue.php:138-145`):** Correct. `zAdd` returns the count of *new* members; a re-scheduled existing member returns `0`, which is a legitimate score-update, not an error. Only `=== false` (genuine Redis failure) throws. Matches the `enqueue` `rPush === false` discipline.

## Findings & dispositions

### NIT-1 — AC-3 wording vs FR-7 (“up to 3 times” vs “max 3 attempts”)
`RetryScheduler.php:31-37`, `:72`. `MAX_ATTEMPTS = 3` = **3 total attempts (2 retries)**, matching FR-7 / CLAUDE.md / `queue-processing/SKILL.md:27-31` ("If attempt > 3 → DLQ"). A literal reading of AC-3 "retried up to 3 times" would be 3 *retries* = 4 attempts. The chosen reading is **defensible and the more authoritative one** (FR-7 is the requirement; AC-3 is its acceptance restatement, and the skill's `attempt > 3` boundary is explicit). No code change recommended. **Action:** flag for the spec owner to reword AC-3 to "retried up to 2 times (3 attempts total)" so the two stop contradicting — a spec edit, not a code fix.

### NIT-2 — `attempts = 2` after the first failed try (dashboard semantics)
`EventRepository.php:157-165`, set from `next` (`RetryScheduler.php:78`). After one failed delivery the DB shows `attempts = 2`, i.e. the column means "current/next attempt number", not "number of attempts already made". A naive dashboard reading "attempts" as a past-tense count would over-report by one (shows "2" after one try). This is internally coherent (envelope and DB carry the same control number, ADR D3) and arguably reads as "now on attempt 2 of 3", but FR-9's wording is "attempts" (past tense). **Disposition:** acceptable for T2.3; the dashboard (T3.x) must be built to interpret the column as "attempt number", or a follow-up may switch to writing `attempts = job->attempt()` (tries completed). Worth a one-line note in the T3.x dashboard task so the label matches the semantics. No change in T2.3.

### NIT-3 — stranded-`received` row on `scheduleRetry` failure has no reaper
`RetryScheduler.php:78-79`. As analysed above, a `scheduleRetry` throw after a successful `markForRetry` leaves a row at `received` that is on no queue. This is the deliberate, documented DB-first trade and is no worse than T2.2's already-accepted stuck-`processing` debt — both await a future "reaper / re-queue stuck rows" path (related to T3.2 DLQ re-queue). Recorded as known debt, not a defect.

### NIT-4 — `delayFor(1)` is dead on the retry path
`RetryScheduler.php:88-94`. The first *retry* uses `delayFor(2)` (2–4s); `delayFor(1)` (1–2s) is never invoked by `retryOrFail`. The class/ADR docblocks describe "1–2s / 2–4s / 4–8s" which can read as if all three apply to retries — only the latter two do. Harmless (the method is a pure function of its argument and correctly handles attempt 1), but a one-line docblock clarification ("retries use delayFor(2)/delayFor(3); delayFor(1) is defined for completeness") would prevent confusion. Optional.

### NIT-5 — scope discipline confirmed clean
No DLQ (`webhooks:dlq`) and no SIGTERM handling were introduced (Q6). Exhaustion and the permanent branch remain interim `markFailed` (`RetryScheduler.php:72-75`, `worker.php:142-145`), exactly the T2.4 seam ADR 0013 D5 specifies. The `$job === null` idle tick (`worker.php:84-87`) is left untouched for T2.5. Later tasks fill by addition, not rewrite. No action.

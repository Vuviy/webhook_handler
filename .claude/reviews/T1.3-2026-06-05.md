## Findings
| # | Severity | File:line | Issue | Suggested fix |
|---|----------|-----------|-------|---------------|
| 1 | MINOR | `app/src/Verification/StripeVerifier.php:99-116` | Header parser keeps the **last** `t` seen (`$timestamp = $value` overwrites on each `t=` pair). A crafted header `t=<future>,v1=...,t=<old>` lets the attacker present two timestamps; the *last* wins. Stripe's own libraries also take a single `t`, and `t` is HMAC-covered so a mismatched `t` fails the signature — so this is not exploitable, but "last wins" is an arbitrary choice. Consider rejecting duplicate `t`, or documenting the "last wins" decision explicitly. | Treat a second `t` as `invalid('malformed Stripe-Signature')`, or add a one-line comment that duplicate `t` is intentionally last-wins and safe because `t` is signed. |
| 2 | MINOR | `app/src/Verification/StripeVerifier.php:144-149` | `hash_equals($computed, $candidate)` is called for **every** `v1` candidate. A hostile header can stuff thousands of `v1=` pairs (the body size cap is large), forcing N constant-time compares — a mild CPU-amplification / DoS vector on the synchronous HTTP path (NFR fast-2xx). HMAC is computed once (good), but the compare loop is unbounded. | Cap the number of accepted `v1` candidates (e.g. break after 16–32), or cap total header length before parsing. Low likelihood but cheap to bound. |
| 3 | NIT | `app/src/Verification/StripeVerifier.php:84,179` | psalm (errorLevel 2) flags `MissingOverrideAttribute` on `verify()`/`provider()`. Consistent with `GitHubVerifier` (no `#[Override]` anywhere in the codebase), so this is house style, not a regression — noted only for completeness. | Optional: add `#[\Override]` project-wide in a separate cleanup if psalm is later enforced. |
| 4 | NIT | `app/src/Verification/StripeVerifier.php:128` | `ctype_digit($timestamp)` rejects a `t` with a leading `+`/`-` or whitespace (correct), but also silently accepts an arbitrarily long all-digit `t`; the later `(int) $timestamp` (`:133`) saturates to `PHP_INT_MAX` on overflow. Harmless — an overflowed `t` is astronomically out of tolerance and `invalid`s — but worth a mental note. | None required; behaviour is safe. |

No BLOCKER or MAJOR findings.

### Confirmed correct (the load-bearing security points)
- **Raw-bytes signing:** `$timestamp . '.' . $rawBody` uses the untouched body, never re-encoded JSON (`:141`). ✅
- **Literal `t` string in payload:** the as-received timestamp string is signed, not a re-cast int — byte-exact with Stripe (`:137-141`). ✅
- **Timing-safe:** `hash_equals()` only; no `==`/`===` on any digest. ✅
- **HMAC computed once:** outside the candidate loop, so a stuffed header cannot force repeat crypto (`:141`). ✅
- **Replay window before HMAC:** justified in ADR 0007 / class doc; leaks nothing (attacker supplied `t`), sheds replays cheaply, and the HMAC still covers `t` so freshness alone is never trusted as authenticity (`:133`). ✅
- **`JsonException` never escapes as 5xx:** caught → `invalid()` (`:157-161`). ✅
- **`is_string` guard:** prevents `trim()` TypeError on numeric/array/null `id`/`type` → clean `invalid` instead of 5xx (`:169-170`). ✅
- **No NFR-1 leak:** every `invalid()` reason is a fixed human string; no `t`, hex, body or secret interpolated. ✅
- **Fail-closed on missing id/type:** valid signature but unreadable body → `invalid()`, not `valid()` with empty ids (which `VerificationResult::valid()` would reject anyway) (`:172`). ✅
- **`fromSecrets` 500-not-401 semantics:** null secret throws `VerificationException::missingSecret('stripe')` (`:78`), matching the contract and `GitHubVerifier`. ✅

## Verdict
**Approve with nits.** The Stripe verifier is correct, timing-safe, byte-exact on the signed payload, and fails closed on every malformed/replay/JSON path without ever reaching a 5xx. It conforms to the `ProviderVerifier` contract and stays strictly within T1.3 scope. The two MINOR items (duplicate-`t` "last wins" semantics #1, unbounded `v1` compare loop #2) are hardening suggestions, not correctness or security defects, and may be deferred or addressed in passing. NITs #3/#4 are informational.

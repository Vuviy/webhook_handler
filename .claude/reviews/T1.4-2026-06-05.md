## Acceptance criteria
- [x] **FR-3** `POST /webhooks/paypal` verified via PayPal `verify-webhook-signature` — ✅ PayPalVerifier
  posts to `/v1/notifications/verify-webhook-signature` after obtaining an OAuth2 token; reads back
  `verification_status`. (HTTP routing itself is T1.5, correctly out of scope.)
- [x] **FR-5** Invalid/missing signature → routed to 401, not enqueued — ✅ all bad/forged/malformed
  paths return `VerificationResult::invalid(...)`; `verify()` never throws on routine input.
- [x] **FR-11** Dedupe id available — ✅ extracts `id` + `event_type` from body, only after SUCCESS;
  `valid()` never called with empty ids (guarded).
- [x] **NFR-1** Raw bytes / no secret leak — ✅ raw body forwarded as `webhook_event`; no secret,
  token, Basic header or body in any exception/reason string. (No local HMAC, so `hash_equals`
  correctly absent — comparison is PayPal's.)
- [x] **NFR-2** Transient vs permanent distinction — ✅ transport/timeout/non-2xx/unreadable →
  `error()` (→502, provider retries); explicit `verification_status != SUCCESS` → `invalid()` (→401).
  This is the first real producer of the `error` outcome.
- [x] **Risk §8** Malformed body / missing header / bad JSON → never 5xx — ✅ empty body, missing
  transmission headers, non-JSON, non-object body all map to `invalid()`; `HttpException` and
  `JsonException` are caught on every remote/parse path. Verified by lint + branch testing.
- [x] **SSRF / cert-url** — ✅ `paypal-cert-url` is only forwarded to PayPal, never fetched; the
  HttpClient only ever calls the configured API base. TLS verification left at curl secure default.
- [x] **Scope** — ✅ no controller/registry/routing, no worker, no token caching, no real PayPal
  handler. Clean T1.4-only footprint.

## Notable strengths
- error-vs-invalid boundary is exhaustive and matches the contract docblock and ADR 0008 exactly.
- Parse-before-verify is justified and safe: body is only *forwarded*; id/type are extracted strictly
  after a SUCCESS answer (golden rule respected).
- `fromSecrets()` fails fast (→500 via `VerificationException::missingConfig`) for any of the three
  credentials, naming the env key but never its value.
- Mandatory injectable curl timeouts (connect 2s / total 5s) prevent FPM hangs; `curl_close` in
  `finally`; explicit `curl_exec === false` check (no `@` suppression).
- House pattern consistent with `GitHubVerifier`/`StripeVerifier` (lower-cased header constants,
  `final`, `readonly`/promotion, typed factory exceptions, strict_types).

## Verdict
**Approve with nits** — The PayPal verifier and HTTP seam are correct, secure, and faithful to the
spec, the webhook-security skill (verify-webhook-signature API, five transmission headers, no blind
cert-url fetch, no local crypto) and project conventions. The error/invalid split is the right model
for a remote verifier and is implemented exhaustively. All findings are MINOR/NIT and none require a
change before merge; consider the optional whitespace-token trim (#5) and the 3xx comment (#1) at your
discretion.

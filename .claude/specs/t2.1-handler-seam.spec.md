# Spec: T2.1 — Handler seam (HandlerRegistry + stub handlers)

- **Status:** Draft
- **Author:** backend-architect
- **Date:** 2026-06-06
- **Related ADR:** `.claude/decisions/0011-handler-seam-and-failure-signalling.md`
- **Parent spec:** `.claude/specs/webhook-handler.spec.md` (FR-6, NFR-2)

## 1. Problem
The worker (T2.2) must dispatch each dequeued webhook to provider-specific processing
without knowing the provider's details, and the retry/DLQ logic (T2.3/T2.4) must be able
to tell a **transient** failure (retry) from a **permanent** one (straight to DLQ). T2.1
builds the seam that makes both possible: a handler interface, a registry mapping
provider tag → handler, three stub handlers, and the two typed exceptions that express
the failure distinction. No processing behaviour is implemented (spec Non-goal §3).

## 2. Goals
- A secret-free `Handler` interface the worker can depend on (mirrors `ProviderVerifier`).
- A `HandlerRegistry` mapping `'github'|'stripe'|'paypal'` → `Handler`, `null` for unknown.
- Three stub handlers that compile, are idempotent-by-construction (no-op), and document
  their idempotency contract.
- Two typed exceptions that let T2.3/T2.4 branch transient-vs-permanent.
- A read-only `WebhookEvent` value object as the handler's input contract.

## 3. Non-goals
- The worker loop / `BLPOP` (T2.2), the DB read-by-id that builds `WebhookEvent` (T2.2).
- Retry, backoff, the retry zset (T2.3); DLQ push and `last_error` persistence (T2.4).
- Any status update, logging of payloads, or real per-event business logic.
- Construction-time config/secrets for handlers (none needed for stubs).

## 4. Functional requirements
- **FR-1** `App\Handler\Handler` interface: `handle(WebhookEvent $event): void` and
  `provider(): string`. Normal return = success.
- **FR-2** `App\Handler\WebhookEvent` (final readonly): `provider`, `eventId`,
  `eventType`, `payload` (raw bytes), `attempt` — all typed accessors.
- **FR-3** `App\Handler\HandlerRegistry::get(string $provider): ?Handler` via lazy
  `match`, returning `null` for an unknown tag (mirrors `VerifierRegistry`).
- **FR-4** Three stubs: `GitHubHandler`, `StripeHandler`, `PayPalHandler`, each
  `final`, each returning its provider tag, each a documented no-op.
- **FR-5** `App\Exception\TransientHandlerException` and
  `App\Exception\PermanentHandlerException`, typed-factory style like the existing
  `App\Exception\*` family.

## 5. Non-functional requirements
- **NFR-1 (conventions)** `declare(strict_types=1)`, `final`, full type hints, PSR-12,
  per `.claude/skills/php-conventions/SKILL.md`.
- **NFR-2 (idempotency)** Stubs are no-ops; docblocks state that a real handler must
  dedupe by provider event id under at-least-once delivery (FR-11 of parent spec).
- **NFR-3 (no secret leakage)** The interface and registry are secret-free; exception
  messages name only provider/event id, never payload bytes.
- **NFR-4 (forward-compatibility)** The seam must let T2.3 add retry/DLQ branching
  purely via `catch` clauses, without changing this interface or the stubs.

## 6. Design
Namespace `App\Handler\`. Files: `Handler.php` (interface), `WebhookEvent.php` (value
object), `HandlerRegistry.php` (lazy `match` registry), `GitHubHandler.php`,
`StripeHandler.php`, `PayPalHandler.php` (stubs). Plus `App\Exception\
TransientHandlerException` and `PermanentHandlerException`.

Failure contract (vocabulary defined here, policy enforced in T2.3/T2.4):
`TransientHandlerException` → retryable; `PermanentHandlerException` → DLQ immediately;
any other `Throwable` → treated as transient by the worker (fail-safe). See ADR-0011.

## 7. Acceptance criteria
- [ ] **AC-1** `php -l` passes on all new files; classes autoload under `App\Handler\`.
- [ ] **AC-2** `HandlerRegistry::get()` returns the right stub for each known tag and
      `null` for an unknown one (mirrors `VerifierRegistry` behaviour).
- [ ] **AC-3** `Handler::handle(WebhookEvent)` and the two typed exceptions exist with
      the signatures T2.2/T2.3 will depend on; stubs are no-ops.
- [ ] **AC-4** No file reads secrets, updates status, touches Redis or the DB.

## 8. Risks & edge cases
- `WebhookEvent` defined before its T2.2 producer — accepted (next task).
- Unknown provider in a job envelope → `get()` returns `null`; the worker decides the
  HTTP-less meaning (likely DLQ) in T2.2 — out of scope here.
- Over-engineering: a result object instead of exceptions would force boilerplate on
  every handler — rejected in ADR-0011.

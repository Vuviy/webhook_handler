# Навчальна нотатка: T3.2 — шлях повернення подій із Dead Letter Queue (CLI)

> Мова: українська. Аудиторія: junior → middle PHP.
> Підзадача: **T3.2 — DLQ re-queue / drain (CLI)**.
> ADR: [`.claude/decisions/0017-dlq-requeue-path.md`](../decisions/0017-dlq-requeue-path.md) ·
> Рев'ю: [`.claude/reviews/T3.2-2026-06-06.md`](../reviews/T3.2-2026-06-06.md)

---

## 1. Проблема простими словами

До T3.2 наша Dead Letter Queue (DLQ) була **дорогою в один бік**. Коли подія вичерпувала свої
3 спроби або падала «назавжди», вона потрапляла в `webhooks:dlq` (T2.4), і дашборд показував її
кількість (T3.1) — але **нічого не вміло витягти її звідти назад**. DLQ — це не «смітник», це
«поличка очікування ремонту»: подія застрягла, бо зламаний *downstream* (наш обробник, чужий API,
БД отримувача). Коли інженер причину **полагодив**, він має натиснути «програти заново» — інакше
платіж Stripe чи подія GitHub просто загублені, хоча провайдер свою частину контракту виконав.

T3.2 додає цю «кнопку відтворення» у вигляді **операторського CLI** `bin/requeue-dlq.php`. Команда
дренує (вичерпує) **всі** записи DLQ за один прогін і повертає кожну подію на живий шлях, **ніби це
свіжа доставка**.

Чому це не дрібниця: повернути подію — це **не** просто «штовхнути конверт назад у чергу». Подія
живе у **двох** сховищах одночасно, і обидва треба зрушити синхронно:

1. **Redis** — конверт `{event_id, provider, attempt}` лежить у списку `webhooks:dlq`.
2. **MySQL** — рядок `webhook_events` має `status='failed'`, `attempts=3`, заповнений `last_error`.

Якщо штовхнути лише конверт, worker його дістане, спробує «застовпити» через `markProcessing`
(а той має guard `AND status='received'`), не знайде жодного рядка для оновлення — і **мовчки
пропустить** подію. Тобто повернення = «зрушити Redis» **І** «перевести рядок БД назад у стан, який
guard worker-а зможе виграти знову» (`received`), **І** скинути бюджет спроб.

## 2. Потік виконання

Спершу — звичайний шлях, у який ми повертаємо подію (контекст):

```
provider POST → Nginx → контролер прийому → перевірка підпису (timing-safe)
  → INSERT webhook_events (status=received) → RPUSH webhooks:queue → 202 Accepted
worker BLPOP → markProcessing (guard status='received') → обробник
  → успіх: status=processed
  → збій: scheduleRetry, backoff 2^n, attempts++
  → 3 збої / permanent: deadLetter → status=failed + RPUSH webhooks:dlq
```

Тепер **новий шлях T3.2** — відновлення (recovery), протилежний напрямок:

```
оператор полагодив downstream
  → docker compose exec php php bin/requeue-dlq.php
      │  1. Queue::deadLetterSize()  — зчитати N (LLEN) ОДИН раз = межа циклу
      │  для кожного з N записів (DlqRequeue::drainAll):
      │    2. LPOP webhooks:dlq          (Queue::requeueOneFromDeadLetter → ?Job)
      │    3. UPDATE webhook_events
      │         SET status='received', attempts=0, last_error=NULL
      │         WHERE provider AND event_id AND status='failed'   (requeueFromDlq → bool)
      │    4. RPUSH webhooks:queue з attempt=1   (Queue::enqueue — свіжа доставка)
      │  5. друк рядка на запис + підсумок; exit(0)
  → worker BLPOP підхоплює конверт → markProcessing виграє (рядок знову 'received')
      → обробник → успіх / новий цикл retry
```

Порядок кроків 2→3→4 (**pop → reset БД → push**) — це серце задачі, до нього повернемось у §3.

## 3. Чому саме так

### 3.1. CLI, а не кнопка в дашборді (ADR Decision 1)

Дренування DLQ — це **привілейована, рідкісна, руйнівна** дія оператора, того ж класу, що й
запуск міграцій. Тому CLI `bin/requeue-dlq.php` — близький клон `bin/migrate.php`: завантажує
`bootstrap.php`, будує `Queue` + `EventRepository` через fail-fast фабрики, друкує по рядку на
одиницю в STDOUT і `exit(0)`/`exit(1)`. Він лежить у `bin/` **над** `public/`, тож **ніколи не
досяжний по HTTP**.

Чому це принципово краще за кнопку:

- **Нульова нова HTTP-поверхня.** Кнопка вимагала б HTML-сторінки (а front-контролер жорстко
  віддає `application/json`, ADR 0016), **нового POST-маршруту, що змінює стан**, **CSRF-захисту**
  (форма в браузері, що popає Redis і переписує рядки БД — класична мішень CSRF) і **автентифікації**
  (мутація без auth набагато гірша за читання). Це обсяг роботи на цілий milestone заради задачі
  розміру «S».
- **Межа авторизації = доступ до shell / `docker compose exec`.** Це *строго сильніша* гарантія,
  ніж неавтентифікований ендпоінт на локальному дашборді.

**Відхилено (Option C):** «робіть руками через phpMyAdmin + сирий Redis». Це не дизайн, а
*відсутність* T3.2: оператор мусив би знати запечатану назву ключа й схему конверта, щоразу
вгадувати правильний міжсховищний порядок і скидати бюджет спроб — один промах в `UPDATE` псує
аудит-лог. T3.2 існує саме щоб зробити це **однією підтримуваною коректною операцією**.

### 3.2. Два guard-и роблять шлях ідемпотентним (at-least-once)

Уся система живе за принципом **at-least-once delivery**: ми радше доставимо подію *двічі*, ніж
*жодного разу*. Платою за це є вимога **ідемпотентності** — повторне програвання не має шкодити.
T3.2 досягає її **двома guard-ами в SQL**, які складаються разом:

- `requeueFromDlq` — `... WHERE ... AND status='failed'`. Скидає лише рядок, що **справді** в DLQ.
  Повертає `true` тільки якщо оновив рівно один такий рядок; `false`, якщо рядка немає або він уже
  не `failed`. Тож повторний прогін або конверт, чий рядок уже перепрограли, — **безпечний no-op**,
  а не псування.
- `markProcessing` (worker) — `... WHERE ... AND status='received'`. Воркер «застовпить» подію лише
  якщо рядок у `received`. Стороння копія конверта на черзі не нашкодить: guard просто не дасть її
  обробити двічі.

Разом ці два guard-и поглинають будь-який зайвий дублікат — повна петля **ідемпотентна та
re-runnable** під at-least-once.

### 3.3. Проблема бюджету спроб (чому reset обов'язковий)

Конверт у DLQ несе `attempt=3` (остання спроба, що відпрацювала). Якби ми штовхнули його назад
**без змін**, worker дістав би його, обробник упав би, а `RetryScheduler::retryOrFail` порахував би
`next = 3 + 1 = 4 > MAX_ATTEMPTS` → **миттєво назад у DLQ на першому ж збої, з нуля реальних спроб**.
Повернення, що не скидає бюджет, — це no-op, переодягнений у відновлення.

Тому ми скидаємо бюджет **в обох сховищах разом**, щоб конверт і БД лишались когерентними:

- БД: `attempts = 0` (плюс `last_error = NULL` — щоб дашборд recent-failures не показував уже
  перепрограну подію як «поточний збій»).
- Конверт: `attempt = 1` (нова доставка — ми перевикористовуємо `Queue::enqueue($id, $provider, 1)`).

Рішення (ADR D-default): скидати до **повного свіжого бюджету**, а не «лишити лічильник» (миттєвий
re-DLQ) і не «дати ще одну спробу». Логіка: re-queue стається саме тому, що оператор *вірить, що
причину полагоджено* — подія заслуговує на чесний прогін у 3 спроби.

### 3.4. Міжсховищний порядок pop → reset → push (ADR Decision 3)

Це найважливіше місце задачі. Ми робимо **три записи в двох сховищах без жодної спільної
транзакції** (Redis LPOP, MySQL UPDATE, Redis RPUSH). Якщо CLI впаде посеред запису — який
частковий стан ми отримаємо? Порядок обираємо так, щоб **єдиний можливий залишок краху був
видимим і відновлюваним**, а небезпечний — **неможливим**.

Ключова асиметрія: **рядок БД — джерело істини**, а worker обробляє подію лише коли рядок
`received`. Звідси:

- **Небезпечний** частковий стан: «конверт уже на `webhooks:queue`, але рядок ще `failed`». Worker
  дістає його, `markProcessing` оновлює 0 рядків, подія **мовчки пропускається** — і вона вже
  зникла з DLQ. Подія випарувалась з усіх дієвих поверхонь. Цього **ніколи** не має бути.
- **Відновлюваний** частковий стан: «рядок скинуто в `received`, але свіжий конверт ще не на черзі».
  Подія видима (дашборд рахує її як `received`), а повторний запуск CLI безпечний — він знайде
  рядок уже `received` і просто (пере)штовхне конверт.

Тому:

- **LPOP перший** — щоб запис *спожити* одразу: повторний прогін не popне той самий конверт двічі,
  а сам конверт є *входом* для двох інших записів (без нього не знаємо, який рядок скидати). Залишок
  краху «LPOP пройшов, потім впали» = «конверт ніде, рядок лишився `failed`» — той самий стерпний
  клас, що й «failed-рядок без DLQ-конверта» з T2.4: аудит чесно каже `failed`, оператор бачить.
- **reset БД перед RPUSH** — те саме правило, що в `retryOrFail`/`deadLetter` («DB write first»).
  Якщо push упаде після reset — рядок у відновлюваному `received`, а не orphan «конверт-на-черзі-над-
  failed-рядком».
- **по одному запису (LPOP), а не LRANGE** — крах лишає *решту* списку цілою; повторний запуск
  продовжує дренування з того місця.

**Відхилені альтернативи з ADR:**

- **Option H — `LRANGE 0 -1` + обробити все + `DEL webhooks:dlq`.** Пара read-then-delete = вікно
  гонки: якщо CLI впаде посеред пакета або хтось ще зачепить список — записи масово втрачаються чи
  обробляються двічі. А `DEL` ще й викидає конверти, що прийшли *після* зрізу LRANGE (тиха втрата).
  Відхилено на користь resumable per-entry LPOP.
- **Option I — push першим, потім reset, потім видалити з DLQ.** Це **рівно** небезпечний стан:
  живий конверт над `failed`-рядком, worker мовчки пропускає. Точна інверсія того, що відхилив T2.4.
- **Option K — увесь код у CLI-скрипті (сирий Redis + SQL у `bin/`).** Зламало б single-ownership:
  CLI називав би `webhooks:dlq`/`webhooks:queue` і руками парсив конверти, а SQL жив би поза
  `EventRepository`. Відхилено: entry point лишається тонким, власники — єдиними.

### 3.5. Окремий клас `DlqRequeue`, а не метод на `RetryScheduler` (ADR Decision 4)

Це дзеркальне рішення. `RetryScheduler` володіє політикою **напрямку відмови** (received → retry →
DLQ: backoff, вичерпання, dead-letter). T3.2 — це політика **напрямку відновлення** (DLQ → received).
Це **протилежні потоки**. Пришити дренування до `RetryScheduler` означало б розтягнути його ім'я до
розриву і змішати два зустрічні напрямки в одному класі. Тому — крихітний окремий `final class
DlqRequeue`, який тримає лише **порядок** (pop → reset → push) і tally, делегуючи механізм: Redis
лишається в `Queue`, SQL — в `EventRepository`. Це той самий інстинкт, що дав T3.1 окремий
`DashboardController`, а не купу методів на наявному класі. **(Відхилено Option L.)**

## 4. Слабкі місця та технічний борг

- **Немає міжсховищної транзакції** через триплет LPOP / UPDATE / RPUSH. Пом'якшено порядком (§3.4)
  і guard-ами, але це той самий компроміс, що й усі інші write-шляхи проєкту. Чесно задокументовано
  на оркестраторі.
- **Справжній poison message повертається в DLQ.** Drain-all дає йому свіжі 3 спроби; якщо й далі
  падає — знову в DLQ (розмір на дашборді відскакує назад). Не гірше, ніж було, але автоматичного
  карантину отруйних повідомлень немає (поза обсягом «S»). При зростанні частки збоїв drain-all може
  стати **thundering herd** — масово повернути сотні подій, що знову впадуть синхронно. Майбутній
  `--limit` / by-id режим це пом'якшив би.
- **Тільки drain-all** реалізовано. Режим `requeue-dlq.php <event_id>` і прапор `--limit` —
  задокументовані наступні дрібниці, не побудовані тут.
- **`skipped`-конверт (без `failed`-рядка) викидається з DLQ**, а не зберігається для розслідування.
  Навмисно (нема що перепрогравати), але dangling-запис споживається. Прийнятно: він і так уже
  неузгодженість, і CLI показує його в підсумку.
- **`last_error` стирається** при поверненні — причина початкового збою більше не на рядку після
  успішного replay. Якщо колись захочемо її лишити — це зняти `last_error = NULL` (один рядок).
- **Немає блокування / multi-operator safety.** Коректно для припущення «один воркер, один оператор»
  (атомарність LPOP + два guard-и). Multi-operator майбутнє додало б лок — локальна зміна.
- **Ротація секретів.** Дотично: якщо причиною dead-letter була стара signature secret, повернення
  само по собі не вирішить її — оператор має спершу полагодити downstream/секрет, *потім* дренувати.

### Growth point (зауваження для зростання до middle)

Рев'ю знайшло **MAJOR #1**: у `bin/requeue-dlq.php` catch ловив лише `QueueException | DatabaseException`.
Але сирі виклики phpredis (`lPop`/`lLen`) кидають **`RedisException`**, якщо Redis упаде *посеред*
дренування — і лише `Queue::fromConfig` обгортає його в `QueueException`. Без `RedisException` у catch
середина-дренувальний обрив Redis вилетів би **неперехопленим fatal**, а не чистим `exit(1)`. Виправлено
додаванням `RedisException` у catch. Це типова пастка початківця: **думати про винятки своїх класів і
забувати про винятки бібліотеки нижче**. Завжди питай: «який *найнижчий* шар може кинути тут, і як саме
цей тип проростає крізь мої обгортки?»

Свідомо **залишено** `catch (QueueException)` усередині `DlqRequeue::drainAll` для гілки `corrupt`:
це правильна гранулярність — `RedisException` *не* є `QueueException`, тож інфра-збій усе одно летить
нагору до backstop CLI, а локальний catch ловить лише отруйний конверт (помилку декоду) і дренує далі.

## 5. Патерни, які варто запам'ятати

- **At-least-once delivery** — краще доставити двічі, ніж нуль разів. Зустрічається в Kafka, SQS,
  RabbitMQ, у webhook-системах усіх великих провайдерів (Stripe/GitHub/PayPal самі ретраять).
- **Idempotency key / idempotent consumer** — наші guard-и `status='failed'` та `status='received'`
  роблять операцію безпечною до повтору. Той самий патерн — `Idempotency-Key` в Stripe API,
  upsert у БД, dedupe за event id.
- **Dead Letter Queue** — терминальна поличка для того, що впало назавжди. Є в SQS, RabbitMQ,
  Azure Service Bus. T3.2 додає до неї **redrive policy** (повернення на живий шлях) — пряма аналогія
  з кнопкою «Start DLQ redrive» в AWS SQS.
- **Exponential backoff** — `2^n` між спробами (живе в `RetryScheduler`); ми його *скидаємо* при
  поверненні. Скрізь, де є ретраї: HTTP-клієнти, gRPC, мережеві драйвери.
- **Saga / compensating ordering без розподіленої транзакції** — pop → reset → push з обраним
  порядком замість 2PC. Класика мікросервісів: коли немає спільної транзакції, обирай порядок так,
  щоб частковий стан був *відновлюваним*.
- **Outbox / source-of-truth in DB** — важкий payload у MySQL, у черзі лише легке посилання за
  event id; worker перечитує джерело істини. Патерн «черга несе вказівник, а не дані».
- **Mechanism vs policy split** — `Queue` = механізм Redis, `DlqRequeue` = політика відновлення,
  `EventRepository` = власник SQL. Кожен клас single-purpose.
- **Operator CLI над `public/`** — привілейовані дії (міграції, redrive) як консольні команди поза
  HTTP-поверхнею; авторизація = доступ до shell. Аналог `php artisan`, `rails`, `manage.py`.

```
php -l app/src/Queue/Queue.php
php -l app/src/Queue/DlqRequeue.php
php -l app/src/Queue/DlqRequeueReport.php
php -l app/src/Repository/EventRepository.php
php -l app/bin/requeue-dlq.php
```

Для всіх п'яти: `No syntax errors detected in ...`.

**Чому:** lint — найдешевший фільтр. Немає сенсу запускати end-to-end, якщо файл навіть не парситься.

### Крок 4 — перший прогін на наявних тестових даних

Хтось лишив 3 записи в DLQ. Спершу підтвердив це:

```
redis-cli LLEN webhooks:dlq      →  3
```

Потім прогін CLI:

```
php bin/requeue-dlq.php
```

Вивід:

```
re-queued: github t32-requeue-1
skipped:   github t32-no-row (no failed row)
skipped:   <corrupt envelope> (could not decode)
Done — 1 re-queued, 1 skipped, 1 corrupt (of 3).
```

Цей один прогін відразу показав **усі три гілки** `drainAll`: `requeued` (рядок існує й `failed`),
`skipped` (конверт є, рядка-`failed` немає), `corrupt` (конверт не декодувався). Після прогону:
`webhooks:queue` містив `{"event_id":"t32-requeue-1","provider":"github","attempt":1}`,
`LLEN webhooks:dlq` = 0, а рядок `t32-requeue-1` у БД став `received` / `0` / `NULL`.

**Чому:** перевіряю не лише «щасливий шлях», а й як CLT поводиться з битими/осиротілими записами —
бо саме там ховаються тихі втрати.

### Крок 5 — перевірка схеми таблиці

```
SHOW CREATE TABLE webhook_events\G
```

Підтвердило колонки `provider`, `event_id`, `status` (enum), `attempts`, `last_error` і **унікальний
ключ `uq_provider_event`** на `(provider, event_id)`.

**Чому:** мій `WHERE provider AND event_id AND status='failed'` коректний лише якщо `(provider,
event_id)` справді унікальні — інакше `rowCount() === 1` був би хибним припущенням.

### Крок 6 — власний чистий end-to-end тест

**Очистка** (щоб стартувати з відомого стану):

```
DELETE FROM webhook_events WHERE event_id LIKE 't32e2e%';
redis-cli DEL webhooks:queue webhooks:dlq
```

**Seed** одного контрольованого dead-lettered запису:

```
INSERT INTO webhook_events (provider,event_id,event_type,payload,signature_valid,status,attempts,last_error)
VALUES ('stripe','t32e2e-A','payment_intent.succeeded','{}',1,'failed',3,'handler 500');
redis-cli RPUSH webhooks:dlq '{"event_id":"t32e2e-A","provider":"stripe","attempt":3}'
```

**BEFORE:** `LLEN webhooks:dlq` = 1, `LLEN webhooks:queue` = 0, рядок `failed` / `3` / `handler 500`.

**Прогін #1:**

```
php bin/requeue-dlq.php
```

Вивід:

```
re-queued: stripe t32e2e-A
Done — 1 re-queued, 0 skipped (of 1).
```

`exit=0`. **AFTER:** `webhooks:dlq` = 0, `webhooks:queue` містить
`{"event_id":"t32e2e-A","provider":"stripe","attempt":1}` (зверни увагу: **attempt=1**, бюджет
скинуто), рядок став `received` / `0` / `NULL`.

**Прогін #2 (ідемпотентність):**

```
php bin/requeue-dlq.php
```

Вивід:

```
Dead-letter queue is empty — nothing to re-queue.
```

`exit=0`.

**Чому:** це доводить дві ключові властивості одразу — (а) повний цикл pop→reset→push із коректним
скиданням бюджету (`attempt=1`, `attempts=0`), і (б) **ідемпотентність**: повторний прогін на
порожньому DLQ — чистий no-op з `exit(0)`, а не помилка.

### Крок 7 — повторний контрольований прогін після виправлень рев'ю

Seed `t32v-ok` (`failed`/`3`/`boom`) + битий конверт `not-json{` як corrupt:

```
INSERT INTO webhook_events (...) VALUES ('github','t32v-ok','push','{}',1,'failed',3,'boom');
redis-cli RPUSH webhooks:dlq '{"event_id":"t32v-ok","provider":"github","attempt":3}'
redis-cli RPUSH webhooks:dlq 'not-json{'
php bin/requeue-dlq.php
```

Вивід:

```
re-queued: github t32v-ok
skipped:   <corrupt envelope> (could not decode)
Done — 1 re-queued, 0 skipped, 1 corrupt (of 2).
```

Рядок `t32v-ok` став `received` / `0` / `NULL`.

**Чому:** після правок рев'ю треба перепереконатися, що поведінка не змінилась і битий конверт усе
ще лише пропускається (а не валить увесь прогін).

### Крок 8 — перевірка гілки `RedisException` (виправлення MAJOR #1)

```
docker compose stop redis
php bin/requeue-dlq.php
```

Вивід:

```
Re-queue error: Failed to connect to Redis at "redis:6379."
```

`exit=1` — **чистий вихід, не fatal**. Потім:

```
docker compose start redis
redis-cli PING      →  PONG
```

**Чому:** це **головний доказ виправлення рев'ю**. Я навмисно «вбив» Redis і підтвердив, що CLI
ловить `RedisException` і виходить кодом 1 з типізованим повідомленням, а не неперехопленим fatal.
Саме цю гілку MAJOR #1 додав у catch.

### Крок 9 — прибирання тестових даних

```
DELETE FROM webhook_events WHERE event_id LIKE 't32e2e%' OR event_id LIKE 't32-%';
DELETE FROM webhook_events WHERE event_id LIKE 't32v%';
redis-cli DEL webhooks:queue webhooks:dlq
```

Фінально: `LLEN webhooks:dlq` = 0, `LLEN webhooks:queue` = 0.

**Чому:** тести не мають лишати сміття в БД чи Redis — наступний прогін (чи дашборд) має бачити
чистий стан, інакше «3 записи, що хтось лишив» із кроку 4 повторяться для наступного інженера.

## 7. Запити до бази даних

Усі SQL виконувалися в контейнері `db_webhook` через
`mysql -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE" -e "..."`. Ось **кожен** запит:

```sql
-- Крок 5: перевірка схеми (колонки, enum status, унікальний ключ uq_provider_event)
SHOW CREATE TABLE webhook_events\G

-- Крок 4: огляд наявних тестових рядків T3.2
SELECT provider,event_id,status,attempts,last_error
FROM webhook_events WHERE event_id LIKE 't32%';

-- Крок 6: очистка перед чистим end-to-end
DELETE FROM webhook_events WHERE event_id LIKE 't32e2e%';

-- Крок 6: seed одного dead-lettered рядка
INSERT INTO webhook_events
  (provider,event_id,event_type,payload,signature_valid,status,attempts,last_error)
VALUES ('stripe','t32e2e-A','payment_intent.succeeded','{}',1,'failed',3,'handler 500');

-- Крок 6: перевірка рядка до/після прогону
SELECT event_id,status,attempts,last_error
FROM webhook_events WHERE event_id='t32e2e-A';

-- Крок 9: прибирання end-to-end та першого набору
DELETE FROM webhook_events WHERE event_id LIKE 't32e2e%' OR event_id LIKE 't32-%';

-- Крок 9: прибирання набору перевірки рев'ю
DELETE FROM webhook_events WHERE event_id LIKE 't32v%';

-- Крок 7: seed рядка для перевірки після правок рев'ю
INSERT INTO webhook_events
  (provider,event_id,event_type,payload,signature_valid,status,attempts,last_error)
VALUES ('github','t32v-ok','push','{}',1,'failed',3,'boom');

-- Крок 7: перевірка цього рядка
SELECT event_id,status,attempts,last_error
FROM webhook_events WHERE event_id='t32v-ok';
```

Запит, який CLI виконує всередині (через `EventRepository::requeueFromDlq`, не вручну) —
для повноти картини:

```sql
UPDATE webhook_events
SET status = 'received', attempts = 0, last_error = NULL
WHERE provider = :provider AND event_id = :event_id AND status = 'failed';
```

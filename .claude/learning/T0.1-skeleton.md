# Навчальна нотатка: T0.1 — каркас застосунку + фронт-контролер

> Мова: українська. Аудиторія: junior → middle PHP.
> Це поглиблення загального розбору з `НАВЧАННЯ.md` саме по підзадачі T0.1.

## 1. Проблема простими словами

Перш ніж писати верифікацію підписів, чергу й воркер, системі потрібен **скелет**:
одна точка входу, через яку проходить кожен HTTP-запит, і доказ того, що
автозавантаження класів реально працює. T0.1 не додає бізнес-логіки — вона
закладає *форму* проєкту, на якій усе подальше триматиметься.

Що конкретно зроблено:

- `app/public/index.php` — фронт-контролер (єдина точка входу): вмикає
  `strict_types`, підключає `vendor/autoload.php`, створює `App\Health`, віддає
  `200` з `Content-Type: application/json` і тілом `{"status":"ok","service":"webhook-handler"}`.
- `app/src/Health.php` — `final class App\Health` з методом `status(): array`.
  Його єдина мета зараз — довести, що PSR-4 (`App\` → `src/`) працює: контролер
  створює об'єкт **без жодного ручного `require`**.
- `docker/nginx/conf.d/default.conf` — web root змінено з `/var/www/html` на
  `/var/www/html/public`. Тепер назовні видно лише `public/`.
- Видалено старий `app/index.php`, щоб не було двох точок входу.
- `composer.json` уже містив PSR-4 `App\` → `src/`, його не чіпали.

Чому це важливо саме для системи вебхуків: провайдери (GitHub, Stripe, PayPal)
шлють POST із сирим тілом і підписом. Цей сирий потік мусить заходити через
**одне** контрольоване місце, де згодом стоятимуть verify → persist → enqueue →
`202`. Фронт-контролер — це те «горло», через яке все проходить. А винесення
коду й секретів вище web root — це базова вимога безпеки ще *до* того, як з'явиться
бодай один секрет у `.env`.

## 2. Потік виконання (що відбувається на одному запиті)

Повний цільовий конвеєр системи описаний у `CLAUDE.md`
(`provider POST → Nginx → verify → DB → Redis → 202 → worker → handler →
success/retry/backoff → DLQ`). На етапі T0.1 реально працює лише **початок** цього
шляху — і це нормально, бо ми будуємо фундамент:

1. **HTTP-запит** `GET http://localhost/` приходить у контейнер `nginx`
   (порт `80:80` у `docker-compose.yml`).
2. **Nginx** має `root /var/www/html/public`. Для `/` спрацьовує
   `try_files $uri $uri/ /index.php?$query_string`: фізичного файлу нема →
   fallback на `/index.php`.
3. Локейшн `location ~ \.php$` віддає `.php` у **PHP-FPM** через
   `fastcgi_pass php:9000`. Тут Nginx і PHP — це **окремі контейнери**, що
   спілкуються по FastCGI, а не один процес.
4. **PHP-FPM** виконує `public/index.php`: `require '../vendor/autoload.php'`
   реєструє автозавантажувач Composer.
5. `new Health()` тригерить **PSR-4**: автозавантажувач за іменем `App\Health`
   обчислює шлях `src/Health.php` і підключає його сам.
6. Контролер ставить `http_response_code(200)`, заголовок
   `Content-Type: application/json; charset=utf-8` і друкує
   `json_encode($health->status(), JSON_THROW_ON_ERROR)`.
7. Відповідь повертається тим самим шляхом FPM → Nginx → клієнт.

Як це перевірено (важливо для розуміння, що web root реально замкнувся):

- `GET /` → `200`, `application/json`, тіло `{"status":"ok","service":"webhook-handler"}`.
- `GET /src/Health.php` → `404` — файл лежить **вище** web root, його не існує
  всередині `public/`.
- `GET /.env`, `GET /composer.json` → `200`, **але тіло = той самий health-JSON**.
  Це не «секрет віддався». Це `try_files` не знайшов такого файлу в `public/` і
  впав на fallback `/index.php`. Реальні `.env`/`composer.json` лишилися
  недоступними — їх просто не існує в межах web root.

Те, чого ще НЕ відбувається (свідомо): немає роутингу за провайдером
(`/webhooks/github` тощо) — це T1.6; немає читання конфігу — T0.2; немає БД —
T0.3; немає черги Redis і воркера — T0.4. Воркер у `docker-compose.yml` зараз
крешиться в циклі (`command: ["php", "worker.php"]`, а файлу ще нема) — і це
очікувано на стадії каркаса.

## 3. Чому саме так

Ключове рішення T0.1 — **де тримати точку входу** — задокументоване в
`.claude/decisions/0002-web-root-and-front-controller.md`. Розглядали три варіанти:

**A) Лишити `index.php` в корені `app/`, web root = `/var/www/html`.**
Плюс: нуль роботи, поточний URL уже працює. Мінус фатальний: web root —
це **вся** тека застосунку. Nginx спеціально обробляє лише `*.php`, а все інше
(`.env`, `composer.json`, `composer.lock`, `src/`, `vendor/`, майбутні
`migrations/`) віддається як статика через `try_files`. Тобто `GET /.env`
реально віддав би секрети, а `vendor/` містить здатний до виконання PHP, який не
має бути досяжним напряму. Для системи, що оперує секретами провайдерів, це
прямий витік.

**B) Обрано: винести в `app/public/`, web root = `/var/www/html/public`.**
Назовні за **побудовою** видно лише `public/`. `.env`, `src/`, `vendor/`,
`composer.*`, `migrations/` фізично лежать вище web root, і їх неможливо дістати
по HTTP — не тому, що ми «заборонили», а тому, що їх там просто **нема**. Це
стандартний layout PHP-проєктів. Ціна: дворядкова правка Nginx і пересоздання
контейнера; автолоад тепер за відносним `__DIR__ . '/../vendor/autoload.php'`.

**C) Лишити в корені, але дописати в Nginx deny-правила** (`location ~ /\.`,
блок `composer.*`, `vendor/`, `src/`). Плюс: не рухаємо файли. Мінус: це
**deny-list**, тобто «перелік заборон». Кожен новий чутливий артефакт вимагає
нового правила; одне забуте правило — і витік. Це крихка модель.

Чому B принципово кращий за C — це різниця між **allow-list** і **deny-list**, і
це фундаментальний принцип безпеки «secure by default»:

- **Deny-list (C)** перелічує, що *заборонено*. Усе, що ти не згадав, —
  **дозволено**. Безпека дорівнює повноті твого списку, а список завжди відстає
  від реальності: додав `migrations/` — згадай дописати правило, інакше витік.
  Помилка тут «тиха»: ти дізнаєшся про неї, коли вже хтось викачав файл.
- **Allow-list (B)** перелічує, що *дозволено* (тільки `public/`). Усе інше
  заборонено за замовчуванням. Щоб відкрити новий файл назовні, треба **свідомо**
  покласти його в `public/`. Помилка тут «гучна» і безпечна: забув покласти —
  отримаєш `404`, а не витік.

Загальне правило, яке варто винести: *там, де ціна помилки — компрометація,
обирай модель, у якій замовчування безпечне, а небезпечну дію треба робити
явно.* Те саме стосується firewall-правил, прав доступу, CORS, SQL-грантів.

## 4. Слабкі місця та технічний борг

Це **каркас**, тому слабкість — здебільшого в тому, чого ще нема. Чесно:

- **Health не перевіряє здоров'я.** `App\Health::status()` завжди повертає `ok`,
  навіть якщо MySQL чи Redis лежать. Зараз це чесно (його мета — лише довести
  PSR-4), але назву легко переплутати з реальним health-check. Коли з'являться
  залежності, або клас перейменують (наприклад, `Bootstrap`/`Ping`), або
  навчать реально пінгувати БД і Redis.
- **Немає роутингу й обмеження методів.** `index.php` віддає `200` на будь-який
  метод і будь-який шлях. Конвенції (`php-conventions/SKILL.md`) вимагають
  `405` на неправильний метод, `400`/`401` на поганий payload/підпис — цього ще
  нема, бо це T1.6 та етап верифікації.
- **Воркер крешиться в циклі.** `worker.php` ще не існує — контейнер
  рестартиться нескінченно. Шум у логах, який легко сплутати з реальною
  проблемою.
- **`docker-compose.yml` тримає секрет у `environment` як root.** `DB_USERNAME:
  root` і пароль через `${MYSQL_ROOT_PASSWORD}` — для локалки прийнятно, але це
  не зразок для проду (окремий користувач БД з мінімальними правами). Узгодження
  імен змінних `.env` ↔ compose свідомо винесене в T0.2.
- **`json_encode` з `JSON_THROW_ON_ERROR`.** Це правильно (інакше `json_encode`
  «тихо» повернув би `false`). Але кидок виключення зараз нічим не ловиться:
  PHP-FPM віддасть `500` з типовим тілом. Для каркаса ок; з появою справжніх
  ендпойнтів знадобиться єдина точка обробки помилок у фронт-контролері.

Що з цього «вибухне» зі зростанням: жодне з вищеназваного не масштабне саме по
собі — це борг етапу. Реальні навантажувальні ризики (poison messages,
thundering herd на retry, ротація секретів) з'являться разом із чергою та
воркером (T0.4) і будуть темою окремих нотаток.

## 5. Патерни, які варто запам'ятати

- **Front Controller (фронт-контролер).** Єдина точка входу, через яку проходять
  усі запити; зручне місце для спільної логіки (роутинг, автолоад, обробка
  помилок, у нас згодом — verify/persist/enqueue). Де ще: Symfony і Laravel
  обидва мають саме `public/index.php` як фронт-контролер; WordPress —
  `index.php`. Ми робимо те саме руками, без фреймворку.
- **Web root як allow-list / secure by default.** Окрема `public/` тека —
  індустріальний стандарт PHP-layout саме тому, що дозволене визначається
  включенням, а не виключенням. Той самий принцип — у firewall (default deny),
  у правах файлів, у мінімальних грантах БД.
- **PSR-4 autoloading.** Угода «простір імен ↔ шлях у файловій системі»
  (`App\Foo\Bar` → `src/Foo/Bar.php`). Composer генерує мапу, і `new App\Health()`
  сам підключає файл — жодних ручних `require` на кожен клас. Це стандарт PHP-FIG,
  на ньому стоять усі сучасні PHP-проєкти. Навіщо: розв'язує імена від шляхів,
  прибирає десятки `require`, робить структуру передбачуваною.
- **Strict types + типізовані сигнатури.** `declare(strict_types=1)` і
  `status(): array` (з докблоком `array{status: string, service: string}`) —
  PHP не «підмінятиме» типи нишком, помилки ловляться раніше. Конвенція проєкту
  на кожен файл.

Зв'язка, яку варто тримати в голові цілісно: **Nginx (HTTP) → PHP-FPM (FastCGI)
→ Composer autoload → клас → відповідь.** Nginx не виконує PHP — він лише
вирішує, який файл і кому віддати, і проксує `.php` у FPM. FPM виконує PHP. Між
ними — FastCGI-протокол, а не виклик функції. Розуміння цього кордону рятує при
дебагу «чому віддається не той файл» (відповідь майже завжди — `try_files` і
web root).

## 6. Що далі

Це лише фундамент. Попереду: конфіг і `.env` (T0.2), БД та event log (T0.3),
черга Redis і воркер (T0.4), роутинг за провайдером і коректні HTTP-статуси
(T1.6), далі — верифікація підписів, retry/backoff і DLQ. Кожен крок
вбудовуватиметься саме в цей `public/index.php` — тому варто, щоб каркас із
самого початку був чистим і безпечним за замовчуванням.

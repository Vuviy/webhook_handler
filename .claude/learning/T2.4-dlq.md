# Навчальна нотатка: T2.4 — DLQ при вичерпанні спроб + збережений `last_error`

> Мова: українська. Аудиторія: junior → middle PHP.
> Пов'язані документи: ADR `.claude/decisions/0014-dlq-on-exhaustion.md`
> (та попередній `.claude/decisions/0013-*.md`), рев'ю `.claude/reviews/T2.4-2026-06-06.md`.

## 1. Проблема простими словами

Уяви собі обробку вебхука як конвеєр. Більшість подій проходить успішно. Частина падає
тимчасово (downstream таймаутить) — їх ми вже вміємо повторювати з backoff (це зробила
T2.3). Але є два випадки, коли повторювати **немає сенсу або вже нічого не лишилося**:

1. **Перманентна помилка** — payload зламаний так, що обробник ніколи не впорається
   (`PermanentHandlerException`). Повторювати — марно палити ресурси.
2. **Вичерпання спроб** — подія тимчасово падала, ми зробили всі 3 спроби, четвертої
   не буде.

До T2.4 у цих двох місцях код робив пів-роботи: позначав рядок у БД як термінально
`failed` і **вже** зберігав `last_error`, але **не клав** подію в чергу мертвих листів
(`webhooks:dlq` у Redis). Тобто подія «вмирала тихо»: оператор бачив `status='failed'`
у БД, але не мав окремого, призначеного для людини списку «ось що остаточно зламалося,
розберись». ADR 0013 (Decision 5) свідомо залишив ці два шви відкритими як борг.

**T2.4 закриває обидва шви — «доповненням, а не переписуванням».** Єдина *нова* робота —
RPUSH у `webhooks:dlq`. `last_error` уже писався раніше (через `markFailed`), його ми не
чіпали. Це закриває FR-8 і AC-4.

Чому це важливо саме для системи вебхуків: провайдери (GitHub/Stripe/PayPal) шлють подію
*at-least-once* — за умови, що ми відповіли `2xx`. Як тільки контролер прийому віддав
`202`, провайдер вважає свою справу зробленою і **більше не повторить**. Отже, з цього
моменту відповідальність за подію — повністю наша. Якщо подія остаточно падає, єдине, що
рятує бізнес від мовчазної втрати — це **аудит у БД** + **видимий DLQ**. DLQ — це не
«сміттєвий бак», це **черга на ручний розбір** (observability, NFR-4).

## 2. Потік виконання

Повний шлях вебхука після цієї зміни:

```
GitHub / Stripe / PayPal
   │  POST /webhooks/{provider}
   ▼
 Nginx ──► PHP-FPM (контролер прийому)
   │  1. читає RAW body
   │  2. timing-safe перевірка підпису (hash_equals)
   │  3. INSERT event (status=received) у MySQL
   │  4. RPUSH job у webhooks:queue
   │  5. повертає 202 Accepted   ← тут провайдер «відпускає» подію
   ▼
 Redis (webhooks:queue) ──► Worker (довгоживучий)
   │  promoteDue() — підтягує дозрілі retry із webhooks:retry
   │  consume() — BLPOP job
   │  markProcessing (UPDATE ... status='processing' WHERE id=:id AND status='received')
   │  dispatch у обробник провайдера
   │
   ├─ успіх ─────────────► markProcessed (status='processed')
   │
   ├─ TransientHandlerException / будь-який Throwable
   │       └─► RetryScheduler::retryOrFail
   │             ├─ є ще спроби (next ≤ 3): markForRetry (status='received', attempts++) 
   │             │      + scheduleRetry (ZADD у webhooks:retry, score = час+backoff)
   │             └─ ВИЧЕРПАНО (next > 3): ───┐
   │                                          │
   ├─ PermanentHandlerException ──────────────┤   ← T2.4 додає сюди виклик
   │                                          │
   └─ handler === null (захисна гілка) ───────┤   ← після рев'ю теж сюди
                                              ▼
                          RetryScheduler::deadLetter
                            1. markFailed  (status='failed', last_error=...)  ← СПОЧАТКУ БД
                            2. queue->deadLetter (RPUSH у webhooks:dlq)       ← ПОТІМ Redis
                                              ▼
                  MySQL (джерело правди) + webhooks:dlq (на розбір людиною / T3.2)
```

Ключове: **три** термінальні точки (перманент, вичерпання, відсутній обробник) тепер
ведуть в **одну** `deadLetter()`. Це і є «консолідація шва».

## 3. Чому саме так

Рішення задокументовані в ADR 0014. Головні чотири:

**(1) Розділення MECHANISM / POLICY.**
`Queue::deadLetter()` володіє *механізмом* — ім'я ключа `webhooks:dlq` і RPUSH крихітного
конверта `{event_id, provider, attempt}`. `RetryScheduler::deadLetter()` володіє *політикою*
— вирішує, що подія термінальна, і об'єднує два (після рев'ю — три) шви, щоб вони лишалися
**ідентичними**. Це дзеркало того, як T2.3 винесла backoff-математику в `RetryScheduler`, а
ZADD лишила в `Queue`. Принцип: ім'я ключа і схема конверта живуть в одному місці, щоб
жоден виклик не хардкодив `"webhooks:dlq"` і не винаходив конверт заново.

**(2) Порядок запису: спочатку БД, потім Redis.**
Це найважливіше рішення нотатки, тому розберемо повільно. Два записи (`markFailed` у MySQL
і RPUSH у Redis) **не в одній транзакції** — між ними процес може впасти. Отже існують дві
можливі «напівстани» після краху:

- **Рядок `failed` БЕЗ запису в DLQ** (наш порядок). Це **відновлюваний** стан: подію
  видно на дашборді за `status`, а майбутній drain (T3.2) може звіритися за `status='failed'`
  і добити запис у DLQ.
- **Запис у DLQ, але рядок завис у `processing`** (зворотний порядок). Це **катастрофа**:
  `markProcessing` захищений умовою `AND status='received'`, тому такий рядок **ніколи** не
  можна перезахопити — це невидимий орфан, він не `received`, не `failed`, не `processed`.

Тому БД пишемо першою: **аудит-рядок — джерело правди (NFR-4)**, він перемагає. Те саме
правило діє на retry-гілці (`markForRetry` перед `scheduleRetry`).

**(3) Гучний збій замість тихого.**
`deadLetter()` кидає `QueueException::deadLetterFailed`, якщо RPUSH повернув `false` —
так само, як `enqueue` і `scheduleRetry` ніколи не «втрачають» job мовчки. Подія, яка тихо
не доїхала до DLQ — це подія, втрачена з шляху відновлення. Зовнішній backstop воркера це
залогує і зробить backoff.

**(4) Конверт несе `job->attempt()`** — останню спробу, що *реально виконалася* (3 при
вичерпанні; спроба, що кинула виняток, при перманенті). Так запис у DLQ лишається
**когерентним** зі стовпцем `attempts` у БД.

### Відхилені альтернативи (з компромісами)

- **Один великий `try/catch` у воркері, який і ловить, і пушить у DLQ.** Простіше на
  перший погляд, але змішує політику (коли термінально) з механізмом (як писати в Redis) і
  розмазує її по воркеру. Втрачаємо єдине місце, де гарантовано однакова поведінка трьох
  шляхів. Відхилено.
- **Зберігати в DLQ повний payload (жирний конверт).** Зручно для drain (усе під рукою),
  але дублює дані, що вже є в `webhook_events`, роздуває Redis і створює ризик розсинхрону
  двох копій. Ми лишили крихітний конверт-посилання; drain пере-читає рядок. Відхилено.
- **DLQ як окрема таблиця в MySQL замість Redis-списку.** Транзакційно з `markFailed` (один
  COMMIT — зникає проблема порядку!), але ламає симетрію з рештою черги (queue/retry в Redis)
  і змішує «оперативний» шар черги з «аудитним» шаром БД. Свідомо лишили DLQ у Redis поряд із
  `queue`/`retry`, а проблему порядку вирішили правилом «БД спочатку». Розумний компроміс, не
  безкоштовний.
- **Зворотний порядок (Redis спочатку, БД потім).** Розібрано вище — створює невидимих
  орфанів. Відхилено.

## 4. Слабкі місця та технічний борг

- **Немає атомарності двох записів.** Як описано — можливий рядок `failed` без DLQ-запису.
  Ми обрали *відновлюваний* напівстан, але повне закриття — це reconciliation у T3.2
  (звірка `status='failed'` ↔ вміст `webhooks:dlq`). Поки T3.2 немає — борг свідомий.
- **DLQ нічим не обмежений.** Якщо «отруйна» подія (poison message) стабільно падає у
  багатьох провайдерів, або якщо хвиля помилок зростає — `webhooks:dlq` росте без межі. Немає
  ні алерту «DLQ > N», ні TTL, ні автоматичного drain. При зростанні обсягу це перше, що
  заболить.
- **Захисна гілка `handler === null`** означає, що подію з невідомим провайдером ми
  термінально dead-letter'имо. Це коректно, але якщо в DLQ почнуть масово сипатися такі —
  це сигнал конфігураційної помилки маршрутизації, а не «зламаних» подій. Без окремого
  розрізнення причин у дашборді їх легко переплутати.
- **Поведінка при rotation секретів.** Якщо секрет підпису провайдера змінили, а старі
  in-flight події ще в черзі — вони можуть падати на перевірці й потенційно доходити до
  DLQ. T2.4 цього не вирішує (перевірка підпису — на прийомі, не у воркері), але про це
  варто пам'ятати як про джерело «фальшивих» термінальних падінь.
- **`markFailed` не пише `attempts`** (рев'ю, NIT #3). Для перманент-шляху це означає, що
  `attempts` у БД лишається тим, чим був до падіння, тоді як конверт DLQ несе фактичну
  спробу. Контракт `markFailed` свідомо не міняли (поза скоупом T2.4), але це місце, де БД і
  DLQ можуть розповідати трохи різні історії про номер спроби.

## 5. Патерни, які варто запам'ятати

- **Dead Letter Queue (DLQ)** — окреме термінальне сховище для повідомлень, які не вдалося
  обробити. Зустрічається всюди: RabbitMQ (dead-letter exchange), AWS SQS (redrive policy),
  Kafka (dead-letter topic). Суть однакова — не губити «погані» повідомлення мовчки.
- **At-least-once delivery + ідемпотентність.** Провайдер може прислати подію двічі; ми
  можемо повторити job. Тому обробники мають бути ідемпотентні (dedupe за `(provider,
  event_id)` унікальним ключем). DLQ — частина цієї ж філософії: краще зайвий запис на
  розбір, ніж втрачена подія.
- **Audit / event log як джерело правди (source of truth).** Коли є два сховища (MySQL +
  Redis) і немає спільної транзакції — *одне* має бути авторитетним. Тут це рядок у БД, тому
  його пишемо першим. Це загальний принцип: визнач джерело правди й узгоджуй порядок записів
  на його користь.
- **Mechanism vs Policy split.** «Як зробити» (RPUSH, ім'я ключа) відокремлено від «коли і
  чи робити» (термінальність, ліміт спроб). Класичний прийом, що тримає політику тестовною й
  зосередженою в одному місці.
- **Consolidation of branches (DRY для критичних рішень).** Три шляхи → один метод
  `deadLetter()`. Коли кілька місць *мусять* поводитися однаково, винеси їх у одну точку, щоб
  вони не могли розійтися при майбутніх правках.
- **Fail loud, not silent.** Збій інфраструктурного запису кидає виняток, а не ковтається.
  Дзеркало того, як `enqueue`/`scheduleRetry` ніколи не втрачають job тихо.

**Крок 5 — одноразовий інтеграційний harness `app/verify_t24.php`.**
Зібрав `Queue`/`EventRepository`/`RetryScheduler` рівно так, як це робить `worker.php` (через
`bootstrap.php`), прогнав три кейси проти **справжніх** Redis + MySQL і видалив файл.
*Навіщо:* `php -l` не доводить *поведінку*. Треба переконатися, що термінальні шляхи реально
і пишуть `failed`/`last_error` у БД, і кладуть конверт у `webhooks:dlq`, а контрольний кейс
(є ще спроби) — **не** dead-letter'ить. Harness одноразовий, бо це не unit-тест проєкту, а
ручна верифікація скоупу.

Фактичний вивід harness:
```
=== Case A: PERMANENT error path (worker permanent catch -> deadLetter) ===
DB: status=failed attempts=0 last_error="bad payload: cannot ever succeed"

=== Case B: EXHAUSTION path (retryOrFail, attempt 3 -> next 4 > MAX) ===
DB: status=failed attempts=0 last_error="downstream still timing out"

=== Case C: control — retryOrFail with attempts REMAINING must NOT dead-letter ===
DB: status=received attempts=2 (expect 'received', NOT in dlq)

=== Redis webhooks:dlq contents ===
LLEN webhooks:dlq = 2
  [0] {"event_id":"T2.4-perm","provider":"github","attempt":1}
  [1] {"event_id":"T2.4-exhaust","provider":"stripe","attempt":3}

=== Cleanup ===
test rows + keys removed
```
*Інтерпретація:*
- **Case A (перманент):** `failed` + `last_error` + конверт у DLQ зі `attempt:1` (спроба, що
  кинула виняток).
- **Case B (вичерпання):** `failed` + `last_error` + конверт у DLQ зі `attempt:3` (остання
  спроба, що виконалася).
- **Case C (контроль):** `received`, `attempts=2`, у DLQ **не** потрапив (усього 2 записи в
  списку, а не 3) — підтверджує, що поки є спроби, dead-letter не спрацьовує.
- `attempts=0` у A/B — це **артефакт harness**: рядки засіювалися свіжими, а не проганялися
  через реальний багатоспробовий потік, де `markForRetry` записав би `attempts=3`. `markFailed`
  навмисно не чіпає `attempts` (див. борг у розділі 4).

**Крок 6 — застосування рев'ю.**
Рев'ю (`.claude/reviews/T2.4-2026-06-06.md`, вердикт «Approve with nits»):
- **MINOR #1 — застосував:** захисну гілку `$handler === null` у `worker.php` провів через
  `$scheduler->deadLetter(...)` замість «голого» `markFailed`, щоб **усі** термінальні падіння
  однаково потрапляли в DLQ.
- **NIT #2 — прийняв:** `RetryScheduler::deadLetter` має бути `public` (його кличе воркер).
- **NIT #3 — відхилив:** `markFailed` не пише `attempts` — контракт незмінний, поза скоупом
  T2.4 (зафіксовано як борг).

Після правки — повторний lint і перевірка єдиності точки виклику:

## Запити до бази даних

### SQL, який виконує сам КОД ФІЧІ на DLQ-шляху

`markFailed` (тіло НЕ змінювалося в T2.4 — це БД-половина термінальної пари):
```sql
UPDATE webhook_events SET status = 'failed', last_error = :error WHERE id = :id;
```

### SQL, який виконував мій верифікаційний HARNESS (і потім прибрав за собою)

```sql
-- пре-очистка кожного тестового рядка
DELETE FROM webhook_events WHERE provider = ? AND event_id = ?;

-- вставка (через EventRepository::insertReceived)
INSERT INTO webhook_events (provider, event_id, event_type, payload, signature_valid, status)
VALUES (?, ?, ?, ?, 1, 'received')
ON DUPLICATE KEY UPDATE id = id;

-- findForProcessing
SELECT id, event_type, payload, status
FROM webhook_events
WHERE provider = :provider AND event_id = :event_id;

-- markProcessing (захищений claim)
UPDATE webhook_events SET status = 'processing'
WHERE id = :id AND status = 'received';

-- markFailed (Cases A, B)
UPDATE webhook_events SET status = 'failed', last_error = :error WHERE id = :id;

-- markForRetry (Case C)
UPDATE webhook_events SET status = 'received', attempts = :attempts, last_error = :error
WHERE id = :id;
```

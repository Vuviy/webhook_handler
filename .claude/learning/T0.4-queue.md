# Навчальна нотатка: T0.4 — Redis client wrapper (`Queue`)

> Мова: українська. Аудиторія: junior → middle PHP.

## 1. Проблема простими словами

Контролер прийому вебхуків повинен віддавати провайдеру `202 Accepted` максимально
швидко (правило з `CLAUDE.md`: **HTTP-запит ніколи не робить важку роботу**). Тож після
перевірки підпису й запису події в MySQL нам треба лише **поставити завдання в чергу** —
а вже довготривалий воркер його забере й обробить.

У цій підзадачі ми зробили обгортку `App\Queue\Queue` над Redis (розширення `phpredis`),
яка інкапсулює дві речі, котрих у сирого `\Redis` немає:

- **ім'я ключа черги** — `webhooks:queue` (одне-єдине джерело істини),
- **схему JSON-конверта завдання** — `{event_id, provider, attempt}`.

Скоуп саме цієї задачі свідомо вузький: **підключення + `enqueue()` (RPUSH) + `size()`
(LLEN)**. Споживання (`BLPOP`), черга відкладеного retry (sorted set) і Dead Letter Queue —
це задачі воркера T2.x, тут їх НЕ реалізовано навмисно.

Чому це важливо для системи вебхуків: черга — це місце, де HTTP-частина «відпускає» подію.
Якщо обгортка тут наплутає (тихо загубить завдання, повісить FPM на недоступному Redis,
розмаже ключ черги по коду), то постраждає або швидкість відповіді провайдеру, або
гарантія доставки.

## 2. Потік виконання

Де `Queue` стоїть у загальному маршруті вебхука (жирним — те, що додала ця задача):

```
GitHub / Stripe / PayPal
   │  POST /webhooks/{provider}
   ▼
Nginx ──► PHP-FPM (контролер прийому)        ← T1.x, ще попереду
   1. читає RAW body
   2. перевіряє підпис (timing-safe)
   3. INSERT події (status=received) у MySQL  ← важкий payload лишається ТУТ
   4. **Queue::enqueue(eventId, provider)  →  RPUSH {event_id,provider,attempt} у webhooks:queue**
   5. повертає 202 Accepted
   ▼
Redis (список webhooks:queue)
   ▼
Worker (довготривалий)                        ← T2.x, ще попереду
   - BLPOP завдання
   - читає за event_id повний рядок із MySQL (джерело істини)
   - success → status=processed
   - failure → retry (backoff 2^n), attempt++
   - 3 невдачі → DLQ, status=failed
```

Зверни увагу на крок 4↔воркер: у черзі лежить **не сам payload**, а маленьке посилання
по `event_id`. Воркер потім **перечитує джерело істини з БД**. Це навмисно (див. §3).

Усередині `enqueue()` потік такий: `encodeJob()` будує JSON із `JSON_THROW_ON_ERROR` →
`rPush()` додає рядок у кінець списку → перевірка `=== false` → у разі провалу
`QueueException::enqueueFailed`. `RPUSH` додає в кінець, споживач робитиме `BLPOP` з
початку — разом це дає **FIFO**.

## 3. Чому саме так

**phpredis, а не predis.** Розширення `redis` уже скомпільоване в контейнері
(`php -m` показує `redis`), а `predis` немає. Брати `predis` означало б тягнути нову
composer-залежність без жодної потреби. Рішення: phpredis. (ADR: `.claude/decisions/0005-redis-queue-client.md`.)

**Чому тут обгортка виправдана, а в T0.3 (`Connection`) — ні.** У `php-conventions`
SKILL.md заборонено passthrough-wrapper'и (клас, що лише пробрасує чужий API). `\PDO`
вже має повний API — обгортка над ним була б порожнім посередником, тому в T0.3
`Connection` лишився **тонкою фабрикою**. А `Queue` додає **словник**, якого в сирому
`\Redis` немає: назву ключа й схему конверта. Це **доменна абстракція**, а не passthrough,
тож виняток із правила тут свідомий і виправданий.

**Eager connect у `fromConfig()` з таймаутом 1.5 с.** Підключення відбувається одразу
на bootstrap, як і в `Connection::fromConfig`. Чому: погана конфігурація (недоступний
Redis) має падати **на старті**, а не посеред обробки запиту. Таймаут 1.5 с не дає
PHP-FPM «висіти» на мертвому Redis — це елемент **fail-fast** і захист від вичерпання
FPM-воркерів.

**Маленький конверт навмисно.** Важкий payload лишається в MySQL (`webhook_events`),
у черзі — лише `event_id`. Чому: доставка **at-least-once**, тож воркер у будь-який
момент перечитує актуальний стан із БД (джерело істини), а не довіряє копії в черзі,
яка могла застаріти або задублюватися.

**Помилки — типізований `QueueException`, без секретів.** Повідомлення містять
максимум `host:port` або `event_id` і **ніколи payload чи секрети** — щоб нічого
чутливого не потрапило в логи/стектрейси. Дзеркалить `DatabaseException` із T0.3.

**Відхилення від ADR (рішення головного агента).** `deadLetterSize()` і константи
ключів `webhooks:retry` / `webhooks:dlq` **відкладено до T2.x**. Причина: ці ключі
набувають семантики лише у воркері; оголосити їх зараз = мертвий код без споживача.
Це зафіксовано в ADR у секції «Deviations during implementation».

## 4. Слабкі місця та технічний борг

- **Один список без споживача.** Зараз ми лише наповнюємо `webhooks:queue`. Поки немає
  воркера (T2.x), черга необмежено росте — потенційний out-of-memory у Redis. Це
  очікувано на цьому етапі, але треба пам'ятати.
- **Немає persistence-гарантій Redis.** За замовчуванням список у пам'яті; при падінні
  Redis без AOF/RDB завдання губляться. At-least-once тримається на тому, що подія вже
  в MySQL зі `status=received`, але механізму «дочерпати незапущені» поки немає (це теж T2.x).
- **`enqueue` не атомарний із записом у БД.** Між `INSERT` у MySQL і `RPUSH` у Redis є
  вікно: якщо процес упаде поміж ними — подія є в БД, але не в черзі. Класична проблема
  dual-write; промислове рішення — патерн **transactional outbox** (поки не наша задача).
- **`size()` ≠ кількість «живих» завдань.** Це довжина одного списку, без урахування
  retry-zset і DLQ. Для дашборду пізніше доведеться рахувати кілька ключів.
- **Поки немає захисту від poison message й thundering herd на retry** — це буде в T2.x
  (backoff `2^n`, обмеження 3 спроб, DLQ). Просто тримай у голові, що `attempt` у конверті
  закладено саме під це.

## 5. Патерни, які варто запам'ятати

- **At-least-once delivery** — повідомлення може прийти ≥1 раз; тому обробники мають бути
  **ідемпотентними**. Зустрічається скрізь: Kafka, SQS, RabbitMQ, самі провайдери вебхуків.
- **Idempotency key / дедуплікація** — тут роль ключа гратиме `(provider, event_id)` на
  стороні споживача. Той самий принцип — у Stripe API (`Idempotency-Key`), у платіжних системах.
- **Reference message (claim check)** — у чергу кладемо посилання, а не великий payload;
  тіло лежить у БД/сховищі. Патерн **Claim Check** з Enterprise Integration Patterns.
- **Fail-fast / connect timeout** — краще швидко впасти, ніж тримати ресурс заблокованим.
  Аналог: connection timeouts у HTTP-клієнтах, circuit breaker.
- **Domain wrapper vs passthrough** — обгортати чужий API варто лише коли додаєш словник/
  правила домену; інакше це зайвий шар. Орієнтир для майбутніх рішень «обгортати чи ні».
- (Далі в системі) **Exponential backoff**, **Dead Letter Queue**, **timing-safe порівняння
  підписів** — з'являться у T1.x/T2.x; `attempt` у конверті — їхній заділ.

## Покрокова хроніка

Реальні команди й вивід, у порядку виконання.

1. **Збір контексту.** Підтверджено, що `ext-redis` встановлено:
   ```
   php -m | grep redis
   redis
   ```
   Redis 7.4-alpine, сервіс `redis`, `REDIS_HOST=redis`, `REDIS_PORT=6379`,
   клас `RedisConfig` уже існує (з T0.x).

2. **Архітектор** спроєктував T0.4 і записав ADR `.claude/decisions/0005-redis-queue-client.md`
   (phpredis vs predis; чому обгортка виправдана; eager connect; малий конверт).

3. **Реалізація:** `app/src/Queue/Queue.php` (namespace `App\Queue`) і
   `app/src/Exception/QueueException.php`.

4. **Лінт синтаксису:**
   ```
   php -l app/src/Queue/Queue.php          → No syntax errors detected
   php -l app/src/Exception/QueueException.php → No syntax errors detected
   ```

5. **Smoke-тест** (через `php -r` у контейнері):
   ```php
   $q = Queue::fromConfig(RedisConfig::fromEnv());
   $q->enqueue('evt_1', 'github');
   $q->enqueue('evt_2', 'stripe', 2);
   echo $q->size();   // 2
   ```
   Усередині це викликало `connect(host, port, 1.5)`, два `rPush('webhooks:queue', <json>)`
   і `lLen('webhooks:queue')`.

6. **Перевірка вмісту в Redis:**
   ```
   redis-cli LRANGE webhooks:queue 0 -1
   {"event_id":"evt_1","provider":"github","attempt":1}
   {"event_id":"evt_2","provider":"stripe","attempt":2}

   redis-cli LLEN webhooks:queue
   2
   ```
   Видно FIFO-порядок: `RPUSH` поклав `evt_1` першим, `evt_2` — у кінець.

7. **Перевірка шляху помилки.** З `REDIS_HOST=nope_no_host`:
   ```
   fromConfig() → QueueException: Failed to connect to Redis at "nope_no_host:6379".
   ```
   На цьому етапі phpredis ще друкував і нативний PHP Warning (виправлено пізніше).

8. **Рев'ю (code-reviewer):** вердикт «схвалити з дрібницями», без BLOCKER/MAJOR.
   `phpstan` (level max) — чисто; `phpcs` (PSR-12) — чисто; `psalm` не запускався (немає
   `psalm.xml`). Застосовано:
   - **#1** вузький `@` лише на `connect()`, щоб прибрати подвійний Warning (не ковтає
     `RedisException` і не скасовує перевірку `=== false`);
   - **#3** `enqueue()` тепер перевіряє `rPush() === false` → `QueueException::enqueueFailed`;
   - **#2** у ADR додано секцію про відхилення (`deadLetterSize` відкладено до T2.x).

9. **Повторна верифікація після правок:**
   ```
   php -l  → чисто на обох файлах
   happy path → size() = 1
   шлях помилки → лише типізований QueueException, БЕЗ нативного Warning
   ```

## Запити до бази даних

**SQL-запитів до MySQL у цій підзадачі НЕ виконувалося** — `Queue` працює виключно з
Redis. Натомість виконувались такі команди до Redis:

`redis-cli` (вручну):
```
redis-cli DEL webhooks:queue            # очистка списку перед тестами
redis-cli LRANGE webhooks:queue 0 -1    # перегляд вмісту черги
redis-cli LLEN webhooks:queue           # довжина черги
```

Через сам клас `Queue` (phpredis під капотом):
```
connect(host, port, 1.5)                # eager connect у fromConfig()
rPush('webhooks:queue', <json-конверт>) # enqueue()
lLen('webhooks:queue')                  # size()
```

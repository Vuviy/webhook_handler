# Навчальна нотатка: T2.2 — цикл воркера (`worker.php`)

> Мова: українська. Аудиторія: junior → middle PHP.
> Дизайн і обґрунтування: `.claude/decisions/0012-worker-loop.md`.
> Попередній крок (seam для диспетчеризації): `.claude/decisions/0011-*` (T2.1).

---

## 1. Проблема простими словами

До T2.2 у нас уже був HTTP-бік: контролер приймає вебхук, перевіряє підпис,
пише рядок у `webhook_events` зі статусом `received` і кладе крихітне посилання
(`{event_id, provider, attempt}`) у Redis-чергу `webhooks:queue`. На цьому
HTTP-запит завершується відповіддю `202 Accepted`. Але **ніхто не діставав**
ці завдання з черги — вони просто накопичувалися.

T2.2 додає **довгоживучий процес-воркер** — другу, асинхронну половину системи.
Він у нескінченному циклі дістає завдання з черги, читає відповідний рядок із
БД, «захоплює» його (`received → processing`), віддає у провайдер-специфічний
обробник і фіксує результат: `processed` при успіху або (наразі) `failed` при
будь-якій невдачі.

**Чому це окремий процес, а не робота прямо в HTTP-запиті.** Провайдери
(GitHub, Stripe, PayPal) чекають **швидкий `2xx`**. Якщо ти почнеш робити важку
роботу синхронно в контролері (звернення до зовнішніх API, повільні записи,
ретраї), провайдер впреться у власний таймаут, **вважатиме доставку невдалою і
переретраїть її на своєму боці** — ти отримаєш дублікати й каскад навантаження.
Тому архітектурне правило з `CLAUDE.md`: *HTTP-запит ніколи не робить важку
роботу — лише перевіряє, записує й ставить у чергу.* Це класична **бекпресія**:
сплеск вхідних вебхуків поглинається чергою, а воркер споживає їх у своєму
темпі, не валячи систему. Плюс **ізоляція збоїв**: падіння обробника одного
вебхука не зачіпає прийом інших.

Що **поза скоупом** T2.2 (і це навмисно): retry з backoff (T2.3), Dead Letter
Queue (T2.4), graceful SIGTERM-зупинка (T2.5). T2.2 будує робочий happy-path і
**визначену** поведінку для невдач, лишаючи чіткі шви, у які ці задачі
вставляться **доповненням, а не переписуванням**.

## 2. Потік виконання

Повний шлях вебхука після цієї зміни:

```
provider POST /webhooks/{provider}
        │
        ▼
   Nginx ──► PHP-FPM (контролер прийому)        ← HTTP-бік (вже був)
        │  1. читає RAW-тіло
        │  2. перевіряє підпис (timing-safe, hash_equals)
        │  3. INSERT ... status='received' (ідемпотентно, ON DUPLICATE KEY)
        │  4. RPUSH {event_id, provider, attempt} → webhooks:queue
        │  5. повертає 202 Accepted
        ▼
   Redis (webhooks:queue)
        │
        ▼
   worker.php (НОВЕ в T2.2) — нескінченний цикл:           ← асинхронний бік
        │  a. BLPOP webhooks:queue (фінітний таймаут 5с) → ?Job
        │     ├─ null (таймаут) → idle-tick, continue (тут житиме T2.5)
        │     └─ Job → далі
        │  b. findForProcessing(provider, eventId) → ?row
        │     └─ null (рядок зник) → лог + continue   (at-least-once: нема що робити)
        │  c. markProcessing(id)  guard: AND status='received'
        │     └─ false (0 рядків) → continue           (повторний попап → dedupe, без повтору обробника)
        │  d. registry->get(provider) → ?Handler
        │     └─ null → markFailed("no handler ...")    (перманентна вада)
        │  e. handler->handle(event)
        │     ├─ ok → markProcessed(id)  (processed_at = NOW())
        │     ├─ TransientHandlerException → markFailed  [SEAM T2.3]
        │     ├─ PermanentHandlerException → markFailed  [SEAM T2.4]
        │     └─ будь-який інший Throwable → markFailed  (як transient, ADR 0011) [SEAM T2.3]
        ▼
   MySQL (повний аудит) + (майбутній) Dashboard
```

Стан-машина статусу (T2.2):

```
received --markProcessing (guard)--> processing --handle() ok--> processed
   ^                                      |
   |  повторний попап:                    |  handle() кидає Transient|Permanent|other
   |  guard оновлює 0 рядків → skip        v
   |  (обробник НЕ запускається вдруге)  failed   (інтерим: сюди ВСІ невдачі;
                                                   T2.3 переадресує transient, T2.4 додає DLQ)
```

## 3. Чому саме так

Чотири справжні рішення (деталі та відхилені варіанти — в ADR 0012).

**Рішення 1 — `Queue::consume(int $timeout): ?Job`, що повертає типізований `Job`.**
`Queue` уже володіє `encodeJob()` (схемою конверта на боці запису), тож декод має
жити там само. Відхилено: повертати сирий `array` (Option A) — це знову розкрило б
імена полів конверта (`event_id`, `provider`, `attempt`) воркеру, і кожен виклик
мусив би їх перевалідовувати; та callback-API `consume(callable)` (Option C) —
воно б закопало контрольний потік воркера (переходи статусу, catch-блоки)
всередину абстракції черги й інвертувало володіння політикою обробки.
`Job` — це **value object**, дзеркало `encodeJob()`: схема конверта запечатана
всередині `Queue` з обох боків, як `WebhookEvent` / `VerificationResult`.

**Чому `Job` окремо від `WebhookEvent`.** `Job` — це *посилання в черзі* (що
дістати: лише id), а `WebhookEvent` — *уже дістаний перевірений рядок* (що
обробляти: тип події, payload). Вони перетинаються в `provider`/`attempt`, але
це різні речі. Якби ми їх злили, колонки БД протекли б у шар черги. Важкий
payload навмисно лишається в MySQL — у черзі лише крихітне посилання.

**Чому фінітний BLPOP-таймаут (5с), а не блокування назавжди (`BLPOP … 0`).**
З `0` цикл ніколи не отримує контроль між завданнями: T2.5 не зможе перевірити
прапор зупинки без жорсткого вбивства, а обрив з'єднання Redis спливе лише на
наступному пуші. Фінітний таймаут дає циклу «idle-tick»: він прокидається кожні
N секунд навіть без роботи — це природне місце для T2.5 і для помічання
розірваного з'єднання. Ціна — один дешевий порожній прокид раз на 5с.

**Рішення 2 — інтент-іменовані, guard-захищені методи репозиторію.**
`findForProcessing` (один SELECT), `markProcessing` (guard `AND status='received'`),
`markProcessed`, `markFailed`. Відхилено: один загальний
`updateStatus($id, $status, $error)` (Option D) — stringly-typed статус провокує
друкарку в значенні enum, що тихо ламає дашборд, і не виражає *захопленого*
переходу; та беззахисні записи статусу (Option F) — викинули б безкоштовний
guard проти повторного попапу.

**Чому guard `AND status='received'` у `markProcessing` — серце ідемпотентності.**
Доставка — **at-least-once**: те саме завдання може попастися двічі (повторний
RPUSH провайдером, повторна доставка). Guard робить захоплення **атомарним**:
перший виклик матчить рядок (`received`) і переводить у `processing`; другий
виклик матчить **0 рядків** (рядок уже не `received`), `rowCount() === 0` → метод
повертає `false`, і воркер **пропускає завдання, не запускаючи обробник вдруге**.
Це dedupe рівня воркера **без другого SELECT** (FR-11). Бонус: він уже сумісний
із T2.3 — ретрай поверне рядок у `received` перед повторною постановкою в чергу,
тож легітимний ретрай знову виграє захоплення. Це приклад **оптимістичного
захоплення (optimistic claim)**: ми не блокуємо рядок, а покладаємось на умовний
`UPDATE`, що сам собою атомарний.

**Рішення 3 — інтерим `failed` для ВСІХ невдач.** Ще немає retry/DLQ, тож усі
три гілки (`Transient`, `Permanent`, catch-all `Throwable`) наразі викликають
`markFailed` + пишуть `last_error`, логують один рядок і йдуть далі. Відхилено:
дати винятку вилетіти з циклу (Option G) — він убив би процес, а
`restart: unless-stopped` тоді **гаряче зациклить рестарти на poison-повідомленні**,
лишивши рядок навічно в `processing`; та «лишати transient у `received`» без
планувальника (Option I) — рядок сидів би в `received`, але **не** в черзі:
невидимий застряглий стан, гірший за `failed`. Чесний `failed` із `last_error`
видимий в аудиті. **Три catch-блоки — це точні шви для T2.3/T2.4**: пізніші задачі
**замінять тіла** блоків (transient → запланувати retry / mark `received`;
permanent/вичерпаний → `webhooks:dlq`), а не форму циклу чи інтерфейс.

**Рішення 4 — infra-backstop (зовнішній `try/catch (\Throwable)` + `sleep 1s`).**
Збої *обробника* ловляться внутрішніми catch. Окремо — *інфраструктурні* збої
(BLPOP кидає `RedisException`, запис статусу кидає `PDOException`). Під
`restart: unless-stopped` непохоплена інфра-помилка → гарячий crash-loop. Зовнішній
backstop логує (`error_log((string) $e)` — та сама дисципліна, що в
`public/index.php`: повна деталь у лог, ніколи не назовні) і робить паузу 1с,
дегрейдячись до «retry-the-loop». Сполучення будуються **один раз до циклу** —
тож обрив на старті валиться **fail-fast** ще до входу в цикл (як `bin/migrate.php`).
Важливо: цей `sleep 1s` — це **INFRA backoff**, а **не** retry backoff T2.3.
Їх не можна плутати.

## 4. Слабкі місця та технічний борг

- **Інтерим `failed` пере-комітить transient-вади.** Доки немає T2.3, тимчасова
  помилка (мережевий блимок зовнішнього API) термінально позначається `failed`
  замість ретраю. Це усвідомлений борг на одну задачу: чесно, залоговано,
  видимо в аудиті — але **не** автоматично відновлюється. Задокументовано в
  докблоці `worker.php` і в ADR.
- **Немає захисту від poison-повідомлень як стратегії.** Зараз отруйне завдання
  один раз позначається `failed` і зникає з черги. Коли з'явиться retry (T2.3)
  без DLQ (T2.4), отруйне завдання могло б ретраїтись вічно — тому DLQ і
  лічильник `attempts` критичні саме разом.
- **Застрягання в `processing`.** Якщо `handle()` успішний, але `markProcessed()`
  падає (DB-блимок), рядок лишається в `processing` (це навмисно — див. урок
  нижче), а завдання вже зникло з черги. Потрібен майбутній «reaper» застряглих
  `processing` — поки що це борг.
- **`attempt` тече, але не діє.** Він проходить із конверта у `WebhookEvent`, але
  **не інкрементується** і ні на що не впливає; `markProcessing` не чіпає колонку
  `attempts`. Інкремент і retry-математика — власність T2.3.
- **Два невеликі «магічні числа»** (BLPOP-таймаут 5с, infra-backoff 1с) — обидва
  суто інфраструктурні. Їх легко сплутати з майбутнім retry backoff — тому
  явно названо.
- **Thundering herd при майбутньому ретраї.** Коли прийде T2.3, наївний
  фіксований backoff змусив би всі невдалі завдання ретраїтись синхронно. Тому
  експоненційний backoff (+ jitter) у T2.3 — не примха, а захист від стада.
  В T2.2 цього ще нема — це передумова, яку треба пам'ятати.

### Урок із рев'ю (MAJOR-1) — межа «помилка обробника» vs «інфра-фолт»

Спершу `markProcessed()` стояв **усередині** внутрішнього `try` разом із
`handle()`. Сценарій, що це ламав: `handle()` **успішний**, а `markProcessed()`
падає через DB-блимок. Тоді `catch (\Throwable)` спіймав би це і викликав
`markFailed()` — тобто **успішно оброблену подію записав би як `failed`**. Це
псує аудит і ламає at-least-once (завдання вже зникло з черги, у `processed` воно
ніколи не потрапить).

Виправлення: внутрішній `try` обгортає **ЛИШЕ** `handle()`; кожен catch
завершується `continue`; `markProcessed()` винесено **ПІСЛЯ** `try`. Тепер збій
`markProcessed()` — це інфра-фолт, що падає у зовнішній backstop, а рядок чесно
лишається в `processing`. **Принцип:** межа між «помилкою бізнес-обробника» і
«інфраструктурним фолтом» має бути в коді чіткою — від того, що ти загорнув у
`try`, прямо залежить коректність стан-машини.

## 5. Патерни, які варто запам'ятати

- **At-least-once delivery** — гарантія «доставимо хоча б раз, можливо двічі».
  Звідси випливає обов'язкова **ідемпотентність** споживача. Зустрічається скрізь:
  Kafka, SQS, RabbitMQ, вебхуки Stripe/GitHub.
- **Idempotency / optimistic claim через guard-UPDATE** —
  `UPDATE ... WHERE id=? AND status='received'` + перевірка `rowCount()`. Атомарне
  захоплення без блокування рядка. Той самий патерн: `compare-and-swap`,
  оптимістичне блокування з версією рядка, `SELECT ... FOR UPDATE SKIP LOCKED` у
  важчих чергах на БД.
- **Producer/consumer + черга як буфер бекпресії** — HTTP пише, воркер читає у
  своєму темпі. Класика: job-черги (Sidekiq, Laravel Queue, Celery).
- **Стан-машина (state machine)** — `received → processing → processed | failed`
  з визначеними переходами. Робить систему передбачуваною й придатною до аудиту.
- **Fail-fast на старті, fault-tolerant у циклі** — сполучення будуються один раз
  і валяться голосно на старті; всередині циклу інфра-фолти дегрейдяться до
  retry-the-loop. Той самий принцип у супервізорах процесів.
- **Seam (шов) для майбутнього коду** — три порожні-за-змістом catch-блоки як
  точні місця вставки T2.3/T2.4. Дизайн «під заміну тіл, а не переписування».
- **Value object як типізований контракт між шарами** (`Job`, `WebhookEvent`) —
  «розпарсив один раз, передав типізоване значення далі», замість сирих масивів.
- **Не логувати секрети/сирі байти** (NFR-1): `QueueException::decodeFailed()`
  не називає ні payload, ні підпис. `last_error` навмисно лишається в БД, а не
  ллється в загальний лог.

## Покрокова хроніка (реальні команди та вивід)

Нижче — кожен крок, що я зробив, з реальними командами, виводом і поясненням «чому».

### Крок 1 — Лінт усіх 5 файлів у контейнері `php`

```bash
docker compose exec -T php php -l worker.php
docker compose exec -T php php -l src/Queue/Job.php
docker compose exec -T php php -l src/Queue/Queue.php
docker compose exec -T php php -l src/Exception/QueueException.php
docker compose exec -T php php -l src/Repository/EventRepository.php
```

Вивід (для кожного файлу):

```
No syntax errors detected in <файл>
```

**Чому.** `php -l` — найдешевша перевірка: ловить синтаксичні помилки до запуску
будь-якої логіки. Лінтуємо **в контейнері** (а не на хості), бо саме PHP 8.3 із
контейнера виконуватиме код у проді — версії й розширення мають збігатися.

### Крок 2 — Переконатися, що таблиця на місці (міграція)

```bash
docker compose exec -T php php bin/migrate.php
```

Вивід:

```
Database is up to date — no migrations to apply.
```

**Чому.** Воркер пише в `webhook_events`. Перед інтеграційним тестом треба
впевнитись, що схема актуальна. Цього разу нових міграцій не було — **жодного DDL
не застосовано**, що теж важливо зафіксувати чесно (тест ішов на наявній схемі).

### Крок 3 — Покласти реальну GitHub-подію в чергу через справжні класи

```bash
docker compose exec -T php php -r '
  require "bootstrap.php";
  /* ... build Config, Connection, EventRepository, Queue ... */
  $new = $events->insertReceived("github", "t2.2-happy-1780731948", "push", "{...}");
  $queue->enqueue("t2.2-happy-1780731948", "github");
  echo "inserted_new=" . ($new ? "true" : "false")
     . " event_id=t2.2-happy-1780731948 queue_size=" . $queue->size() . "\n";
'
```

Вивід:

```
inserted_new=true event_id=t2.2-happy-1780731948 queue_size=2
```

**Чому.** Я тестую через **справжні класи** (`insertReceived` + `enqueue`), а не
вставляю рядок руками: так перевіряється реальний шлях, яким ходить продакшн.
`queue_size=2` — у черзі вже був старий stale-job (без рядка в БД), і це навмисно
покаже гілку «рядок зник» на наступному кроці. **Альтернатива** — згенерувати
завдання сирим `redis-cli RPUSH`: швидше, але обійшло б `encodeJob()` і не
довело б, що продюсер і консюмер узгоджені по схемі конверта. Відхилено.

### Крок 4 — Запустити воркер і подивитись обробку

```bash
docker compose up -d worker
sleep 8
docker compose logs --tail=30 worker
```

Вивід (логи):

```
worker: started, waiting for jobs on webhooks:queue
worker: no row for 666 event "555"; skipping
```

Перевірка стану в БД (див. «Запити до бази даних», запит 1):

```
id | provider | event_id              | status    | attempts | last_error | processed_at
---+----------+-----------------------+-----------+----------+------------+--------------------
 N | github   | t2.2-happy-1780731948 | processed |    1     | NULL       | 2026-06-06 07:45:56
```

Розмір черги після обробки: `0`.

**Чому.** Це happy-path end-to-end: завдання дістано, рядок захоплено, обробник
відпрацював, статус → `processed`, `processed_at` проставлено. Лог
`no row for 666 event "555"` — це той stale-job без рядка: воркер коректно
**пропустив** його (гілка `findForProcessing → null`), а не впав. Так на живому
прикладі видно гілку «рядок зник» під at-least-once.

### Крок 5 — Тест дедупу (повторний попап) + невідомий провайдер

```bash
docker compose exec -T php php -r '
  /* ... */
  $queue->enqueue("t2.2-happy-1780731948", "github");   // вже processed → повторний попап
  $events->insertReceived("acme", "t2.2-unknown-1", "x", "{}");
  $queue->enqueue("t2.2-unknown-1", "acme");             // провайдера acme немає в registry
'
sleep 7
```

Перевірка стану в БД (див. «Запити до бази даних», запит 2):

```
id | provider | event_id              | status    | last_error                       | processed_at
---+----------+-----------------------+-----------+----------------------------------+--------------------
 N | github   | t2.2-happy-1780731948 | processed | NULL                             | 2026-06-06 07:45:56
 M | acme     | t2.2-unknown-1        | failed    | no handler for provider "acme"   | NULL
```

**Чому.** Два важливі шляхи в одному тесті:
1. **Дедуп.** GitHub-рядок **лишився `processed`** — guard `AND status='received'`
   у `markProcessing` спрацював: рядок уже не `received`, оновлено 0 рядків,
   воркер пропустив завдання, **обробник не запускався вдруге**. Це доказ
   ідемпотентності рівня воркера.
2. **Невідомий провайдер = перманентна вада.** `acme` → `status=failed`,
   `last_error='no handler for provider "acme"'`, `processed_at` лишився `NULL`.
   Ретрай тут не допоміг би (обробника просто немає), тож це коректно одразу
   `failed`.

### Крок 6 — Прибирання тестових рядків

```sql
DELETE FROM webhook_events WHERE event_id LIKE 't2.2-%';
```

Вивело: видалено 2 рядки.

**Чому.** `webhook_events` — це аудит-таблиця; тестове сміття треба прибрати, щоб
не спотворювати майбутній дашборд і подальші тести.

### Крок 7 — Рев'ю та реакція на знахідки

- **MAJOR-1** (правильна): `markProcessed()` був усередині внутрішнього `try`. Я
  переструктурував `worker.php` — виніс `markProcessed()` **за** внутрішній `try`,
  у кожен catch додав `continue` (див. урок у розділі 4).
- **MINOR-1** (відхилено свідомо): нібито неправильний порядок у docblock —
  `phpcs` показував те саме «зауваження» на `migrate.php` та `index.php`, тобто
  правило фіктивне/непослідовне. Не змінював.
- **MINOR-2** (прийнято): уточнив у докблоці `markProcessing`, що `updated_at`
  оновлюється сам через `ON UPDATE CURRENT_TIMESTAMP` (колонка з міграції 0001),
  тож явний `updated_at = NOW()` був би зайвим.

**Чому.** Рев'ю не для того, щоб приймати все підряд: кожну знахідку треба або
застосувати, або **свідомо відхилити з причиною**. MINOR-1 — приклад фіктивного
зауваження, яке варто відхилити обґрунтовано.

### Крок 8 — Повторна верифікація після фіксу

## Запити до бази даних

Під час T2.2 SQL виконувався двома шляхами: **напряму** через `mysql`-клієнт у
контейнері `db_webhook` (перевірка/прибирання) і **опосередковано** через мої
PHP-класи (це і є суть фічі). Наводжу обидва.

### A. Запущені напряму через `mysql`-клієнт

```sql
-- 1) Перевірка стану всіх тестових подій після першого прогону воркера (Крок 4)
SELECT id, provider, event_id, status, attempts, last_error, processed_at
FROM webhook_events
WHERE event_id LIKE 't2.2-%'
ORDER BY id;

-- 2) Перевірка дедупу + невідомого провайдера (Крок 5)
SELECT id, provider, event_id, status, last_error, processed_at
FROM webhook_events
WHERE event_id LIKE 't2.2-%'
ORDER BY id;

-- 3) Перевірка повторного прогону після фіксу MAJOR-1 (Крок 8)
SELECT provider, event_id, status, processed_at
FROM webhook_events
WHERE event_id LIKE 't2.2-recheck-%';

-- 4) Прибирання основних тестових рядків (Крок 6) — видалено 2 рядки

-- 5) Прибирання recheck-рядка (Крок 8)
DELETE FROM webhook_events WHERE event_id LIKE 't2.2-recheck-%';
```

Призначення: запити 1–3 — це **спостереження за стан-машиною** (підтвердити
переходи `received → processing → processed` і `→ failed`); 4–5 — прибрати тестове
сміття з аудит-таблиці.

### B. Виконані опосередковано через мої класи (суть T2.2)

```sql
-- EventRepository::insertReceived  (через php -r для github / acme / stripe тестових подій)
-- Призначення: ідемпотентний запис ПЕРЕВІРЕНОЇ події як 'received'.
-- rowCount()===1 → новий рядок; 0 → дублікат (re-delivery). Це dedupe рівня прийому.
INSERT INTO webhook_events (provider, event_id, event_type, payload, signature_valid, status)
VALUES (:provider, :event_id, :event_type, :payload, 1, 'received')
ON DUPLICATE KEY UPDATE id = id;

-- EventRepository::findForProcessing
-- Призначення: один SELECT, щоб дістати рядок і побудувати WebhookEvent.
-- null під at-least-once = "рядок зник", воркер пропускає.
SELECT id, event_type, payload, status
FROM webhook_events
WHERE provider = :provider AND event_id = :event_id;

-- EventRepository::markProcessing  ← КРИТИЧНИЙ guard
-- Призначення: атомарно ЗАХОПИТИ подію received → processing.
-- Guard `AND status='received'` робить захоплення ідемпотентним: повторний попап
-- оновлює 0 рядків → rowCount()===0 → false → воркер пропускає, обробник НЕ
-- запускається вдруге. Це at-least-once dedupe рівня воркера БЕЗ другого SELECT (FR-11).
UPDATE webhook_events
SET status = 'processing'
WHERE id = :id AND status = 'received';

-- EventRepository::markProcessed
-- Призначення: термінальний happy-path стан + штамп часу завершення (FR-9).
UPDATE webhook_events
SET status = 'processed', processed_at = NOW()
WHERE id = :id;

-- EventRepository::markFailed
-- Призначення: інтерим-обробка ВСІХ невдач у T2.2 — позначити 'failed' і зберегти
-- людино-читабельну причину в last_error (видимо в аудиті/дашборді, FR-9, NFR-4).
UPDATE webhook_events
SET status = 'failed', last_error = :error
WHERE id = :id;
```

Окремо: `bin/migrate.php` (Крок 2) запускав `MigrationRunner`, але **нових
міграцій не було** («Database is up to date»), тож **жодного DDL цього разу не
застосовано**.

> Чому guard у `markProcessing` критичний (ще раз, бо це ядро задачі): без нього
> повторна доставка того самого завдання призвела б до **повторного запуску
> обробника** — і нас рятувала б лише власна ідемпотентність обробника. Guard
> переносить цей захист на рівень воркера, атомарно й без додаткового запиту.

# Навчальна нотатка: T1.1 — інтерфейс `ProviderVerifier`

> Мова: українська. Аудиторія: junior → middle PHP.

## 1. Проблема простими словами

Кожен провайдер (GitHub, Stripe, PayPal) підписує свої вебхуки **по-своєму**:
GitHub — HMAC-SHA256 у заголовку `x-hub-signature-256`, Stripe — власна схема `v1`
із міткою часу в `stripe-signature`, PayPal — узагалі віддалений виклик API
`verify-webhook-signature`. Якби контролер прийому (T1.5) знав про всі ці схеми,
він перетворився б на купу `if ($provider === 'github') ... elseif ...` і кожен
новий провайдер ламав би наявний код.

У цій підзадачі ми **не писали жодного верифікатора**. Ми описали лише **контракт** —
єдиний інтерфейс `ProviderVerifier`, за яким контролер зможе перевірити будь-який
вебхук, не знаючи, чий це провайдер. Це той «шов» (seam), через який пізніше
під'єднаються конкретні реалізації T1.2/T1.3/T1.4.

Чому це важливо саме для системи вебхуків: перевірка підпису — це **межа довіри**.
Усе, що проходить її, ми вважаємо автентичним і кладемо в чергу на обробку; усе, що
не проходить, мусимо чітко відрізняти від наших власних аварій. Контракт — це місце,
де ми один раз і назавжди закріплюємо ці правила.

## 2. Потік виконання

Де саме цей контракт стоїть у повному маршруті вебхука (показую весь шлях; жирним —
ділянка, якої стосується T1.1):

```
GitHub / Stripe / PayPal
        │  POST /webhooks/{provider}   (сирий JSON + заголовок підпису)
        ▼
   Nginx ──► PHP-FPM
        │  1. контролер читає СИРЕ тіло з php://input
        │  2. ┌──────────────────────────────────────────────┐
        │     │  ►►► T1.1: $verifier->verify($rawBody,        │
        │     │            $headers): VerificationResult      │
        │     │  Valid   → їдемо далі                         │
        │     │  Invalid → 401, НЕ кладемо в чергу (FR-5)     │
        │     │  Error   → 502, провайдер хай повторить       │
        │     │  кинуто VerificationException → 500 (конфіг)  │
        │     └──────────────────────────────────────────────┘
        │  3. INSERT event (status=received) у MySQL
        │  4. RPUSH job у чергу Redis
        │  5. return 202 Accepted
        ▼
   Redis queue ──► Worker (довгоживучий процес)
        │  - pop job
        │  - dispatch у provider handler
        │  - успіх → status=processed
        │  - збій → retry (backoff 2^n), attempts++
        │  - 3 збої → Dead Letter Queue, status=failed
        ▼
   MySQL (повний аудит) + Dashboard (read-only)
```

Сам інтерфейс — синхронний крок усередині HTTP-запиту. Він **навмисно дешевий**
для GitHub/Stripe (локальний HMAC), і саме тому верифікація не порушує правила
«HTTP-запит не робить важкої роботи». Виняток — PayPal, чия перевірка вимагає
мережевого виклику; саме заради нього в контракті існує стан `Error`.

## 3. Чому саме так

ADR: `.claude/decisions/0006-provider-verifier-interface.md`.

**Три стани результату, а не `bool`.** Головне рішення підзадачі. Замість
`bool verify()` повертаємо `VerificationResult` з трьома можливими наслідками
(`VerificationOutcome`: `Valid | Invalid | Error`):

- `Valid` → запит автентичний → 202, кладемо в чергу.
- `Invalid` → підроблений / відсутній / зіпсований підпис → 401, у чергу **не** кладемо
  (FR-5). Це штатний шлях «нам прислали сміття».
- `Error` → перевірку **не вдалося виконати** (PayPal API ліг / таймаут) → 502,
  провайдер хай повторить.

Чому це принципово: булеве «false» **злило б** дві геть різні події — *чужу підробку*
і *нашу власну аварію*. Якби PayPal API впав, а ми повернули `false → 401`, ми б
збрехали провайдеру, що його підпис поганий, і він **перестав би повторювати**
цілком валідний вебхук. `401` каже «ти винен», `502` каже «я тимчасово зламаний, спробуй
ще». Це різниця в HTTP-семантиці, яка прямо впливає на доставку.

**Верифікатор сам дістає `event_id` і `event_type` і кладе в `valid()`.** Він уже
тримає сире тіло в руках і єдиний розуміє формат конкретного провайдера. Ці значення
потрібні контролеру одразу: `event_id` — ключ дедуплікації (`UNIQUE (provider, event_id)`,
FR-11), `event_type` — `NOT NULL`-колонка. Парсимо тіло **один раз**, тим, хто його
розуміє, і контролер лишається провайдер-незалежним.

**Секрету немає в інтерфейсі.** Кожен конкретний верифікатор отримує свій секрет у
конструктор з `App\Config\ProviderSecrets` (T1.2+). Відсутній секрет — це **помилка
конфігурації деплою**, а не підробка: тому `verify()` кидає `VerificationException`
(→ 500), а не повертає `Invalid` (→ 401). Сплутати ці дві речі — означало б маскувати
зламаний деплой під «хакерську атаку» і ніколи його не помітити.

**Вхід — `(string $rawBody, array $headers)`.** `rawBody` — сирі байти з `php://input`
(NFR-1). Ніколи не пересеріалізований JSON: одне `json_encode(json_decode(...))`
змінить байти (пробіли, порядок ключів, екранування) і **зламає HMAC**. `headers` —
мапа з ключами в нижньому регістрі (нормалізацію робить контролер у T1.5), бо HTTP-
заголовки регістронечутливі, і кожен верифікатор читає лише свій (`x-hub-signature-256`,
`stripe-signature`, `paypal-*`).

## 4. Слабкі місця та технічний борг

- **Контракт — це обіцянка, яку ще ніхто не виконує.** Жодного реального верифікатора
  поки немає; уся цінність розкриється тільки в T1.2–T1.4. Ризик: реалізуючи їх,
  легко піддатися спокусі «трохи розширити» інтерфейс під конкретний провайдер і
  розмити шов. Тримати інтерфейс вузьким.
- **`Error` поки що чисто теоретичний.** Лише PayPal (T1.4) колись його породить.
  Поки контролер (T1.5) не навчиться відрізняти `Error` від `Invalid` і віддавати 502,
  цей стан — мертвий код. Борг: не забути дотягнути обробку `Error` у контролері,
  інакше аварію PayPal знову віддамо як 401.
- **`event_id` / `event_type` як `string`.** Контракт гарантує лише непорожність
  (guard у `valid()`). Він **не** обмежує довжину чи формат — занадто довгий `event_id`
  від провайдера впреться вже в схему БД, а не тут. Це свідомо: валідація формату — не
  завдання контракту.
- **Нормалізацію регістру заголовків делеговано T1.5.** Якщо контролер забуде це
  зробити, верифікатори тихо не знайдуть свій заголовок і повернуть `Invalid` — тобто
  баг конфігурації замаскується під «поганий підпис». Це найтонше місце контракту:
  передумова, яку не видно з самого інтерфейсу.

## 5. Патерни, які варто запам'ятати

- **Strategy / поліморфізм за інтерфейсом.** `ProviderVerifier` — класична стратегія:
  один контракт, багато реалізацій, вибір у рантаймі за тегом `provider()`. Так само
  працюють PSR-3 логери, драйвери черг, платіжні шлюзи.
- **Result object замість булева/винятку для очікуваних результатів.** Очікуваний
  «поганий вхід» (підроблений підпис) — це **значення** (`Invalid`), а не виняток.
  Винятки лишаємо для справді виняткового — зламаної конфігурації. Те саме у Rust
  (`Result<T,E>`), у функціональному стилі (`Either`), у валідаторах форм.
- **Value Object з приватним конструктором + named constructors.** `valid()/invalid()/
  error()` роблять **недопустимі стани невиразними**: не можна випадково створити
  `Valid` без `event_id`. Загальний прийом «make illegal states unrepresentable».
- **Fail loud on misconfiguration, fail soft on bad input.** Конфіг-помилка → гучний
  500; ворожий вхід → тихий 401, ніколи не 5xx (spec Risk §8). Базовий принцип
  стійких HTTP-сервісів.
- **Idempotency key.** `event_id` тут — заготовка під дедуплікацію at-least-once
  доставки (FR-11). Той самий патерн — idempotency-key у платіжних API Stripe.
- **Timing-safe порівняння (`hash_equals`).** Прямо в T1.1 коду немає, але контракт
  існує саме щоб конкретні верифікатори зробили це правильно — порівняння підписів
  без витоку часу.

## Запити до бази даних

У цій підзадачі **жодного SQL-запиту до БД не виконувалося**. T1.1 — це чистий
контракт у PHP (інтерфейс + value object + enum + клас винятку), без жодного доступу
до даних. Згадки про `UNIQUE (provider, event_id)` та `NOT NULL` колонки в нотатці —
це **пояснення, навіщо** контракт несе `event_id`/`event_type`, а не виконані запити.
Реальна робота з БД почнеться в контролері прийому (T1.5).

# Навчальна нотатка: T3.1 — Дашборд: лічильники за статусами, останні падіння, розмір DLQ

> Мова: українська. Аудиторія: junior → middle PHP.
> Артефакти: ADR `.claude/decisions/0016-dashboard.md`,
> рев'ю `.claude/reviews/T3.1-2026-06-06.md`.

## 1. Проблема простими словами

Усі попередні підзадачі (T1.x — прийом, T2.x — обробка, retry, DLQ, graceful shutdown)
**писали** дані: рядки в `webhook_events`, конверти в `webhooks:dlq`. Але оператор досі не
мав жодного **вікна всередину системи**. Щоб дізнатися «скільки подій оброблено», «що
зараз падає» чи «наскільки виросла черга мертвих листів», доводилося лазити руками в
MySQL і Redis. Це не моніторинг — це археологія.

T3.1 — перша підзадача Milestone 3 (observability). Вона закриває FR-10 / AC-5: дати
**read-only** зріз стану системи трьома числами/списками:

1. **Лічильники за статусами** — скільки подій у кожному з `received / processing /
   processed / failed`.
2. **Останні падіння** — список нещодавно термінально провалених подій із причиною
   (`last_error`), щоб оператор бачив, *що саме* ламається.
3. **Розмір DLQ** — довжина `webhooks:dlq`, тобто скільки подій чекають на ручний розбір.

Ключове слово — **read-only**. T3.1 нічого не змінює: не popає чергу, не пере-чергує, не
оновлює рядки. Drain / re-queue DLQ — це наступна підзадача T3.2, і ADR 0016 свідомо
ставить тут паркан скоупу. Дашборд **тільки читає**.

Чому це важливо саме для системи вебхуків: ми працюємо в моделі *at-least-once* і самі
відповідаємо за подію після `202`. Якщо щось тихо сиплеться в DLQ, без видимого
дашборда оператор дізнається про це від розлюченого бізнесу, а не від графіка. DLQ без
вікна на нього — це той самий «сміттєвий бак», від якого ми тікали в T2.4. T3.1 робить
біль видимим.

## 2. Потік виконання

Спільний шлях вебхука не змінився. T3.1 додає **другий, окремий вхід** у той самий
фронт-контролер — не для провайдерів, а для оператора:

```
                     ┌─ провайдер ─────────────────────────────────┐
GitHub/Stripe/PayPal │ POST /webhooks/{provider} → Nginx → PHP-FPM │
                     │ verify → INSERT(received) → RPUSH → 202      │
                     └─────────────────────────────────────────────┘
                                       (без змін)

                     ┌─ оператор / liveness-проба ─────────────────┐
   GET /health  ────►│ Health::status() — БЕЗ БД, БЕЗ Redis → 200   │  ← проба ліврості
                     └─────────────────────────────────────────────┘

   GET /        ────► dispatch() матчить '/' ──► будує У ЦІЙ ГІЛЦІ:
                        EventRepository(Connection::fromConfig(...))   ← БД відкривається
                        Queue::fromConfig(...)                          ← Redis відкривається
                            │            ТІЛЬКИ ТУТ
                            ▼
                      DashboardController::handle()
                        ├─ EventRepository::countsByStatus()   → MySQL: GROUP BY status
                        ├─ EventRepository::recentFailures(20)  → MySQL: WHERE failed, LIMIT 20
                        └─ Queue::deadLetterSize()              → Redis: lLen webhooks:dlq
                            ▼
                      json_encode({counts, recent_failures, dlq_size})
                            ▼
                      незмінний render-блок index.php → Content-Type: application/json → 200
```

Дві деталі потоку, які варто засвоїти:

- **`GET /` тепер дашборд, `GET /health` — проба.** Раніше `/` віддавав health-JSON. ADR
  0016 (D2) їх розвів: health отримав власний шлях, бо
  `docker-compose.yml` документує «Dashboard: http://localhost/», і root має показувати
  дані оператору.
- **БД і Redis відкриваються тільки в гілці `/`.** Це дзеркало того, як гілка webhook-POST
  будує свої з'єднання лише після матчингу. `/health`, 404, 405 не відкривають **нічого**.

## 3. Чому саме так

Рішення в ADR 0016. Три головні.

**(D1) Тільки JSON-API, без серверного HTML.**
Дашборд віддає `application/json` з `{counts, recent_failures, dlq_size}`, а не зрендерену
HTML-сторінку. Чому це правильний дефолт саме тут:

- **Нуль змін у render-контракті фронт-контролера.** `index.php` *безумовно* ставить
  `Content-Type: application/json`, а `dispatch()` повертає трійку `[status, body, Allow]`,
  де `body` — уже закодований JSON. Дашборд лягає в цей самий канал так само, як кожен
  інший маршрут. HTML вимагав би розширити трійку четвертим слотом (content-type) і
  розгалужувати заголовок — структурна правка дбайливо мінімізованого entry point.
- **Нуль нової XSS-поверхні.** Серверний HTML означав би ручний `htmlspecialchars()` для
  `last_error` / `event_type` — а це рядки, які прийшли ззовні (провайдер міг покласти що
  завгодно в тип події, а `last_error` ми формуємо самі, але звичка небезпечна). JSON цієї
  поверхні просто не має: екранування лягає на споживача (браузер через `textContent` у
  майбутньому статичному фронті).
- **Найменша поверхня рев'ю.** Уся задача стиснулася до: два read-методи в
  `EventRepository` + один `Queue::deadLetterSize()` + крихітний контролер + одна гілка
  маршруту.

Відхилено: **серверний HTML (Option B)** — змушує міняти content-type і додає XSS-поверхню
заради трьох чисел. **JSON + статичний `index.html` (Option C)** — гарний наступний крок
(екранування на боці DOM, чистий поділ API/представлення), але це другий артефакт і
питання віддачі статики через Nginx — scope-creep для T3.1. Свідомо відкладено, не забуто.

**(D2) Дашборд на `GET /`, health переїхав на `GET /health` (без залежностей).**
Найважливіший принцип нотатки: **проба ліврості мусить бути dependency-free**. `/health`
не відкриває ні БД, ні Redis — викликає лише `Health::status()`. Чому це інваріант, а не
дрібниця: liveness-проба відповідає на питання «чи живий *процес*?», а не «чи здорова вся
інфраструктура?». Якщо health сходить у БД і БД лежить — проба впаде, оркестратор вирішить,
що **процес** мертвий, і **рестартне здоровий контейнер**. Це перетворює збій залежності
на каскадний рестарт-шторм. Тому health навмисно нічого не торкає. (Готовність —
*readiness* — інша річ; її можна робити залежною, але це окрема проба, не T3.1.)

Відхилено: дашборд на `/dashboard` зі здоров'ям на `/` — суперечить задокументованому
`http://localhost/`; health-at-root і слабша конвенція, ніж health-at-`/health`. Контент-
негоціація на `/` за `Accept`/`User-Agent` — крихка й змусила б health-гілку *іноді*
відкривати БД залежно від заголовка, ламаючи сам інваріант. Відхилено.

**(D3) Три read-аксесори, кожен у класі, що володіє своїм сховищем.**
Це продовження правила single-ownership з попередніх ADR: увесь SQL по `webhook_events`
живе в `EventRepository`, усі ключі Redis — у `Queue`. Жоден `SELECT` чи `webhooks:dlq` не
протікає в контролер.

- **`EventRepository::countsByStatus()`** — один згрупований запит (`GROUP BY status`,
  обслуговується `idx_status`), один round-trip на всі чотири кошики. Контролер
  **нормалізує** результат: усі чотири enum-ключі присутні й дефолтяться в `0`. Тобто
  статус, у якому ще немає рядків, віддасть `0`, а не зникне з відповіді — **стабільний
  контракт JSON** для майбутнього фронту.
- **`EventRepository::recentFailures(int $limit)`** — `WHERE status='failed'` (по
  `idx_status`), `ORDER BY updated_at DESC` (бо `updated_at` має `ON UPDATE
  CURRENT_TIMESTAMP` — це момент, коли рядок став термінальним, тож «найсвіжіші падіння
  згори» — правильне сортування для оператора), `LIMIT :limit`. **Колонка `payload`
  НІКОЛИ не вибирається** (NFR-1) — список колонок прибитий вручну до безпечних метаданих.
- **`Queue::deadLetterSize()`** — `(int) lLen(webhooks:dlq)`, точне дзеркало `size()`. Лише
  читання, без pop/drain (то T3.2).

Тут — **дві пастки рівня middle**, які варто запам'ятати окремо:

- **`SELECT` зі списком колонок, а не `SELECT *`.** `payload` — це LONGTEXT із сирими
  підписаними байтами. `SELECT *` (а) тягнув би ці байти по дроту даремно і (б) ризикував
  би **протекти payload у відповідь** — рівно та діра NFR-1, від якої ми захищаємось.
  Прибитий список колонок робить витік payload **структурно неможливим**, а не «ми
  обіцяємо не забути».
- **`LIMIT :limit` треба біндити як `PDO::PARAM_INT`.** Бо `Connection` працює з
  `ATTR_EMULATE_PREPARES => false` — тобто справжні prepared statements. MySQL відкине
  *рядково*-зв'язаний параметр у `LIMIT` (синтаксична помилка → 500). При увімкненій
  емуляції PDO підставив би значення сам і це б «зійшло з рук» — тому пастка тиха й
  спливає лише на реальних prepared statements.

## 4. Слабкі місця та технічний борг

- **Зріз НЕ атомарний між сховищами.** `counts` читаються з MySQL, `dlq_size` — з Redis,
  у двох окремих викликах. Між ними job може переїхати (наприклад, з `processing` у DLQ).
  Тобто два числа лише *eventually consistent* одне з одним. Для **моніторингового** зрізу
  це прийнятно — крос-сховищна атомарність тут не потрібна, і кожне число коректне на
  момент *свого* читання. Але якщо колись робити з цих чисел алерт-логіку «processing == 0
  AND dlq > 0», треба пам'ятати, що це знімок, а не транзакція.
- **Немає стилізованої сторінки для людини.** Root віддає сирий JSON. Браузер його
  показує читабельно, але це не дашборд із таблицями. Рекомендований наступний крок —
  статичний `index.html`, що `fetch()`ить цей JSON (Option C). Відкладено свідомо.
- **`recent_failures` обмежений LIMIT 20 без пагінації.** Якщо хвиля падінь >20, дашборд
  покаже лише верхівку. Для «глянути поточний сплеск» вистачає; для розслідування глибше —
  потрібен `?limit=` (валідований/затиснутий) або пагінація. Поки немає — це межа видимості.
- **`dlq_size` — лише число, без вмісту.** Оператор бачить «їх 47», але не *що це за
  події*. Перегляд/розбір конвертів DLQ — T3.2. Поки розмір росте, а причини невидимі —
  це сигнал, але не діагноз.
- **Ні auth, ні кешування.** Дашборд — внутрішнє вікно за локальною Docker-мережею; spec
  Non-goals виключають auth. Але **перед будь-яким не-локальним виставленням** це треба
  переглянути: зараз будь-хто з мережним доступом бачить `last_error` усіх падінь.
- **Таймстемпи без таймзони (MINOR з рев'ю, відкладено).** `created_at`/`updated_at`
  віддаються як є, без маркера TZ. Споживач може неправильно їх інтерпретувати. Свідомо
  відкладено до майбутнього статичного фронту, який формуватиме представлення.
- **Помилки їдуть на загальному Throwable-backstop.** Дашборд **не має власного error-
  шляху**: якщо PDO не приконнектиться чи Redis ляже, виняток спливає до
  `try/catch (\Throwable)` у `index.php`, який логує трейс і віддає `500 {"status":"error"}`
  без витоку. Це *перевага* (нуль нової поверхні витоку), але й **залежність**: дашборд
  правильний рівно настільки, наскільки backstop не протікає. Не винаходь локальний
  error-рендеринг — він би міг злити повідомлення/трейс/секрет.

## 5. Патерни, які варто запам'ятати

- **Single ownership of SQL & Redis keys.** SQL по таблиці живе в репозиторії, ключ Redis —
  у `Queue`. Контролер не знає рядка `webhooks:dlq` чи тексту `SELECT`. Той самий принцип
  тримали ADR 0005/0012/0014. Це робить зміну схеми/ключа **однією правкою в одному місці**.
- **Dependency-free liveness probe.** Проба «чи живий процес» не має торкатися залежностей,
  інакше збій залежності → каскадний рестарт здорового процесу. Розрізняй *liveness* (не
  залежна) і *readiness* (може бути залежною) — це Kubernetes-словник, але принцип
  універсальний.
- **Column-pinned SELECT замість `SELECT *` (least-disclosure).** Не тягни й не віддавай
  те, що не потрібно — особливо чутливі колонки (`payload`). Витік стає структурно
  неможливим, а не питанням дисципліни. Це форма принципу найменшого розкриття.
- **PARAM_INT для `LIMIT` під справжніми prepared statements.** Загальний урок: з
  `ATTR_EMULATE_PREPARES => false` типи bind-параметрів мають значення; числові метадані
  запиту (LIMIT/OFFSET) бінди як `PARAM_INT`. Емуляція ховає цю пастку — справжні
  prepared її показують.
- **Stable JSON contract (нормалізована форма відповіді).** Усі чотири ключі `counts`
  завжди присутні (дефолт 0); `recent_failures` ніколи не містить `payload`. Споживач
  (фронт/алерт) може покладатися на форму, не перевіряючи наявність полів. Той самий
  принцип — у будь-якому стабільному API-контракті.
- **Non-atomic cross-store snapshot.** Коли читаєш з двох сховищ в одному запиті без
  спільної транзакції — це знімок, не транзакція. Усвідом і прийми (для моніторингу — ок)
  або уникай (для рішень, де потрібна узгодженість).
- **Read/write concern separation.** Аксесори читання додані поряд із наявними write-
  методами того ж власника, не в новий «сервіс читання». Просто, без зайвої абстракції —
  рівно стиль цього проєкту.

## Покрокова хроніка

Нижче — кожен крок, який я (головний агент) реально зробив, із фактичними командами та їх
фактичним виводом, і поясненням «навіщо».

**Крок 1 — читання контексту.**
Прочитав ADR 0016 (форма, маршрути, методи, пастки), специфікацію (FR-10, AC-5, NFR-1),
файл задач (паркан скоупу T3.1 vs T3.2) і весь релевантний код: `index.php` (render-
контракт, Throwable-backstop, інваріант «БД лише в матчленій гілці»), `EventRepository.php`
(наявні write-методи, де живе SQL), `Queue.php` (`size()`, константа `DLQ`), `Health.php`,
`Connection.php` (`ATTR_EMULATE_PREPARES => false`), міграцію 0001 (`idx_status`,
`ON UPDATE CURRENT_TIMESTAMP` на `updated_at`).
*Навіщо:* T3.1 — адитивна зміна. Треба точно знати наявні дзеркала (`size()` → `deadLetterSize()`),
щоб вписатися, а не винаходити, і не зачепити незмінні гілки фронт-контролера.

**Крок 2 — реалізація 4 правок.**
- `EventRepository.php` — `countsByStatus()` (`GROUP BY status`) + `recentFailures(int $limit)`
  (прибитий список колонок БЕЗ `payload`, `LIMIT :limit` як `PARAM_INT`).
- `Queue.php` — `deadLetterSize()`, дзеркало `size()` (`lLen(self::DLQ)`).
- `DashboardController.php` — **НОВИЙ**: `final`, чистий, бере `EventRepository` + `Queue`,
  повертає `json_encode(['counts','recent_failures','dlq_size'], JSON_THROW_ON_ERROR)`;
  константа `RECENT_FAILURES_LIMIT = 20`; нормалізує counts до всіх чотирьох ключів.
- `public/index.php` — маршрут `/health` (без БД/Redis) + маршрут `/` (будує
  `EventRepository`+`Queue`+`DashboardController` **тільки** в матчленій гілці); оновлені
  докблоки маршрутизації.
*Навіщо саме так:* див. розділ 3 — це втілення D1/D2/D3 з ADR 0016.

**Крок 3 — lint усіх чотирьох файлів у контейнері php.**
```
$ docker compose exec -T php php -l /var/www/html/src/Repository/EventRepository.php
$ docker compose exec -T php php -l /var/www/html/src/Queue/Queue.php
$ docker compose exec -T php php -l /var/www/html/src/Http/DashboardController.php
$ docker compose exec -T php php -l /var/www/html/public/index.php
=> "No syntax errors detected" для кожного з 4 файлів
```
*Навіщо:* `php -l` — дешева перша лінія захисту від синтаксису до інтеграційної перевірки.

**Крок 4 — підняв nginx (був Exited).**
```
$ docker compose up -d nginx
=> container Started; 0.0.0.0:80->80/tcp
```
*Навіщо:* маршрути дашборда перевіряються лише через живий HTTP-фронт; контейнер nginx
був зупинений, без нього `curl` не пройде.

**Крок 5 — перевірка маршрутів curl-ом (порожня система).**
```
$ curl -s -w "\nHTTP %{http_code}\n" http://localhost/health
{"status":"ok","service":"webhook-handler"}
HTTP 200

$ curl -s http://localhost/
{"counts":{"received":0,"processing":0,"processed":0,"failed":0},"recent_failures":[],"dlq_size":0}
HTTP 200

$ curl -s -i -X POST http://localhost/
HTTP/1.1 405 Method Not Allowed
Content-Type: application/json

$ curl -s http://localhost/webhooks
{"status":"rejected"}
HTTP 400
```
*Навіщо й інтерпретація:*
- `/health` віддав health-JSON, **не торкнувшись БД/Redis** — інваріант ліврості цілий.
- `/` на порожній системі повернув **усі чотири ключі counts по 0** (нормалізація працює),
  порожній `recent_failures`, `dlq_size:0`.
- `POST /` → `405 Allow: GET` із незмінним `Content-Type: application/json` — render-
  контракт не зачеплено.
- `/webhooks` → `400 {"status":"rejected"}` — наявна гілка не зламалася (контроль регресії).

**Крок 6 — засів різноманітних даних і запис у DLQ.**
Засіяв 5 рядків (по одному в кожен статус, два `failed`) через db-контейнер (SQL — у
розділі «Запити до бази даних»), і поклав конверт у DLQ через Redis:
```
$ docker compose exec -T redis redis-cli RPUSH webhooks:dlq '{"event_id":"t3_1_fail_a","provider":"paypal","attempt":3}'
1
$ docker compose exec -T redis redis-cli LLEN webhooks:dlq
1
```
*Навіщо:* порожня система не доводить *поведінки*. Треба побачити реальні лічильники, що
у `recent_failures` справді два об'єкти **без `payload`**, і що `dlq_size` читає Redis.
(Команди `RPUSH`/`LLEN` — це **Redis, не SQL**; SQL-засів — нижче.)

**Крок 7 — повторний curl `/` (pretty-print) із даними.**
```
$ curl -s http://localhost/ | jq .
{
  "counts": { "received": 1, "processing": 1, "processed": 1, "failed": 2 },
  "recent_failures": [
    { "id": ..., "provider": "github", "event_type": "workflow_run",
      "attempts": 3, "last_error": "permanent: unknown event type",
      "created_at": "...", "updated_at": "..." },
    { "id": ..., "provider": "paypal", "event_type": "PAYMENT.SALE.DENIED",
      "attempts": 3, "last_error": "handler exhausted: downstream 500",
      "created_at": "...", "updated_at": "..." }
  ],
  "dlq_size": 1
}
```
*Навіщо й інтерпретація:* counts збіглися із засівом (`received:1, processing:1,
processed:1, failed:2`); `recent_failures` має **рівно два** об'єкти, кожен із
`id/provider/event_type/attempts/last_error/created_at/updated_at` і **БЕЗ поля `payload`**
— це підтверджує AC-5 + NFR-1 разом; `dlq_size:1` читає `webhooks:dlq`. Тобто всі три
джерела (GROUP BY, failed-список, lLen) працюють на живих даних.

**Крок 8 — прибирання за собою.**
```
$ # DELETE засіяних рядків (SQL нижче) → remaining_rows 0
$ docker compose exec -T redis redis-cli LREM webhooks:dlq 1 '{"event_id":"t3_1_fail_a","provider":"paypal","attempt":3}'
1
$ docker compose exec -T redis redis-cli LLEN webhooks:dlq
0
$ curl -s http://localhost/
{"counts":{"received":0,"processing":0,"processed":0,"failed":0},"recent_failures":[],"dlq_size":0}
```
*Навіщо:* верифікація не має лишати сміття. `LREM`/`LLEN` — знову Redis, не SQL. Фінальний
curl довів, що система повернулась у нульовий стан — і заразом ще раз підтвердив
нормалізацію counts.

## Запити до бази даних

### SQL, який виконує сам КОД ФІЧІ (нові методи дашборда)

```sql
-- EventRepository::countsByStatus()
-- один round-trip; обслуговується idx_status; контролер нормалізує
-- результат до всіх чотирьох enum-ключів (відсутній статус → 0).
SELECT status, COUNT(*) AS total
FROM webhook_events
GROUP BY status;
```

```sql
-- EventRepository::recentFailures($limit)
-- WHERE status='failed' по idx_status; сортування за updated_at DESC
-- (момент переходу в термінальний стан); :limit БІНДИТЬСЯ як PDO::PARAM_INT
-- (бо ATTR_EMULATE_PREPARES => false). КОЛОНКА payload НІКОЛИ не вибирається (NFR-1).
SELECT id, provider, event_type, attempts, last_error, created_at, updated_at
FROM webhook_events
WHERE status = 'failed'
ORDER BY updated_at DESC
LIMIT :limit;
```

### Redis-команди (НЕ SQL — для повноти аудиту)

Ці команди працювали з `webhooks:dlq` у Redis і **не є SQL**:

```
RPUSH webhooks:dlq '{"event_id":"t3_1_fail_a","provider":"paypal","attempt":3}'   -- засів DLQ
LLEN  webhooks:dlq                                                                 -- assert розміру
LREM  webhooks:dlq 1 '{"event_id":"t3_1_fail_a","provider":"paypal","attempt":3}' -- cleanup
LLEN  webhooks:dlq                                                                 -- assert 0 після очистки
```

Сам метод `Queue::deadLetterSize()`, який читає дашборд, виконує читаючу Redis-команду
`LLEN webhooks:dlq` — також **не SQL**.

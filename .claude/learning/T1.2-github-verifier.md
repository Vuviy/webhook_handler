# Навчальна нотатка: T1.2 — GitHub-верифікатор вебхуків (HMAC-SHA256)

> Мова: українська. Аудиторія: junior → middle PHP.

## 1. Проблема простими словами

GitHub надсилає нам POST-запити («вебхуки»), коли в репозиторії щось стається
(push, pull request тощо). Будь-хто в інтернеті може постукати на наш ендпоінт і
прикинутися GitHub. Тому перш ніж записати подію в базу й поставити в чергу, ми
маємо **довести, що запит справді від GitHub і його не змінили в дорозі**.

GitHub підписує точні байти тіла запиту секретом, спільним лише між ним і нами
(HMAC-SHA256), і кладе підпис у заголовок `X-Hub-Signature-256`. Ми перераховуємо
той самий HMAC своїм секретом і порівнюємо. Збіглося — запит автентичний; ні —
відкидаємо (401), нічого не записуючи й не ставлячи в чергу.

T1.2 — це **лише GitHub-верифікатор**: `final class GitHubVerifier`, що реалізує
спільний контракт `ProviderVerifier` із T1.1. Stripe (T1.3), PayPal (T1.4),
контролер і роутинг (T1.5/T1.6) — окремі підзадачі. Тут — один провайдер, чистий
PHP, без доступу до БД чи мережі.

## 2. Потік виконання

Де саме в загальному маршруті вебхука живе цей шматок (виділено наш блок):

```
GitHub POST /webhooks/github
        │  тіло = сирий JSON, заголовок X-Hub-Signature-256: sha256=<hex>
        ▼
   Nginx ──► PHP-FPM (контролер прийому, T1.5/T1.6 — ще попереду)
        │  читає СИРЕ тіло з php://input
        ▼
   ┌─────────────── GitHubVerifier::verify($rawBody, $headers) — ЦЕ T1.2 ───────────────┐
   │  1. порожнє тіло?              → invalid('empty request body')                       │
   │  2. немає X-Hub-Signature-256? → invalid('missing X-Hub-Signature-256 header')       │
   │  3. computed = 'sha256=' . hash_hmac('sha256', $rawBody, $secret)                    │
   │     hash_equals(computed, provided) хибне? → invalid('signature mismatch')           │
   │  4. eventId  = trim(X-GitHub-Delivery)  (GUID, ключ дедуплікації)                    │
   │     eventType = trim(X-GitHub-Event)    (напр. "push")                               │
   │     порожні?                   → invalid('missing X-GitHub-Delivery or ... header')  │
   │  5. усе гаразд                 → valid(eventId, eventType)                           │
   └────────────────────────────────────────────────────────────────────────────────────┘
        │  valid → контролер: INSERT event (status=received) → RPUSH у Redis → 202
        │  invalid → 401, нічого не записуємо, нічого не ставимо в чергу (fail closed)
        ▼
   Redis queue ──► Worker ──► обробник → успіх / retry (backoff 2^n) / DLQ
```

Конструювання верифікатора (`fromSecrets`) відбувається ще **до** запиту, на старті:
немає секрета → `VerificationException` → 500. Тобто крок «де взяти секрет» винесений
з гарячого шляху `verify()`.

## 3. Чому саме так

Це серце нотатки — пояснюємо рішення, а не переказуємо рядки.

- **HMAC рахуємо над СИРИМИ байтами, тіло не парсимо.** Підпис прив'язаний до точних
  байтів із `php://input`. Якщо зробити `json_decode` і потім знову `json_encode`,
  байти зміняться (інший порядок ключів, пробіли, екранування Unicode) — і HMAC не
  збіжиться, хоча запит легітимний. Тому для GitHub тіло — це **непрозорі підписані
  байти**, ми його взагалі не розбираємо.

- **Префікс `sha256=` входить у порівняння.** GitHub шле підпис як `sha256=<hex>`. Ми
  додаємо той самий префікс до свого обчисленого дайджесту й порівнюємо рядки цілком.
  Так один `hash_equals()` покриває і тег алгоритму, і сам дайджест — не треба окремо
  «відрізати префікс».

- **`hash_equals()`, а не `==`/`===`.** Наївне порівняння рядків виходить на першому ж
  розбіжному байті. Різниця в часі відповіді (мікросекунди) дає зловмиснику зворотний
  зв'язок: за багато спроб можна підбирати підпис побайтово (timing attack).
  `hash_equals()` порівнює за **сталий час** незалежно від того, де саме розбіжність.
  Це і конвенція проєкту, і вимога безпеки (NFR-1). `hash_equals` коректно й безпечно
  обробляє і **різні довжини** рядків, тому окрема перевірка довжини не потрібна.

- **id і type для GitHub беремо із ЗАГОЛОВКІВ.** У GitHub ключ дедуплікації
  `X-GitHub-Delivery` (GUID кожної доставки) і тип `X-GitHub-Event` (напр. "push")
  лежать у заголовках, а **не** в тілі. У Stripe/PayPal навпаки — id у тілі. Саме тому
  «звідки витягти id/type» — відповідальність кожного конкретного верифікатора за
  спільним контрактом. `event_id` потрібен для дедуплікації (FR-11,
  `UNIQUE(provider, event_id)`), `event_type` — для NOT NULL колонки в таблиці подій.

- **Валідний підпис, але немає delivery-заголовків → `invalid()`, не `error()` і не
  виняток.** Перевірка підпису пройшла, та без `X-GitHub-Delivery` у нас немає ключа
  дедуплікації — а справжня доставка GitHub завжди має ці заголовки. Тому **fail
  closed**: повертаємо 401 і нічого не ставимо в чергу, а не вигадуємо собі id.
  `error()` ми лишаємо для випадку «не змогли перевірити взагалі» (віддалена аварія) —
  для локального HMAC такого не буває.

- **Секрет резолвиться в конструкторі (`fromSecrets`).** Відсутній секрет — це помилка
  **конфігурації/деплою** → 500, а не «поганий підпис» → 401. Якби ми повернули 401,
  то збрехали б легітимному GitHub «у тебе неправильний підпис», тоді як насправді
  МИ не налаштовані. Сконструйований верифікатор гарантовано має секрет, тож `verify()`
  не перевіряє його щоразу — гарячий шлях чистіший (fail-fast у фабриці).

- **Legacy `X-Hub-Signature` (SHA-1) свідомо ігноруємо.** SHA-1 зламаний; новий код
  його не приймає й покладається лише на SHA-256.

- **`trim()` витягнутих id/type.** Захист від проксі, що може віддати присутній, але
  порожній заголовок. Без `trim()` пробільний `event_id` дійшов би до
  `VerificationResult::valid()`, який кидає `\InvalidArgumentException` — тобто
  внутрішня помилка замість акуратного 401.

**ADR не писали** — і це свідоме рішення архітектора: T1.2 — пряме застосування
контракту з T1.1 плюс skill `webhook-security`, без реальної архітектурної розвилки.
Папка `.claude/decisions/` для цієї підзадачі нового запису не отримала.

## 4. Слабкі місця та технічний борг

- **Дедуплікація тут НЕ виконується.** Верифікатор лише дістає `event_id`; реальний
  захист від повторів — це `UNIQUE(provider, event_id)` у БД + ідемпотентний обробник
  (доставка at-least-once: GitHub повторить, якщо ми не відповіли швидко 2xx). Якщо
  далі по конвеєру забути про дедуп — одна подія обробиться двічі.

- **Один секрет на провайдера.** `fromSecrets` бере єдиний `githubSecret()`. Під час
  **ротації секрета** (старий ще активний, новий уже виданий) ми не вміємо приймати
  обидва — на вікні ротації частина легітимних вебхуків впаде в 401. Зрілий варіант —
  приймати список секретів і вважати підпис валідним, якщо збігся хоч з одним.

- **Розмір тіла не обмежений на рівні верифікатора.** Дуже велике тіло — це і пам'ять,
  і час `hash_hmac`. Ліміт мають накласти Nginx/контролер раніше; верифікатор на це
  не розрахований.

- **Немає захисту від replay за часом.** Валідний, але старий перехоплений запит з
  правильним підписом пройде перевірку. GitHub не дає timestamp у схемі підпису (на
  відміну від Stripe), тож єдиний бар'єр проти повтору — дедуп за `event_id`.

- **Повідомлення `reason` — лише для логів.** Воно не має витікати клієнту дослівно,
  інакше підказує атакувальнику, на якому саме кроці він спіткнувся.

## 5. Патерни, які варто запам'ятати

- **Timing-safe comparison (порівняння за сталий час)** — `hash_equals()`. Будь-де, де
  порівнюються секрети/підписи: токени API, CSRF-токени, скидання пароля.
- **HMAC автентифікація повідомлення** — спільний секрет підтверджує і
  автентичність, і цілісність. Той самий принцип у JWT (HS256), у підписаних URL, у
  AWS SigV4.
- **Fail closed** — при сумніві відмовляй, а не пропускай. Базовий принцип безпеки:
  дефолт — «заборонено».
- **Verify over raw bytes** — підпис рахуємо до парсингу/нормалізації. Це поширене
  правило для всіх вебхук-провайдерів; ламається саме на «json_decode → json_encode».
- **Fail-fast configuration / Guard clause у конструкторі** — невалідна конфігурація
  падає на старті, а не під час обробки запиту. Сконструйований об'єкт завжди валідний.
- **Idempotency key** — `event_id` (тут `X-GitHub-Delivery`) як ключ дедуплікації при
  at-least-once доставці. Зустрічається в платіжних API, чергах повідомлень (Kafka,
  SQS), Stripe `Idempotency-Key`.

## Відхилені альтернативи (компроміси)

- **Парсити `event_id` з ТІЛА через `json_decode` для GitHub** — зайве й ризиковане:
  id уже є в заголовку, а тіло не варто чіпати без потреби (та й парсинг до перевірки
  підпису — потенційний вектор атаки).
- **Окрема перевірка префікса `sha256=` / довжини hex перед `hash_equals`** — нічого
  не дає: `hash_equals` безпечно обробляє нерівні довжини й неформатні рядки, зайва
  гілка лише шум.
- **Брати `?string` секрет у конструктор і перевіряти в `verify()` щоразу** — каламутить
  гарячий шлях і розмиває семантику «нема секрету = 500». Fail-fast у фабриці робить це
  структурно: якщо об'єкт є — секрет є.

   рішення для всього проєкту краще ухвалити окремо, а не вводити точково тут.
2. Порожній заголовок підпису дає reason «missing» (а не «empty») — семантично
   еквівалентно для клієнта (обидва → 401), а reason бачать лише логи.
3. Об'єднане повідомлення про відсутній delivery/event — обидва заголовки обов'язкові,
   розрізняти, якого саме бракує, користі не дає.

**3) Реалізація.** Створив файл `app/src/Verification/GitHubVerifier.php` (інструмент
Write) — `final class GitHubVerifier implements ProviderVerifier`.

**4) Лінт + повний прогін усіх гілок у контейнері `php`** (на хості PHP немає, тому все
через контейнер):

Команда (спрощено): `docker compose exec -T php sh -lc 'cd /var/www/html && php -l
src/Verification/GitHubVerifier.php && php -r "..."'` — у вбудованому скрипті створив
верифікатор із секретом `"mysecret"`, тілом `{"zen":"Keep it logically awesome."}`,
обчислив правильний підпис через `hash_hmac` і прогнав усі сценарії.

Фактичний вивід:

```
No syntax errors detected in src/Verification/GitHubVerifier.php
valid sig: outcome=valid id=guid-123 type=push
tampered: invalid reason=signature mismatch
no sig header: missing X-Hub-Signature-256 header
empty body: empty request body
valid sig but no delivery: outcome=invalid reason=missing X-GitHub-Delivery or X-GitHub-Event header
whitespace event: invalid
provider: github
missing secret throws: Webhook secret for provider "github" is not configured.
fromSecrets ok: valid
```

Що цей прогін доводить:

- `php -l` — синтаксис чистий.
- **valid sig** — правильний підпис → `valid`, з коректно витягнутими `id=guid-123` і
  `type=push` із заголовків.
- **tampered** — змінене тіло/підпис → `invalid(signature mismatch)`.
- **no sig header** — немає `X-Hub-Signature-256` → акуратний `invalid`.
- **empty body** — порожнє тіло → `invalid` ще до обчислення HMAC.
- **valid sig but no delivery** — підпис валідний, але немає delivery-заголовків →
  `invalid` (fail closed), а НЕ виняток і не `error`.
- **whitespace event** — пробільний `X-GitHub-Event` після `trim()` → `invalid` (не
  доходить до `valid()`, який кинув би `\InvalidArgumentException`).
- **provider()** = `github`.
- **missing secret** — `fromSecrets` без секрета кидає `VerificationException`
  («…is not configured.») → це шлях на 500, а не 401.
- **fromSecrets ok** — з наявним секретом конструюється й верифікує штатно.

**5) Рев'ю (sub-agent).** Запустив `code-reviewer` → «Approve with nits»; 3 NIT
свідомо відхилив (див. розділ «Рев'ю»).

## Запити до бази даних

**Жодного SQL-запиту до БД у цій підзадачі НЕ виконувалося.** `GitHubVerifier` — це
чистий PHP-верифікатор без доступу до даних: він рахує HMAC і читає заголовки, але сам
нічого не читає/не пише в MySQL. Колонки `event_id` / `event_type` і обмеження
`UNIQUE(provider, event_id)` я лише **прочитав** із файлу міграції
`app/migrations/0001_create_webhook_events.sql`, щоб звірити контракт, — без виконання
запитів до бази.

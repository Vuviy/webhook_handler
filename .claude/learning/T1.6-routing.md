# Навчальна нотатка: T1.6 — Маршрутизація `/webhooks/{provider}` + обробка методу / `401` / `400`

> Мова: українська. Аудиторія: junior → middle PHP.

## 1. Проблема простими словами

У T1.5 ми зробили **чистий** контролер `App\Http\IngestionController::handle(...)`:
він не торкається жодної суперглобальної змінної (`$_SERVER`, `$_POST`), не читає
`php://input`, а отримує `provider`, сире тіло й заголовки **аргументами**. Це
ідеально для тестів, але такий контролер ні до чого не підключений — у нього немає
«дверей» з мережі.

T1.6 — це ті самі двері: **фронт-контролер** (`app/public/index.php`), у який Nginx
зливає кожен запит. Його робота:

1. зчитати сире тіло запиту й зібрати «вигляд» запиту (`ServerRequest`);
2. за парою `(шлях × метод)` вирішити, **куди** цей запит веде;
3. для справжнього вебхука — викликати `IngestionController` і віддати його відповідь;
4. для всього іншого — повернути правильний HTTP-статус (`400` / `404` / `405`);
5. гарантувати, що **жоден** `Throwable` не витече в тіло відповіді (NFR-1).

Чому це важливо саме для системи вебхуків? Провайдери (GitHub, Stripe, PayPal)
звертаються до нас машинно. Вони не «здогадуються» — вони реагують на **код статусу**.
Неправильний статус на неіснуючому шляху, або 500 зі стек-трейсом у тілі, або
відкриття зʼєднання з БД на кожен health-check — усе це або зламає інтеграцію, або
дасть атакувальнику підказку, або покладе систему під навантаженням. Маршрутизація —
це не «if-и заради краси», це місце, де ми домовляємось із зовнішнім світом мовою
HTTP.

## 2. Потік виконання

Як HTTP-запит проходить систему **після** цієї зміни:

```
provider POST /webhooks/{provider}
        │
        ▼
   Nginx  (document root → public/, try_files … /index.php)
        │   нормалізує // у шляху, віддає все у фронт-контролер
        ▼
   index.php (фронт-контролер)
        │  1. favicon.ico? → одразу return (не маршрутизуємо)
        │  2. $rawBody = file_get_contents('php://input')  // "0" зберігаємо!
        │  3. $request = ServerRequest::fromGlobals($_SERVER, $rawBody)
        │        └─ відновлює заголовки з HTTP_* (getallheaders() недоступний)
        │  4. try { dispatch($request, $config) } catch (\Throwable) { 500 }
        ▼
   dispatch()  — маршрут за (шлях × метод):
        ├─ GET  /                    → 200 health JSON
        ├─ *    /                    → 405, Allow: GET
        ├─ *    /webhooks|/webhooks/ → 400 (немає сегмента провайдера)
        ├─ POST /webhooks/{provider} → будуємо контролер ТУТ ↓
        ├─ *    /webhooks/{provider} → 405, Allow: POST
        └─ *    решта                → 404
        ▼
   (тільки на гілці POST /webhooks/{provider})
   new IngestionController(VerifierRegistry, EventRepository(Connection), Queue)
        │   ← саме тут вперше відкриваються сокети MySQL і Redis
        ▼
   $controller->handle(strtolower(provider), rawBody, headers)
        │  verify signature (timing-safe) → INSERT (received) → RPUSH у Redis
        ▼
   202 Accepted  (або 401 / 404 / 502 / 500 від самого контролера)
```

Далі по ланцюжку йде вже частина T2.x: `Redis queue → worker → handler → success /
retry / backoff → DLQ`. У T1.6 ми відповідаємо лише за **синхронний фронт** — до
`202` включно. Але важливо бачити, що T1.6 — це та сама «швидка квитанція»: ми
підтверджуємо прийом і відпускаємо провайдера, не роблячи важкої роботи в HTTP-запиті.

## 3. Чому саме так

ADR: `.claude/decisions/0010-routing-front-controller-and-backstop.md` (Option C).

**3.1. Окремий обʼєкт-значення `ServerRequest` замість парсингу прямо в `index.php`.**
`index.php` — це скрипт-точка-входу: він `echo`-ить і пише в глобальний стан, тож
його **неможливо** покрити юніт-тестом. А відновлення заголовків — це саме та логіка,
де легко помилитися: `HTTP_X_HUB_SIGNATURE_256` треба перетворити на
`x-hub-signature-256` (зняти префікс `HTTP_`, `_`→`-`, у нижній регістр). Це
безпекочутливий код — від нього залежить, чи знайде верифікатор підпис. Тому він
живе в `final readonly class ServerRequest` з фабрикою `fromGlobals(array $server,
string $rawBody)`, якій у тесті можна передати **фейковий** `$server` — без реального
запиту. Принцип: *логіку, яка може бути неправильною, виносимо туди, де її можна
перевірити*. Відхилено **Option A** (усе інлайном) саме тому, що це повторило б
помилку «логіка там, де її не дістати тестом».

**3.2. Чому не повноцінний `Router`.** Маршрутів усього два сімейства. Клас `Router`
з таблицею маршрутів — це абстракція з єдиною реалізацією, тобто
оверінжиніринг (відхилений **Option B**). Правило конвенцій: не вводити абстракцій
заради абстракцій. Коли зʼявиться третій тип маршруту — тоді й буде привід для
маленького роутера, не раніше.

**3.3. Розділення `400` і `404` — і чому їх не можна злити.** Це тонкий, але
«мідловий» момент HTTP-семантики:
- `400 Bad Request` → `/webhooks` чи `/webhooks/` **без сегмента провайдера**. URL
  структурно зламаний: він навіть не вказує, до якого контролера звертатись. Це
  провина **клієнта**, і вирішує її **маршрутизатор**.
- `404 Not Found` → `/webhooks/bitbucket`: URL коректний, він **називає** провайдера,
  просто такого провайдера ми не підтримуємо. Це вже робота **контролера** (як у
  T1.5). Маршрутизатор не префільтрує провайдерів — він довіряє це контролеру.

Якби ми злили їх в один статус, ми б брехали клієнту про природу помилки: «ти
сформував поганий URL» і «ти попросив невідомий ресурс» — це різні діагнози.

**3.4. Ліниве (lazy) відкриття зʼєднань, а не fail-fast на старті.** Найважливіше
архітектурне рішення тут: `IngestionController` (а отже `Connection::fromConfig` і
`Queue::fromConfig`, які **відкривають сокети** MySQL і Redis) будується **лише
всередині гілки `POST /webhooks/{provider}`**. Наслідок: health-check, усі `404`,
`405` і `400` **не відкривають жодного зʼєднання**. Падіння Redis **не повинно**
ламати health-check — інакше моніторинг показав би «все мертве», коли насправді
лежить лише черга, а прийом ще міг би (частково) працювати. Це свідомий вибір *lazy
connection* проти *fail-fast at boot*: ми платимо зʼєднанням рівно тоді, коли воно
справді потрібне для роботи.

**3.5. Backstop проти витоку (NFR-1).** Весь `dispatch()` загорнутий в один
`try/catch (\Throwable)`. Будь-який неперехоплений виняток стає чистою `500` з тілом-
константою `{"status":"error"}` — **ніколи** `$e->getMessage()`, ніколи стек-трейс,
ніколи payload. Повна деталізація йде лише в `error_log()`. Чому `\Throwable`, а не
`\Exception`? Бо фабрики зʼєднань і `json_encode(..., JSON_THROW_ON_ERROR)` можуть
кинути й `\Error`/`\JsonException` — ловимо найширше, щоб нічого не просочилось.

## 4. Слабкі місця та технічний борг

- **Match маршруту — у нетестованому файлі.** Самі `if`/regex живуть в `index.php`,
  який тестом не дістати. Для двох маршрутів це прийнятно, але третій тип маршруту —
  це сигнал винести рішення в тестований шар (маленький роутер або метод VO).
- **`error_log((string) $e)` пише повний трейс.** Рев'ю (MINOR) слушно позначило це
  як латентний ризик: трейс безпечний для **тіла** відповіді (туди він не йде), але
  якщо колись хтось покладе payload чи секрет у *повідомлення винятку*, воно осяде в
  лог-файлі. Свідоме рішення: трейс лишили (саме він робить 500 від падіння БД/Redis
  діагностованою) і додали **guard-коментар** на тому рядку — попередження майбутньому
  коду ніколи не класти payload/секрет у текст винятку. Сьогодні жоден виняток на
  шляху build/handle цього не робить — це перевірено.
- **Регістр і `//`.** `strtolower($matches[1])` нормалізує провайдера, але сам шлях
  до `/webhooks` ми порівнюємо літерально. Подвійні слеші (`//webhooks/github`)
  нормалізує Nginx до нас — тобто ми **покладаємось на проксі**. Якщо колись фронт
  зміниться (інший веб-сервер, прямий FPM), цю нормалізацію доведеться брати на себе.
- **Один трейлінг-слеш толеруємо, глибший шлях — ні.** `/webhooks/github/extra` падає
  в `404`. Це навмисно, але це край, який легко зламати неуважним regex при розширенні.
- **Зростання провайдерів.** Поки `VerifierRegistry` маленький — добре. З десятком
  провайдерів захочеться, щоб «невідомий провайдер → 404» був ще й логований окремо,
  щоб ловити друкарські помилки в URL інтеграцій.

## 5. Патерни, які варто запамʼятати

- **Front Controller** — єдина точка входу, через яку проходить кожен запит. Скрізь у
  PHP-фреймворках (Laravel `public/index.php`, Symfony `public/index.php`); тут —
  руками, тонким скриптом.
- **Value Object для запиту** (`ServerRequest`) — незмінний, типізований «вигляд» на
  сирі дані. Споріднений з PSR-7 `ServerRequestInterface`; суть та сама — зробити
  вхідні дані тестованими й передбачуваними.
- **Lazy initialization / lazy connection** — ресурс (сокет БД, Redis) створюється у
  момент першого реального використання, а не на старті. Протилежність — fail-fast,
  доречний там, де «краще не злетіти зовсім, ніж працювати наполовину».
- **Fail-safe backstop / graceful degradation** — останній `try/catch`, що
  перетворює будь-який збій на коректну відповідь без витоку внутрішностей. Те саме
  роблять error-handler-и фреймворків і middleware на кшталт Symfony `ErrorListener`.
- **HTTP-семантика статусів як контракт** — `400` (зламаний запит клієнта), `404`
  (немає ресурсу), `405` + `Allow` (метод не той, ось дозволені), `401` (підпис не
  пройшов), `202` (прийнято, оброблю асинхронно). Машинні клієнти реагують саме на
  код — це публічний API, а не косметика.
- **Принцип no-leak (NFR-1)** — назовні рівно стільки, скільки треба; деталі — лише в
  лог. Зустрічається в безпеці всюди: від generic «Login failed» до прихованих
  стек-трейсів у проді.

## Запити до бази даних

Я **не виконував жодного** SQL-запиту напряму проти бази даних у межах цієї підзадачі.

Єдиний контакт із БД був **непрямим**: curl `POST /webhooks/github` змусив контролер
відкрити PDO-зʼєднання й пройти шлях dedupe/insert — але це робив сам контролер,
**я не подавав жодного SQL вручну**.

# Навчальна нотатка: T1.3 — Stripe-верифікатор вебхуків

> Мова: українська. Аудиторія: junior → middle PHP.

## 1. Проблема простими словами

Stripe шле нам вебхуки про події (оплати, рефанди тощо). Перш ніж щось із цим
робити, ми зобовʼязані довести дві речі: **запит справді від Stripe** і **це не
старий перехоплений запит, який нам підсунули вдруге**. Якщо пропустити цю
перевірку, будь-хто, хто знає наш URL, зможе вкинути фейкову подію «оплата
успішна» — і вся подальша логіка довірить брехні.

Ми реалізували `StripeVerifier` — конкретну реалізацію контракту
`ProviderVerifier` (з T1.1), поряд із `GitHubVerifier` (T1.2). Це чистий шар
автентифікації: він бере сирий байтовий `rawBody` і заголовки, повертає
`VerificationResult` (`valid` з `event_id`/`event_type` / `invalid` з причиною /
`error` для «не змогли перевірити взагалі»). Жодного запису в БД, жодної черги —
це робота контролера (T1.5/T1.6).

Чому це окрема, маленька, передбачувана відповідальність — бо безпека вебхуків
будується на принципі **«не довіряй payload, доки він не автентифікований»**.
Верифікатор — це ворота. За ворота нічого не проходить непідписаним.

## 2. Потік виконання

Де цей клас живе у загальному потоці системи (повний шлях — мета архітектури):

```
Stripe POST /webhooks/stripe
        │  заголовок Stripe-Signature: t=...,v1=...,v1=...
        ▼
   Nginx ──► PHP-FPM (контролер прийому, T1.5/T1.6)
        │  1. читає RAW body (сирі байти, не перекодований JSON)
        │  2. ► StripeVerifier::verify(rawBody, headers)  ◄── ЦЯ підзадача
        │  3. INSERT event (status=received) у MySQL
        │  4. RPUSH job у Redis
        │  5. return 202 Accepted
        ▼
   Redis ──► Worker → handler → success / retry(2^n) / DLQ
```

Усередині самого `verify()` (крок 2) потік такий:

1. Порожнє тіло → `invalid('empty request body')`.
2. Немає заголовка `stripe-signature` → `invalid`.
3. Парсимо складений заголовок: `explode(',')`, кожна пара через `explode('=', …, 2)`;
   биту пару просто пропускаємо. Беремо один `t` і **усі** `v1`.
4. Немає `t` → invalid; немає жодного `v1` → invalid.
5. `ctype_digit($t)` — інакше `invalid('non-numeric t')`.
6. **Перевірка вікна часу ПЕРЕД HMAC**: `abs(clock() - (int)t) > 300` → `invalid('timestamp outside tolerance')`.
7. `$computed = hash_hmac('sha256', "{t}.{rawBody}", secret)` — рахуємо **один раз**;
   цикл `hash_equals($computed, $v1)` по кандидатах, будь-який збіг → далі, інакше `invalid('signature mismatch')`.
8. Лише ТЕПЕР `json_decode(..., JSON_THROW_ON_ERROR)` у try/catch → дістаємо `id`/`type`;
   биті/відсутні → `invalid`. Інакше `valid($id, $type)`.

Звертай увагу на **порядок**: дешеве й безпечне відсіювання спереду, крипто —
посередині, читання payload — в самому кінці, тільки після проходження підпису.

## 3. Чому саме так

- **Підписаний рядок — `"{t}.{rawBody}"`, не саме тіло.** Stripe рахує HMAC над
  «timestamp.тіло», тому timestamp теж під захистом підпису: підмінити його не
  можна, не зламавши HMAC. Ми беремо **літеральні байти** `t` із заголовка
  (а не перекастований `(int)$t`), щоб байт-у-байт збігтися з тим, що підписав
  Stripe. Це типове джерело багів: «нормалізував» — і підпис уже не сходиться.

- **Толерантність часу (300с) — це окремий захист понад підпис.** Перехоплений
  старий запит має **справжній валідний підпис** — сам HMAC його б прийняв.
  Закриває діру replay саме вікно свіжості. Дедуплікація (FR-11) ловить дублікати
  *уже прийнятих* подій, але вікно ловить ще й старі перехоплення до того, як
  вони взагалі потраплять у систему. Це два різні рубежі, не дублікати.

- **Вікно — ПЕРЕД HMAC.** `t` хоч і всередині підписаного рядка, але перевірка
  вікна не споживає секрет і нічого не «зливає» (зловмисник сам прислав `t`),
  зате дешево відсіює replay до криптороботи. До проходження HMAC ми не довіряємо
  `t` ні для чого, крім перевірки свіжості.

- **`hash_equals`, не `==`.** Захист від timing-атаки (як у GitHub). `$computed`
  рахуємо **один раз поза циклом** — цикл по `v1` це лише порівняння за сталий
  час, тож «напханий» заголовок не змушує повторювати HMAC.

- **Кілька `v1` = ротація ключів.** Під час зміни підписного секрету Stripe слати
  кілька `v1`; приймаємо, якщо збігся **будь-який**. `v0` та інші схеми ігноруємо.

- **id/type беремо з ТІЛА, на відміну від GitHub.** У Stripe `event.id`
  (напр. `evt_123`) і `event.type` (напр. `payment_intent.succeeded`) лежать у
  JSON-тілі, а не в заголовках. Тому тіло декодуємо — але **тільки після**
  проходження підпису (золоте правило: не довіряй payload до автентифікації).

- **Валідний підпис, але тіло не читається → invalid, не error.** Без `id` немає
  ключа дедуплікації; **fail closed** (401). `error()` лишаємо лише для «не
  змогли перевірити взагалі» (віддалена аварія) — у локального HMAC такого не буває.
  `JsonException` ніколи не випливає як 5xx, а `is_string(...)` перед `trim()`
  рятує від `TypeError`, якщо id/type прийшли числом/масивом/null.

- **Секрет резолвиться в конструкторі (`fromSecrets`).** Відсутній `whsec_...` —
  це помилка деплою → `VerificationException::missingSecret('stripe')` → 500, а не
  401. Сплутати ці два — типова помилка: «нема секрета» це не «поганий підпис».

- **Годинник інжектується** (`Closure(): int`, дефолт `time(...)`), щоб гілку
  толерантності можна було тестувати без `sleep` і без мокання глобального часу.
  Зафіксовано в **ADR `.claude/decisions/0007-stripe-verifier-clock-and-tolerance.md`**.

### Відхилені альтернативи

- **`time()` напряму в `verify()`** — гілка толерантності стає нетестованою.
  Тому інжектимо Closure-годинник (ADR 0007, варіант (b) проти прямого `time()` (a)
  і повноцінного `Clock`-інтерфейсу (c) — останній надлишковий, поки немає другого
  споживача).
- **Толерантність з env/конфіга** — поки `const 300` + ctor-параметр: відповідає
  дефолту Stripe, не роздуває `ProviderSecrets` (він лише для секретів), лишає
  двері для env пізніше.
- **HMAC перед вікном часу** — теж коректно (бо `t` підписаний), але тоді на кожен
  replay марно рахуємо HMAC; вікно-першим дешевше і нічого не зливає.
- **Відхиляти дубльований `t` / ліміт на кількість `v1`** — не потрібно: дубль `t`
  безпечний (last-wins, бо `t` під HMAC), а кількість `v1` згори обмежена розміром
  заголовка в nginx; цикл — лише сталі порівняння.

## 4. Слабкі місця та технічний борг

- **Толерантність зашита в константу.** 300с — нормально, але якщо одного дня
  знадобиться різне вікно для різних провайдерів/середовищ, доведеться виносити в
  конфіг. Поки що це свідомо відкладено.
- **Жорсткий годинник системи.** Якщо час на сервері «попливе» (NTP не
  синхронізований), легальні вебхуки почнуть масово падати в `timestamp outside
  tolerance`. Це не баг класу, але операційний ризик: моніторинг має ловити сплеск
  таких invalid.
- **Дедуплікація ще не реалізована (FR-11).** Верифікатор лише *дістає* `event_id`;
  власне захист від повторної обробки одного й того самого `evt_...` — це робота
  пізнішого шару (БД/воркер). До того моменту вікно часу — єдиний бар'єр проти
  повторів, і він не ловить дубль, надісланий у межах 300с.
- **Ротація секретів обробляється на боці прийому кількох `v1`, але самого
  механізму зберігання двох секретів у нас нема.** Поки секрет один; коли Stripe
  даватиме перехідний період із двома, нам теж треба буде вміти тримати обидва.
- **Poison-повідомлення / thundering herd на ретраї** — не у цьому класі, але
  пам'ятай: верифікатор пропускає лише автентичні події, проте «автентична» не
  означає «легко оброблювана». Подальші шари мають мати backoff і DLQ.

## 5. Патерни, які варто запам'ятати

- **Timing-safe comparison** (`hash_equals`) — скрізь, де порівнюєш секрети/токени/
  підписи: API-ключі, CSRF-токени, скидання паролів.
- **HMAC over a signed string** — підпис не лише тіла, а тіла + метаданих (тут
  timestamp). Той самий прийом у JWT (`header.payload` під підписом), у AWS SigV4.
- **Replay protection через вікно часу** — TOTP/2FA, AWS-підписи запитів, nonce у
  платіжних протоколах. Підпис каже «справжнє», вікно каже «свіже».
- **Fail closed** — за невизначеності відмовляй, не пропускай. Безпекова дефолтна
  поведінка скрізь: авторизація, файрволи, перевірка сертифікатів.
- **Don't trust payload before authentication** — спершу автентифікуй, потім
  парси. Уникає цілого класу атак на парсер недовіреними даними.
- **At-least-once delivery + idempotency key** — Stripe (і ми) гарантують
  доставку «хоча б раз», тож `event.id` стає ключем ідемпотентності. Той самий
  патерн у Kafka-консюмерах, платіжних API, чергах SQS.
- **Dependency injection годинника (clock injection)** — робить час тестованим;
  загальний прийом для всього, що залежить від «зараз» / випадковості / I/O.

## Покрокова хроніка (реальні команди та вивід)

1. Використав skill `webhook-security` (Stripe-секція) і прочитав міграцію (колонки
   `event_id`/`event_type`) — контекст уже був із T1.1/T1.2.

2. Запустив архітектора (sub-agent) → дав дизайн і записав ADR
   `.claude/decisions/0007-stripe-verifier-clock-and-tolerance.md` (інжекція
   годинника + джерело толерантності).

3. Створив файл `app/src/Verification/StripeVerifier.php` (Write).

4. Лінт + прогін 14 гілок у контейнері `php` (на хості php немає). Команда:

   ```bash
   docker compose exec -T php sh -lc 'cd /var/www/html \
     && php -l src/Verification/StripeVerifier.php \
     && php -r "..."'
   ```

   У PHP-скрипті створив верифікатор із фіксованим годинником
   `fn(): int => 1700000000`, секретом `"whsec_test"`, обчислив правильні підписи
   через `hash_hmac('sha256', "$t.$body", $secret)` і прогнав сценарії.

   Фактичний вивід:

   ```

   valid: valid id=evt_123 type=payment_intent.succeeded
   rotation: valid
   stale: invalid reason=timestamp outside tolerance
   future: timestamp outside tolerance
   tampered: signature mismatch
   non-json: payload is not valid JSON
   ```

   Що показує прогін: валідний підпис → `valid` із витягнутими `id`/`type`;
   ротація (другий `v1` збігся) → `valid`; старий/майбутній timestamp поза 300с →
   `invalid(timestamp outside tolerance)`; підроблене тіло → `signature mismatch`;
   валідний підпис над не-JSON → `invalid(payload is not valid JSON)`; валідний
   підпис без `id` → `invalid`; відсутні `t`/`v1` / нечисловий `t` / порожнє тіло /
   без заголовка → коректні `invalid`; відсутній секрет → `VerificationException`.

5. Рев'ю (sub-agent code-reviewer) → вердикт «Approve with nits» (2 MINOR, 2 NIT,
   без BLOCKER/MAJOR), звіт `.claude/reviews/T1.3-2026-06-05.md`. Опрацьовано:
   - **MINOR #1** (дубльований `t` last-wins) — ПРИЙНЯТО частково: додав коментар,
     що пояснює, чому last-wins безпечний (значення `t` під HMAC); логіку
     відхилення не додавав.
   - **MINOR #2** (необмежений цикл `v1`) — ВІДХИЛЕНО: `$computed` рахується раз,
     цикл — лише `hash_equals`, кількість `v1` обмежена розміром заголовка nginx;
     ліміт-константа зайва.
   - **NIT #3** (`#[Override]`) — ВІДХИЛЕНО: у кодовій базі не вживається, рішення
     для всього проєкту пізніше.
   - **NIT #4** (overflow `(int)` на довгому `t`) — ВІДХИЛЕНО: не баг, такий `t`
     завжди поза толерантністю → коректний invalid.

6. Застосував коментар (MINOR #1) і перевірив, що lint чистий і валідний шлях

## Запити до бази даних

Жодного SQL-запиту до БД у цій підзадачі **не виконувалося**. `StripeVerifier` —
це чистий PHP-верифікатор без доступу до даних: він працює лише з сирим тілом
запиту, заголовками та секретом. Запис події в MySQL і постановка в Redis — це
відповідальність контролера прийому (T1.5/T1.6), а не цього класу.

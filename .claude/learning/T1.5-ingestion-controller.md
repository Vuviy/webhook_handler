# Навчальна нотатка: T1.5 — `IngestionController` (raw body → verify → dedupe → insert → enqueue → 202)

> Мова: українська. Аудиторія: junior → middle PHP.

## 1. Проблема простими словами

T1.5 — це **інтеграційний шов**. До нього в нас уже були окремі деталі: три
верифікатори підписів (T1.2 GitHub, T1.3 Stripe, T1.4 PayPal), з'єднання з БД і
таблиця `webhook_events` (T0.3) та черга Redis (T0.4). Кожна деталь працювала
сама по собі, але ніхто не зводив їх у єдиний конвеєр прийому.

Завдання T1.5 — написати логіку, яка на вхідний вебхук **відомого** провайдера:

1. перевіряє підпис (timing-safe, на сирому тілі);
2. **дедуплікує** подію (та сама доставка не повинна оброблятися двічі);
3. записує подію в `webhook_events` зі статусом `received`;
4. ставить job у чергу Redis;
5. віддає `202 Accepted` — і робить це **швидко**.

Навіщо це для системи вебхуків: провайдер на тому кінці — це не людина, а
автомат із власною політикою повторів. Якщо ми відповімо повільно або не-`2xx`,
він **передоставить** подію (можливо, багато разів). Тому весь сенс прийому —
зробити мінімум синхронно (перевір → запиши → постав у чергу → ack) і віддати
всю «важку» роботу воркеру. HTTP-запит не має права робити heavy lifting.

Важливо, що саме НЕ входило в T1.5: роутинг `/webhooks/{provider}`,
перевірка HTTP-методу та `405`, читання `php://input` / `getallheaders()`,
прив'язка до `public/index.php`. Усе це — фронт-контролер у T1.6. Тому контролер
тут навмисно **чистий**: на вхід — value-object (provider, rawBody, headers),
на вихід — value-object (`IngestionResponse`). Жодних суперглобалів.

## 2. Потік виконання

Як вебхук подорожує системою після цієї зміни:

```
provider POST /webhooks/{provider}
   │
   ▼
 Nginx  ──►  PHP-FPM
   │
   ▼
 IngestionController::handle(provider, rawBody, headers)
   │  1. VerifierRegistry::get(provider)
   │        unknown → 404 (нічого не пишемо)
   │  2. array_change_key_case(headers, CASE_LOWER)   ← нормалізація контракту
   │  3. verifier->verify(rawBody, headers) → VerificationResult
   │        Invalid  → 401 (нічого не пишемо)
   │        Error    → 502 (наша аварія перевіряча — провайдер повторить)
   │        throws VerificationException → 500 (нема секрету / misconfig)
   │  4. Valid:
   │        EventRepository::insertReceived(...)  ── INSERT ... ON DUPLICATE KEY UPDATE id=id
   │           rowCount()===1 (новий)  → enqueue job у Redis  → 202
   │           rowCount()===0 (дублікат) → БЕЗ enqueue        → 202
   │        збій БД / черги після verify → 500 (провайдер передоставить, дедуп залікує)
   ▼
 202 Accepted   {"status":"accepted"}
```

Далі (вже поза T1.5, але це кінцева мета конвеєра):

```
 Redis queue ──► worker (long-running)
   │  pop job → provider handler
   │     success → status=processed
   │     failure → retry, backoff 2^n, attempts++
   │     3 невдачі → Dead Letter Queue, status=failed
   ▼
 MySQL (повний аудит) + Dashboard (read-only)
```

Зверни увагу на дві «безшумні» речі в кроці 4. По-перше, **дублікат теж отримує
202** — інакше провайдер вважатиме доставку невдалою і повторюватиме вічно.
По-друге, дублікат **не ставиться в чергу повторно** — інакше та сама подія
оброблялася б двічі. Тобто 202 ми завжди говоримо ввічливо, а от роботу
заводимо рівно один раз.

## 3. Чому саме так

ADR: `.claude/decisions/0009-ingestion-dedupe-insert-and-outcome-http-mapping.md`
(стратегія дедуп-insert + мапінг outcome→HTTP).

**Тонкий HTTP-шлях (NFR-3).** Провайдери очікують швидкий `2xx`. Якби контролер
сам обробляв подію (ходив у зовнішні API, рахував, надсилав листи), запит міг би
тривати секунди — і провайдер передоставить. Тому контролер лише фіксує факт
(«ми це отримали і записали») і делегує. Це класичний поділ
**ingestion vs. processing**.

**Дедуплікація — робота БАЗИ, не застосунку (FR-11, AC-6).** Доставка
at-least-once означає, що одна й та сама подія може прийти двічі, зокрема
**паралельно** (провайдер ретраїть, поки наша перша відповідь ще в дорозі).
Наївний `SELECT → якщо нема, то INSERT` має **гонку**: два запити одночасно
бачать «рядка немає» і обидва вставляють. Тому покладаємось на
`UNIQUE(provider, event_id)` і **один атомарний** запит:

```sql
INSERT ... VALUES (...) ON DUPLICATE KEY UPDATE id = id
```

`ON DUPLICATE KEY UPDATE id = id` — навмисний **no-op**. Він перетворює колізію
унікального ключа на «нічого не роби» замість помилки, але affected-rows
лишається інформативним: MySQL дає **1** на реальну вставку і **0** на no-op
дубліката (на справжній `UPDATE` було б 2, але ми його не робимо). Саме тому
`rowCount() === 1` однозначно означає «вставлено вперше» → можна ставити в чергу.

**Мапінг outcome → HTTP, увесь retry-aware (ADR 0009):**

- `Valid` → 202 (прийняли);
- `Invalid` → 401, **без запису** (у підробленого запиту немає довіреного
  `event_id`, і писати форджі — це ризик флуду аудит-таблиці);
- `Error` (перевіряч сам не зміг відпрацювати, напр. PayPal verify-API
  недоступний) → 502, бо це **наша** тимчасова аварія, і нехай провайдер
  повторить;
- `VerificationException` (нема секрету / конфіг) → 500;
- збій БД/черги вже **після** verify → 500.

Чому misconfig = 500, а не 401: відсутній секрет — це наша помилка деплою.
Віддати 401 означало б **збрехати** легітимному провайдеру, що його підпис
поганий. 500 чесно каже «це ми зламані», і провайдер ретраїтиме, поки ми не
полагодимо конфіг — без втрати події.

**insert-потім-enqueue і orphan-рядок.** Якщо enqueue впаде **після** insert,
лишиться рядок `received` без job. Ми повертаємо 500 → провайдер передоставляє →
дедуп робить повтор безпечним (рядок уже є, другий insert дасть rowCount 0, тож
ми не дублюємо обробку, але й не плодимо рядки). Ми навмисно **не** будуємо
2PC / outbox — це надмір для T1.5; залишковий ризик прийнятний (sweeper для
orphan-рядків — задача на майбутнє).

**Лінивий реєстр верифікаторів — операційна ізоляція.** `VerifierRegistry::get()`
будує верифікатор ЛІНИВО через `fromSecrets()` на момент виклику. Кожен
`fromSecrets()` кидає, якщо немає ЙОГО секрету. Якби ми будували всі три одразу
(eager), ненастроєний PayPal поклав би й GitHub, і Stripe. Лінивість означає, що
ненастроєний провайдер ламає **лише свій** ендпоінт.

**Чистий контролер (value-object in → value-object out).** Контролер не чіпає
`php://input`, `getallheaders()` чи суперглобали — це робота фронт-контролера
(T1.6). Завдяки цьому кожну гілку (`Valid` / `Invalid` / `Error` / дублікат /
unknown) можна юніт-тестувати без живого HTTP-запиту.

**Нормалізація заголовків у контролері.** Верифікатори очікують ключі в нижньому
регістрі. `array_change_key_case($headers, CASE_LOWER)` перед `verify()` —
контролер є власником цього контракту, щоб верифікатори не залежали від того, як
саме фронт-контролер прочитав заголовки.

**Вичерпний `match` по enum без `default`.** Якщо колись з'явиться новий стан
outcome, `match` без `default` зламає компіляцію — це **гучний** провал замість
тихого пропуску невідомого випадку. Fail-loud краще за fail-silent у місцях, де
від рішення залежить безпека/коректність.

### Відхилені альтернативи (компроміси)

- `SELECT-потім-INSERT` для дедупу — гонка під паралельні однакові доставки;
  атомарний `INSERT…ON DUPLICATE` усуває її.
- `INSERT IGNORE` — глушить і **справжні** помилки (truncation, NOT NULL), а це
  аудит-таблиця; `ON DUPLICATE KEY UPDATE id=id` лишає `rowCount` інформативним
  без приховування помилок.
- enqueue-перед-insert — job без рядка в БД; гірше за orphan-рядок (рядок
  самозалікується дедупом).
- 2PC / outbox-патерн — надмір для T1.5.
- Запис `Invalid`/`Error` у `webhook_events` (заради аудиту FR-9) — нема
  довіреного `event_id` (ключ дедупу / NOT NULL колонки), плюс ризик флуду
  форджами; окремий лог відхилень відкладено.
- Eager-побудова всіх верифікаторів — один ненастроєний провайдер поклав би всі;
  лінивий реєстр ізолює.
- Контролер пише відповідь сам (`http_response_code`/`echo`) — куплення до
  глобалів і нетестовність; value-object-out краще.

## 4. Слабкі місця та технічний борг

- **Orphan-рядок.** Якщо enqueue падає після insert — лишається рядок `received`
  без job. Сьогодні нас рятує дедуп + ретрай провайдера, але якщо провайдер
  **не** передоставить (вичерпав свої спроби), подія застрягне в `received`
  назавжди. Борг: фоновий sweeper, який добирає «завислі» `received` і ставить їх
  у чергу.
- **Аудит відхилень неповний (FR-9).** `Invalid`/`Error` ніде не фіксуються. При
  атаці підробленими підписами ми не побачимо її в `webhook_events`. Борг:
  окремий лог/лічильник відхилень (метрика, а не аудит-таблиця, щоб уникнути
  флуду).
- **Thundering herd на ретраях провайдера.** Якщо БД/Redis лежать, ми віддаємо
  500 усім — і всі провайдери одночасно почнуть ретраїти за своїми графіками.
  При сплеску це додасть навантаження саме тоді, коли система й так у біді.
  Пом'якшення — на рівні backoff воркера й, у майбутньому, rate-limit/circuit
  breaker на прийомі.
- **Ротація секретів.** Лінивий реєстр читає секрет на момент виклику, але
  «двох дійсних секретів одночасно» (старий + новий під час ротації) поки нема —
  під час ротації частина легітимних вебхуків ловитиме `Invalid`/500. Борг:
  підтримка переліку дійсних секретів на провайдера.
- **Poison message — поки за межами T1.5.** Подія, що завжди валить обробник,
  тут лише потрапляє в чергу; її доля (3 спроби → DLQ) вирішується у воркері.
  Тримай у голові, що прийом її прийме «успішно» — проблема виявиться пізніше.

## 5. Патерни, які варто запам'ятати

- **At-least-once delivery** — постачальник гарантує доставку «хоча б раз»,
  отже можливі дублі. Зустрічається у всіх чергах (SQS, Kafka, RabbitMQ) і
  webhook-провайдерів. Наслідок: споживач має бути ідемпотентним.
- **Idempotency key** — тут це `(provider, event_id)` під `UNIQUE`. Той самий
  патерн у Stripe API (`Idempotency-Key` заголовок), у платіжних системах,
  у REST `PUT`.
- **Atomic upsert для дедупу** — `INSERT … ON DUPLICATE KEY UPDATE` (MySQL),
  `INSERT … ON CONFLICT DO NOTHING` (Postgres), `MERGE` (інші СУБД). Замінює
  гонку «check-then-act» на одну атомарну операцію.
- **Timing-safe comparison** — `hash_equals()` замість `==` для підписів, щоб не
  злити інформацію через час порівняння. Скрізь, де порівнюються секрети/токени/
  HMAC.
- **Thin ingestion / async processing** — швидкий ack + офлайн-обробка. Лежить в
  основі command queue, event-driven систем, log-collector-ів.
- **Lazy initialization** — будуємо об'єкт тільки коли він потрібен; тут дає
  операційну ізоляцію провайдерів.
- **Dead letter queue + exponential backoff** — поки у воркері, але це частина
  тієї ж картини надійності: обмежені спроби, наростаючі паузи, окреме сховище
  для «безнадійних» подій.

## Шов T1.5 ↔ T1.6

T1.5 = логіка контролера + реєстр + `EventRepository`. T1.6 = роутинг
`/webhooks/{provider}`, метод/`405`, читання `php://input` + `getallheaders`,
прив'язка в `index.php`, рендер `IngestionResponse`. Контролер уже мапить
unknown→404 (forward-compatible за ADR 0009), тож роутинг T1.6 лишиться тонким.

# Навчальна нотатка: T2.3 — Exponential backoff + retry scheduler (zset)

> Мова: українська. Аудиторія: junior → middle PHP.
> Контекст: Milestone 2, depends T2.2. ADR — `.claude/decisions/0013-retry-scheduler.md`,
> рев'ю — `.claude/reviews/T2.3-2026-06-06.md`.

## 1. Проблема простими словами

T2.2 дав воркеру робочий «щасливий шлях»: дістати джоб → застовпити рядок
(`received → processing`) → викликати обробник → `processed`. Але **гілка помилки була
надто категоричною**: будь-яка невдача обробника (навіть тимчасова — впав мережевий
виклик, БД на тій стороні моргнула) одразу позначалася `failed`. Це невірно для системи
вебхуків.

Чому невірно? Бо ми працюємо в моделі **at-least-once delivery**: провайдер (GitHub /
Stripe / PayPal) гарантує, що *хоча б раз* доставить подію, і ми так само маємо
*хоча б раз спробувати* її обробити. Якщо downstream-залежність впала на 3 секунди, це
не привід викидати подію — це привід **зачекати й спробувати ще раз**.

T2.3 додає саме цей механізм: **експоненційний backoff із jitter** + **відкладена черга
ретраїв** на Redis sorted set (`webhooks:retry`). Тимчасова невдача більше не вмирає —
вона переплановується на «зараз + затримка», а коли час настав, воркер сам повертає її в
основну чергу. Лічильник спроб обмежений (`MAX_ATTEMPTS = 3`), тож подія не крутиться
вічно: коли спроби вичерпано, вона стає термінальною (поки що `failed`; DLQ — це вже T2.4).

## 2. Потік виконання

Повний шлях вебхука після цієї зміни. Жирним — те, що додала T2.3.

```
provider POST → Nginx → PHP-FPM (ingestion controller)
   read RAW body → verify signature (hash_equals) → INSERT (status=received)
   → RPUSH job {event_id, provider, attempt=1} у webhooks:queue → 202 Accepted
        │
        ▼
   worker.php (нескінченний цикл), кожна ітерація:
   ┌─► promoteDue()   ← T2.3: перенести дозрілі ретраї z webhooks:retry назад у чергу
   │   BLPOP webhooks:queue (таймаут 5с)
   │   findForProcessing(provider, event_id)   ← читаємо рядок-джерело
   │   markProcessing(id)  guarded AND status='received'   ← застовплення (dedupe)
   │   handler->handle(event)
   │      ├─ OK ──────────────► markProcessed(id)  (processed, processed_at=NOW)
   │      ├─ TransientException ─┐
   │      ├─ \Throwable (any) ───┤► retryOrFail()  ← T2.3
   │      │                      │     next = attempt + 1
   │      │                      │     if next ≤ 3:
   │      │                      │        markForRetry(id, next, error)  (→ received)
   │      │                      │        scheduleRetry(... readyAt = now + delayFor(next))  ZADD
   │      │                      │     else (вичерпано):
   │      │                      │        markFailed(id, error)  ← interim, шов для T2.4 (DLQ)
   │      └─ PermanentException ─► markFailed(id, error)  ← interim, шов для T2.4 (DLQ)
   └───────────────────────────────────────────────────────────────────────────┘
```

Ключова петля ретраю: `retryOrFail` пише в БД `received` **і** кладе конверт у zset зі
score = час готовності. Наступні ітерації циклу через `promoteDue()` рано чи пізно
побачать, що score ≤ `time()`, і `RPUSH` конверт назад у `webhooks:queue` (`ZRANGEBYSCORE →
RPUSH → ZREM`). Воркер знову його `BLPOP`-ає, і оскільки рядок уже повернутий у `received`,
**guarded `markProcessing` знову виграє claim** — спроба повторюється.

## 3. Чому саме так

Усі рішення задокументовані в ADR 0013. Найважливіші:

**D1 — promoteDue() ВСЕРЕДИНІ циклу воркера, а не окремий scheduler-процес.**
У нас рівно **один воркер** (так каже spec). Він — єдиний споживач і черги, і zset, тому
може дешево «підмітати» дозрілі ретраї на кожній ітерації (особливо на idle-tick).
Затримка перенесення обмежена таймаутом BLPOP (≤5с) — для цього масштабу прийнятно.
*Відхилено (Опція B):* окремий scheduler-контейнер. Це другий довгоживучий процес —
другий деплой, health-check, graceful shutdown — і він повертає гонку двох читачів zset
без жодної вигоди при одному воркері. Класичний YAGNI.

**D2 — НЕ-атомарний `ZRANGEBYSCORE + ZREM` свідомо прийнятний.**
Прочитати дозрілі члени, а потім видалити їх — не атомарно: два читачі могли б обидва
прочитати й обидва перепхати (дубль). Але при **одному** воркері другого читача не існує,
тож вікно гонки не відкривається. А навіть якщо колись дубль і просочиться — guarded
`markProcessing` його нейтралізує (другий claim чіпляє 0 рядків і пропускається). Порядок
`RPUSH`, потім `ZREM` — теж навмисний: якщо процес помре між ними, джоб лишиться в zset і
буде перенесений знову (at-least-once), а не загубиться.
*Відхилено (Опція D):* Lua `ZPOPMIN` для атомарного claim-and-remove. Дає безпеку для
багатьох воркерів, якої однопроцесному деплою не треба; додає Lua-рядок, який треба
підтримувати й тестувати. Передчасно — шлях названо в docblock, але не збудовано.

**D3 — конверт `attempt` = контрольне значення, DB `attempts` = аудит-дзеркало.**
Рішення «ретраїти чи ні» приймається за значенням у конверті (воно вже на дроті й переживе
збій БД). Той самий інкрементований номер записується і в БД-колонку `attempts` —
**одним інкрементом, в одному місці** (`retryOrFail`), тож обидва приймачі коректні.
*Відхилено (Опція F):* лише БД як джерело істини — змусило б робити зайвий read `attempts`
на шляху помилки. *Відхилено (Опція G):* лише конверт — `attempts` назавжди лишився б 0, і
дашборд (T3.x, FR-9) ніколи не показав би «спроба 2 з 3».

**D4 — розділення POLICY / MECHANISM.**
`RetryScheduler` володіє **політикою**: математика backoff, jitter, межа `MAX_ATTEMPTS`,
рішення `retryOrFail`. `Queue` володіє **механізмом**: сирі `ZADD` / `ZRANGEBYSCORE` /
`ZREM`, бо саме `Queue` — єдиний власник імен Redis-ключів і схеми конверта (там же живуть
`encodeJob`/`decodeJob`). `scheduleRetry()` — це дзеркало `enqueue()` на боці ретраю.
*Відхилено (Опція I):* усе на `Queue` — затягнуло б «магічні числа» backoff у механізм
черги, змішавши політику з транспортом.

**D6 — база 2с, СЕКУНДИ, equal jitter `D/2 + rand(0, D/2)`, `D = 2^(n-1)·2`.**
Це **розв'язує open question #2 спеки на користь секунд**. Вебхуки відновлюються за
секунди, не хвилини; якби ми тримали подію хвилинами, власні ретраї провайдера почали б
гонитися з нашими й дублювати роботу. **Equal jitter** (а не full jitter `rand(0, D)`)
гарантує ненульовий мінімум розкиду: затримка ніколи не схлопнеться в ~0, але натовп усе
одно розмазується в часі.
*Відхилено:* хвилини (Опція N — провайдер сам передоставить); full jitter (Опція O — може
дати майже миттєвий ретрай і знову зібрати «стампеду»).

## 4. Слабкі місця та технічний борг

Це чесно задокументовано в ADR (Negative/debt) і рев'ю (NIT'и). Жоден пункт не вимагав
правки коду — це усвідомлений борг, що переноситься.

- **Не-атомарне перенесення (D2)** коректне лише тому, що воркер один. Другий воркер
  вимагатиме Lua `ZPOPMIN`. Припущення зафіксоване в docblock методу, тож зміцнення —
  локальна правка, не редизайн.
- **Interim `failed` для вичерпаних і permanent (D5)** живе до T2.4: вичерпаний ретрай —
  `status=failed` у БД, але **ще не в списку `webhooks:dlq`**. Чесно, audited (`last_error`),
  видимо дашбордом — але повноцінного DLQ ще немає. T2.4 прибирає цей борг **додаванням**,
  а не переписуванням.
- **Немає «жнеця» (reaper) застряглих рядків (NIT-3).** Якщо `markForRetry` пройшов, а
  `scheduleRetry` кинув виняток, рядок лишається в `received`, але **на жодній черзі**.
  Він видимий дашборду з `last_error`, але автоматично не відновлюється. Це спільний борг
  із застряглим `processing` із T2.2; обидва чекають на майбутній re-queue-шлях (T3.2).
  *DB-first порядок тут навмисний:* він кращий за Redis-first, який при збої БД залишив би
  джоб запланованим проти рядка, що завис у `processing` (тоді guard заблокував би
  легітимний ретрай назавжди).
- **Семантика колонки `attempts` (NIT-2).** Після першої невдалої спроби в БД буде
  `attempts = 2` (бо пишемо `next`). Колонка означає «номер поточної/наступної спроби», а
  не «скільки спроб уже зроблено». Внутрішньо когерентно, але дашборд T3.x треба будувати
  з цим розумінням, інакше він «переоцінить» на одиницю.
- **Backoff у секундах** припускає швидке відновлення downstream. Справді тривала аварія
  (хвилини) швидко вичерпає всі 3 спроби й відправить подію у DLQ — на це й розрахований
  шлях DLQ + re-queue (T2.4 / T3.2), а не довше очікування в лінії.
- **Зростання навантаження / провайдерів / частоти помилок:** при сплеску однотипних
  невдач jitter рятує від thundering herd на ретраї (без нього сотні подій повернулися б у
  чергу в одну секунду). Poison message (конверт, що валить обробник детерміновано) поки
  не має окремого захисту, крім вичерпання спроб → `failed`/DLQ — це коректний, хай і
  грубий, вихід.

> Growth point (типова помилка джуна, тут НЕ зроблена — варто запам'ятати чому):
> спокусливо обернути `try` навколо всього блоку обробки разом із `markProcessed`. Тоді
> збій *запису статусу* (інфраструктурна помилка) хибно позначив би **успішно** оброблену
> подію як `failed`. У коді `try` навмисно охоплює **лише** `handle()`; `markProcessed`
> лишається ззовні й при збої падає в зовнішній backstop. Розрізняй **помилку обробника**
> (логіка/downstream → ретрай/fail) і **інфраструктурну помилку** (БД/Redis → backstop).

## 5. Патерни, які варто запам'ятати

- **At-least-once delivery** — система гарантує доставку «хоча б раз», тому дублі можливі.
  Зустрічається скрізь: Kafka, SQS, RabbitMQ, самі провайдери вебхуків.
- **Idempotency key + guarded claim** — захист від дублів. Тут це UNIQUE(provider,event_id)
  на вставці + `UPDATE ... WHERE status='received'` на застовпленні. Той самий принцип —
  idempotency-key у Stripe API, conditional writes у DynamoDB.
- **Exponential backoff** — затримка росте як `2^(n-1)·base`. Скрізь у мережевих ретраях:
  TCP, gRPC, AWS SDK, HTTP-клієнти.
- **Jitter (equal jitter)** — випадковий розкид поверх backoff проти **thundering herd**.
  Канонічне джерело — стаття AWS «Exponential Backoff And Jitter».
- **Delayed queue через sorted set** — score = час готовності, periodic sweep переносить
  дозріле. Класична Redis-ідіома (так роблять Sidekiq, Bull, багато job-черг).
- **Dead Letter Queue** — куди йдуть події, що вичерпали ретраї (тут — шов для T2.4).
  SQS DLQ, RabbitMQ dead-letter exchange.
- **Policy/Mechanism separation** — «що вирішуємо» окремо від «як виконуємо». Тут
  `RetryScheduler` (policy) vs `Queue` (mechanism). Загальний принцип чистої архітектури.
- **Single source of truth з одним місцем інкременту** — конверт і БД отримують той самий
  номер з одного `retryOrFail`, тож не розходяться.

## 6. Арифметика спроб (без off-by-one)

Це місце, де джуни найчастіше плутаються. Розберімо точно.

- `enqueue` ставить **attempt = 1** (початкова доставка).
- `retryOrFail` рахує `next = job->attempt() + 1`; межа вичерпання — `next > MAX_ATTEMPTS (3)`.

| Pop `attempt()` | виклик обробника | результат | `next` | гілка | DB `attempts` | заплановано |
|---|---|---|---|---|---|---|
| 1 | обробка #1 | transient fail | 2 | `2 ≤ 3` → retry | 2 | `delayFor(2)` = 2–4с |
| 2 | обробка #2 | transient fail | 3 | `3 ≤ 3` → retry | 3 | `delayFor(3)` = 4–8с |
| 3 | обробка #3 | transient fail | 4 | `4 > 3` → вичерпано | — | interim `markFailed` |

**Підсумок: 3 реальні спроби обробки, 2 заплановані ретраї** — точно «max 3 attempts»
(FR-7). Зверни увагу: `delayFor(1)` (1–2с) **на шляху ретраю не використовується** —
перший *ретрай* чекає `delayFor(2)` = 2–4с. `delayFor(1)` визначено для повноти/чистоти
функції, але `retryOrFail` його не викликає (NIT-4).

## 8. Запити до бази даних

**Ad-hoc SQL у цій сесії я НЕ виконував.** Перевірки були лише через `php -l` (лінт) і
reflection-прогін `delayFor()` — жодного запиту проти БД я не запускав.

Але SQL, який **виконує сам код T2.3** (це частина фічі), такий:

`markForRetry()` — повертає рядок у `received` і записує лічильник + причину:

```sql
UPDATE webhook_events
SET status = 'received', attempts = :attempts, last_error = :error
WHERE id = :id
```

**Чому саме `received`, без guard?** Воркер тримає рядок у `processing` (він щойно виграв
claim), тож це його власна транзиція — guard не потрібен. А значення `received` критичне:
коли `promoteDue()` перенесе ретрай назад у чергу й воркер його дістане, **guarded
`markProcessing` (`WHERE ... AND status='received'`) має знову виграти claim**. Якби рядок
лишився, скажімо, у `processing`, guard зчепив би 0 рядків і легітимний ретрай ніколи б не
запустився. `processed_at` навмисно не чіпаємо — ретрай ще не завершився; штампує його лише
`markProcessed`.

`markFailed()` — запит **незмінений** (interim-гілка для вичерпаних/permanent, шов T2.4):

```sql
UPDATE webhook_events
SET status = 'failed', last_error = :error
WHERE id = :id
```

## 9. Підсумок рев'ю

Вердикт `T2.3-2026-06-06.md`: **Approve with nits**. Жодних BLOCKER / MAJOR /
MINOR-correctness — лише doc/spec-nit'и, усі свідомо прийняті або перенесені:

- **NIT-1:** напруга формулювань AC-3 «up to 3 times» vs FR-7 «max 3 attempts» — на власника
  спеки (код відповідає авторитетнішому FR-7).
- **NIT-2:** семантика колонки `attempts` для дашборда T3.x (див. §4).
- **NIT-3:** немає reaper для застряглого `received` — спільний борг із T2.2.
- **NIT-4:** `delayFor(1)` «мертвий» на шляху ретраю — опціональний docblock-коментар.
- **NIT-5:** дисципліна обсягу чиста (жодного DLQ/SIGTERM не просочилося).

Жодних змін коду рев'ю не вимагало.

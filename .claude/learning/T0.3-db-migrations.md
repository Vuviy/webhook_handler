# Навчальна нотатка: T0.3 — підключення до БД (PDO) + раннер міграцій + таблиця `webhook_events`

> Мова: українська. Аудиторія: junior → middle PHP.
> Підзадача: T0.3. ADR: [`.claude/decisions/0004-db-connection-and-migrations.md`](../decisions/0004-db-connection-and-migrations.md).

## 1. Проблема простими словами

Поки що у нашого вебхук-сервісу немає де зберігати події. А зберігати треба обовʼязково:
саме БД є **аудит-логом** кожного вебхука (специфікація FR-9) і одночасно джерелом правди
про стан обробки (`received → processing → processed/failed`). Без цього ми не зможемо ані
дедуплікувати повторні доставки, ані показати дашборд, ані зробити retry.

T0.3 закриває три речі, без яких далі рухатись неможливо:

1. **Підключення до MySQL через PDO** — тонка фабрика, яка віддає налаштований обʼєкт `\PDO`.
2. **Раннер міграцій** — щоб структуру БД можна було відтворити на будь-якій машині однією
   командою, і щоб історія змін схеми була зафіксована, а не «жила в чиїйсь голові».
3. **Перша міграція — таблиця `webhook_events`** — той самий аудит-лог.

Чому це важливо саме для системи вебхуків: провайдери (GitHub/Stripe/PayPal) доставляють
події за принципом **at-least-once** — той самий вебхук може прийти двічі (їхній ретрай,
таймаут на нашому боці тощо). Тому таблиця подій від першого ж рядка проєктується так, щоб
**повтор не створював дубль** — через композитний `UNIQUE (provider, event_id)`. Це фундамент
ідемпотентності, який ми «закладаємо в бетон» уже на рівні схеми, а не сподіваємось на
акуратний код пізніше.

Поза межами T0.3: Redis (T0.4), HTTP-прийом і `INSERT ... ON DUPLICATE KEY` (T1.5),
сам worker (T2.x).

## 2. Потік виконання

T0.3 — це інфраструктурний шар. Він ще не стоїть на «гарячому» шляху запиту, але саме він
робить решту потоку можливою. Покажу повний маршрут вебхука і відмічу, де працює те, що ми
зробили зараз:

```
provider POST /webhooks/{provider}
   │
   ▼
Nginx ──► PHP-FPM (ingestion-контролер)            ← T1.5
   1. читаємо RAW body
   2. timing-safe перевірка підпису (hash_equals)
   3. INSERT у webhook_events (status=received)     ← ТУТ працює T0.3:
      └─ PDO-зʼєднання (Connection::fromConfig)        таблиця + зʼєднання
      └─ UNIQUE(provider,event_id) ловить дублі
   4. RPUSH задачі в Redis                          ← T0.4
   5. повертаємо 202 Accepted
   │
   ▼
Redis queue ──► Worker (довгоживучий процес)        ← T2.x
   - pop задачі
   - dispatch у provider-handler
   - успіх  → UPDATE status=processed, processed_at  ← знову T0.3-таблиця
   - помилка → retry, backoff 2^n, attempts++
   - 3 невдачі → Dead Letter Queue, status=failed
   │
   ▼
MySQL (повний аудит-лог)  +  Dashboard (read-only)  ← читає webhook_events
```

А ось окремий «потік виконання» того, що ми зробили зараз — як працює міграція:

```
оператор: php bin/migrate.php
   │
   ▼
bootstrap.php → Config (host/db/user/pass з ENV)
   │
   ▼
Connection::fromConfig() → new PDO(...)            ← кидає DatabaseException БЕЗ пароля при збої
   │
   ▼
MigrationRunner::run()
   1. ensureMigrationsTable()  → CREATE TABLE IF NOT EXISTS schema_migrations
   2. appliedMigrations()      → SELECT migration FROM schema_migrations
   3. glob(migrations/*.sql)   → false ⇒ DatabaseException (не «тиха» порожнеча!)
   4. sort() за іменем файлу   → детермінований порядок 0001, 0002, ...
   5. для кожного НЕзастосованого файлу:
        a) exec(вміст .sql)            ← DDL виконується (auto-commit)
        b) INSERT ... schema_migrations ← запис ТІЛЬКИ після успіху DDL
   │
   ▼
друк: «Applied: ...» або «Database is up to date»; exit 0 / exit 1
```

## 3. Чому саме так

Деталі — в ADR 0004, тут головне.

**Чому власний `.sql`-раннер (Option A), а не альтернативи.**
- *Option B — один `schema.sql` з `IF NOT EXISTS`.* Простіше, але не фіксує **історію**:
  ти не знаєш, що і коли застосовано. Гірше — він **мовчки пропускає дрейф схеми**: якщо ти
  додав колонку в існуючу таблицю, `CREATE TABLE IF NOT EXISTS` просто нічого не зробить, і
  різниця між кодом і реальною БД залишиться непоміченою. Відхилено.
- *Option C — бібліотека міграцій (Doctrine Migrations, Phinx).* Зручно, але порушує hard-rule
  проєкту **framework-free**, тягне залежності й «магію». Для навчального проєкту це ховає саме
  ту механіку, яку ми хочемо зрозуміти. Відхилено.
- *Option A — наш вибір:* плоскі `.sql` + таблиця `schema_migrations`, **forward-only**.
  Прозоро, відтворювано, без залежностей, історія застосувань зберігається в самій БД.

**Чому запис у `schema_migrations` робиться ТІЛЬКИ після успіху DDL.**
Це найважливіший нюанс. У MySQL **DDL не транзакційний**: кожна `CREATE/ALTER` робить неявний
`COMMIT`. Тобто не можна обернути міграцію в `BEGIN … ROLLBACK` і відкотити при помилці — як
у звичайних `INSERT/UPDATE`. Якщо ми спершу запишемо «застосовано», а потім DDL впаде, у нас
буде брехливий запис. Тому порядок зворотній: спершу `exec($sql)`, і лише якщо він не кинув
виняток — `INSERT` у `schema_migrations`. Якщо процес впаде між DDL і `INSERT` — файл
залишиться «pending» і застосується знову; саме тому DDL зроблено **ідемпотентним**
(`CREATE TABLE IF NOT EXISTS`) і **одна інструкція на файл** — повторний прогін не зламається.

**Чому `Connection` — тонка фабрика, а не wrapper-клас.**
Спокуса junior-а: загорнути PDO у свій `Database`-клас з методами `query()`, `fetch()` тощо.
Але це абстракція з єдиною реалізацією — вона нічого не додає, лише ховає стандартний PDO API,
який і так гарний. Правило проєкту: не плодити абстракції заради абстракцій. `Connection`
лише **конфігурує** PDO і віддає чистий `\PDO`. Виклики далі працюють з prepared statements
напряму.

**Чому саме ці три атрибути PDO.**
- `ERRMODE_EXCEPTION` — щоб помилки **кричали** винятком, а не поверталися як `false`, який
  легко проґавити. Гучний збій > тихий збій.
- `EMULATE_PREPARES = false` — **справжні** серверні prepared statements. Це не косметика:
  емуляція клеїть значення в рядок запиту на боці PHP, а справжні — відправляють SQL і дані
  окремо, що є коректним захистом від SQL-ін'єкцій.
- `DEFAULT_FETCH_MODE = FETCH_ASSOC` — асоціативні масиви за замовчуванням, без дубльованих
  числових ключів.

**Чому виняток ніколи не містить пароля.**
`DatabaseException::connectionFailed()` приймає лише host і db — не пароль і не повний DSN.
Бо повідомлення винятків потрапляють у логи й стектрейси, а секрети в логах — це класичний
витік. Правило проєкту: секрети тільки через ENV, ніколи не логуються.

**Чому `UNIQUE (provider, event_id)` саме композитний.**
`event_id` унікальний лише в межах одного провайдера — GitHub і Stripe можуть теоретично
видати однаковий рядок-id. Тому ключ складений з пари. Це дозволить у T1.5 писати
`INSERT ... ON DUPLICATE KEY UPDATE` і безпечно ігнорувати повторні доставки.

## 4. Слабкі місця та технічний борг

Це робоче рішення для поточного масштабу, але чесно про межі:

- **Forward-only, без `down`-міграцій.** Відкату немає. Помилкову міграцію виправляють новою
  міграцією-«вперед», а не rollback-ом. Для невеликого проєкту це нормально й навіть безпечніше,
  але треба памʼятати: зіпсував схему — пиши `0002_fix...`, а не «відкочуй».
- **Великі DDL на «живій» таблиці.** Зараз таблиця порожня. Коли в `webhook_events` будуть
  мільйони рядків, `ALTER TABLE` може надовго залочити таблицю. Раннер цього не вирішує —
  це питання операційне (online DDL, вікно обслуговування).
- **Немає блокування паралельних прогонів.** Якщо два `migrate.php` стартують одночасно
  (наприклад, у двох контейнерах при деплої), обидва можуть спробувати застосувати той самий
  файл. `PRIMARY KEY (migration)` врятує від дубля-запису, але один з процесів впаде з помилкою.
  Для prod-сценарію знадобився б advisory lock.
- **`LONGTEXT` для payload.** Гнучко, але payload-и зберігаються «як є»; за великих обсягів це
  тисне на розмір таблиці й на бекапи. Поки прийнятно.
- **`payload NOT NULL` без перевірки на боці схеми.** Валідність JSON гарантує лише код
  прийому (T1.5), не БД. Памʼятати при дедупі.
- **Дрейф схеми все одно можливий вручну.** Якщо хтось зробить `ALTER` напряму в БД, поза
  міграцією — `schema_migrations` про це не дізнається. Дисципліна > інструмент.

Точка зростання (дрібниця, але корисно знати): у `apply()` ми читаємо весь файл і виконуємо
як один `exec()`. Це свідомо обмежує нас «одна інструкція на файл». Якщо junior пізніше
покладе в один `.sql` дві інструкції через `;`, це може спрацювати не так, як очікується, і
зламає гарантію ідемпотентного ретраю. Тримаймо правило «один файл = одна DDL-інструкція».

## 5. Патерни, які варто запамʼятати

- **Schema migrations / forward-only migrations** — таблиця-трекер застосованих змін схеми.
  Той самий патерн всередині Rails (`schema_migrations`), Doctrine Migrations, Flyway, Liquibase,
  Alembic. Ми зробили його руками, щоб зрозуміти кишки.
- **Idempotency key** — `UNIQUE (provider, event_id)`. Зустрічається скрізь, де є at-least-once
  доставка: Stripe `Idempotency-Key` header, платіжні API, обробка повідомлень з Kafka/SQS.
- **At-least-once delivery → idempotent consumers** — фундаментальна звʼязка розподілених
  систем: якщо доставка може повторитись, споживач мусить бути ідемпотентним. Наша схема готує
  до цього вже зараз.
- **Fail loud, not silent** — `ERRMODE_EXCEPTION` і `glob()===false → виняток` замість тихого
  «нема що застосовувати». Принцип: помилку краще побачити одразу, ніж дебажити «чому БД порожня».
- **Thin factory замість wrapper** — не загортай стандартний API в абстракцію з єдиною
  реалізацією. Загальний принцип YAGNI / «не вгадуй майбутню гнучкість».
- **Secrets out of error messages** — типізований виняток, що навмисно не приймає пароль.
  Перетинається з безпекою логування загалом.

## 6. Покрокова хроніка

> Реальні команди й вивід, як вони виконувались.

**Крок 1. Перевірка стану задач.**

рев'ю й цієї нотатки.

**Запити, що їх виконує сам раннер** (`MigrationRunner` / міграція):

```sql
-- ensureMigrationsTable(): bootstrap таблиці-трекера
CREATE TABLE IF NOT EXISTS schema_migrations (
    migration  VARCHAR(255) NOT NULL,
    applied_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (migration)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- appliedMigrations(): які файли вже застосовано
SELECT migration FROM schema_migrations;

-- apply(): запис ТІЛЬКИ після успіху DDL (prepared statement, плейсхолдер)
INSERT INTO schema_migrations (migration) VALUES (?);
```

```sql
-- вміст самої міграції 0001_create_webhook_events.sql
CREATE TABLE IF NOT EXISTS webhook_events (
    id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    provider        VARCHAR(32)     NOT NULL,
    event_id        VARCHAR(255)    NOT NULL,
    event_type      VARCHAR(128)    NOT NULL,
    payload         LONGTEXT        NOT NULL,
    signature_valid TINYINT(1)      NOT NULL DEFAULT 0,
    status          ENUM('received', 'processing', 'processed', 'failed') NOT NULL DEFAULT 'received',
    attempts        INT UNSIGNED    NOT NULL DEFAULT 0,
    last_error      TEXT            NULL,
    created_at      TIMESTAMP       NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMP       NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    processed_at    TIMESTAMP       NULL DEFAULT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uq_provider_event (provider, event_id),
    KEY idx_status (status),
    KEY idx_created_at (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```
